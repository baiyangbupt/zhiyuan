# Release 3.0.1 Stability Plan

本文档定义 `3.0.1` 稳定修复版计划。该版本不是新功能大版本，目标是在 `prod-3.0.0` 已完成迁移和上线验证的基础上，集中修复用户反馈中影响 Web 端可用性、方案调整效率和结果可信度的问题。

默认范围：

- 优先处理 PC/Web 版本。
- 移动端是否同步适配单独评估；如适配，必须补充独立移动端验证。
- 不在本版本内重构整体部署形态、不大改算法主链路、不做大规模 UI 重设计。
- `sessionDetailLegacy` 不再继续做体验优化，后续逐步统一到新版 `sessionDetailV2`。
- 用户侧不再展示“草稿”概念；内部 draft 结构只作为实现细节，前端统一使用“方案”语言。
- 新版本不设计提交状态；历史版本兼容的已提交方案只展示为历史只读提示。

## 0. 文档关系

本文是 `3.0.1` 的版本计划，是范围和优先级的唯一来源。它负责回答：

- 这个版本为什么做。
- 哪些问题进入 `3.0.1`。
- 哪些问题不进入 `3.0.1`。
- 发布前必须满足哪些准入条件。

`docs/release-3.0.1-implementation-design.md` 是实施设计，只承接本文已经确认进入版本的事项。它负责回答：

- 后端状态、接口、数据结构怎么改。
- 前端组件和交互怎么落。
- 测试用例怎么覆盖。
- 还有哪些技术取舍未定。

维护原则：

- 新增用户反馈先进入本文或 backlog，确认优先级后再进入 implementation design。
- 同一条需求的优先级和是否进入版本只在本文维护。
- implementation design 不重复维护完整 P0/P1 清单，只写具体实现。

## 1. 版本目标

`3.0.1` 需要解决三类问题：

1. 结果可信度：导出序号、无候选/候选过少风险提示、方案历史分数展示。
2. 操作效率：返回会话列表、排序、指定位置移动、专业组组级操作、回到顶端。
3. 产品心智：理清候选、方案、审查、导出状态，统一冲稳保颜色，释放方案操作空间。

版本成功标准：

- Web 端用户能清楚进入和退出会话详情页。
- 用户能更高效地查看、排序、移动和导出方案。
- 关键异常状态有明确提示，不再表现为“生成成功但没有方案”。
- 方案展示和导出结果一致，序号连续，历史分数信息可用于调整参考。
- 候选、方案、审查、导出状态有清晰可见的入口和解释，不再混用“草稿”“区间顺序合理”“待调整”等弱状态文案。

## 2. 版本范围

### 2.1 必须进入 3.0.1

#### P0-1 导出文件志愿序号连续

问题：

- 当前方案导出文件里志愿序号可能不连续。

方案：

- 后端导出时基于当前排序结果重新生成连续序号。
- 不复用历史 `position` 或中间状态里可能已失效的序号。
- 覆盖新建方案、迁移方案、手动移动后方案。

验收：

- Excel 序号从 1 连续递增。
- 页面顺序与导出顺序一致。
- 专业模式和专业组模式均通过。

#### P0-2 无候选/候选过少风险提示

问题：

- 专项计划、分数线边界、筛选条件过窄时，可能生成空方案或很少候选。
- 当前用户难以判断原因。

方案：

- 后端候选生成阶段识别空候选和候选过少状态。
- 写入明确操作日志或状态码，例如 `candidate_pool_empty`、`candidate_pool_low_count`。
- 前端展示可理解提示，说明可能原因：专项资格、批次、分数线、筛选条件、地区/专业偏好。

验收：

- 空候选不再静默显示为成功空方案。
- 候选过少时页面有明确提示和调整建议。
- 覆盖专项过滤、分数线边界、筛选过窄测试。

#### P0-3 B 端返回会话列表入口

问题：

- 详情页入口偏 C 端，B 端用户不知道如何回到会话列表。

方案：

- Web 详情页增加稳定、明显的“返回会话列表”入口。
- 默认返回 `/assistant-pc/session`。
- 如页面来源能识别客户详情页，可保留来源返回能力，但不作为首期强依赖。

验收：

- 用户不依赖浏览器返回按钮即可回到会话列表。
- `/assistant-pc/sessionDetailV2` 不出现导航断点；`sessionDetailLegacy` 不再追加体验优化。

#### P0-4 方案状态管理和审查入口

问题：

- 当前面板里能看到“区间顺序合理”“待调整”等状态，但状态含义和流转不够清晰。
- 审查结果已经留在面板里，但缺少直接触发审查的入口。

方案：

- 明确状态分层：候选生成状态、方案状态、审查状态、导出/反馈状态。
- 前端把状态文案改成用户能理解的组合描述，例如“方案已生成，存在待确认调整”“审查通过”“审查发现风险，需要查看”。
- 在方案面板提供明确的“重新审查/执行审查”入口，调用现有 review 接口。
- 审查结果只作为风险判断和解释入口，不隐式改变方案顺序。
- 状态枚举、状态优先级和转换过程以 `docs/release-3.0.1-implementation-design.md` 的“状态值和状态转换”章节为准。

验收：

- 用户能看到当前方案处于已生成、待调整、审查通过或审查有风险中的哪一种。
- 用户能直接从方案面板触发审查。
- 审查触发、结果刷新和风险提示有明确反馈。

### 2.2 应进入 3.0.1

#### P1-1 方案排序能力

方案：

- 方案列表支持按以下维度临时排序：
  - 当前顺序
  - 录取率
  - 院校层次
  - 推荐系数
- 默认是“查看排序”，不直接改写方案顺序。
- 如需要应用排序结果，必须有明确确认动作。

验收：

- 可恢复原方案顺序。
- 临时排序不改变导出顺序，除非用户确认应用。

#### P1-2 展示近三年录取分数/位次

方案：

- 在方案志愿行展示近三年录取分数和位次摘要。
- 数据优先使用现有 `schoolHistoryScores / majorHistoryScores`。
- 缺失年份显示“暂无”，不展示 `0`、`-1` 等内部占位。

验收：

- 方案区和候选区历史分数口径一致。
- 专业组模式下展示口径明确，不误导用户。

#### P1-3 指定目标位置移动

方案：

- 支持“移动到第 N 位”。
- 支持快捷动作：移到顶部、移到底部。
- 后端优先提供一次性目标位置移动能力，避免前端循环调用上移/下移。

验收：

- 移动后序号连续。
- 固定、锁定、历史已提交只读等规则仍生效。
- 移动后审查状态进入待重新审查，避免继续展示旧顺序下的审查结论。

#### P1-4 专业组组级删除和移动

方案：

- `majorGroup` 模式下提供组级移动、删除、固定能力。
- 组内专业随组整体移动，组内顺序保持。
- 前端区分“专业组操作”和“组内专业操作”。

验收：

- 删除专业组不会残留孤立专业。
- 移动专业组不会打散组内专业。

#### P1-5 概念和视觉收敛

包含：

- 前端不再露出“草稿”，候选下方篮子直接作为“方案”入口。
- 冲稳保颜色统一：冲=红，稳=橙，保=绿。
- 顶部数字概览可折叠或隐藏。
- 方案和候选增加“回到顶端”。
- 候选 tab 中的方案篮子色系需要与候选志愿条目明显区分，避免同样偏红导致用户混淆。
- 长列表增加滚动滑杆或快速定位能力，方便用户在方案和候选列表中快速移动。
- 候选筛选标签优化：城市名默认展开过长时需要折叠、搜索或分组，避免用户难以定位目标筛选项。

验收：

- 页面主流程中用户能理解“候选 -> 方案 -> 审查 -> 导出”的流转。
- 折叠顶部概览后，方案操作区域可视空间增加。
- 冲稳保颜色和文字标识同时存在。
- 方案篮子和候选志愿条目视觉上能明显区分。
- 方案和候选长列表可以快速滚动或定位。
- 候选筛选区默认高度可控，城市类标签可以快速查找和展开。

#### P1-6 方案调整和导出行为反馈闭环

问题：

- 当前系统能生成和调整方案，但缺少用户后续如何调整、删除、移动和导出的结构化记录。
- 后续要优化方案构建策略、排序策略和 Agent 规划能力，需要知道哪些推荐被用户保留、哪些被移动、哪些被删除。
- 导出通常代表用户对当前方案有较强认可，可先作为正反馈事件记录。

方案：

- 后端记录方案操作事件，至少覆盖：
  - 添加候选到方案。
  - 从方案删除志愿。
  - 单条移动、移动到目标位置。
  - 专业组模式下的组级移动和删除。
  - 应用排序结果。
  - 导出方案。
- 事件中保留必要上下文：`chatSessionId`、操作类型、操作前后位置、志愿/专业组标识、冲稳保层级、录取率、模式 `major/majorGroup`、是否来自新建或迁移方案、时间戳。
- 导出事件标记为正反馈，但不直接等同于最终录取或真实填报结果。
- 前端只负责在用户触发操作时调用对应接口；以服务端实际成功后的状态为准记录事件，避免失败操作进入反馈数据。

验收：

- 用户完成添加、删除、移动、排序应用、导出后，服务端能查询到对应事件。
- 导出事件能关联到当时的方案快照或版本号。
- 行为记录不影响主流程成功率，记录失败时不能阻断用户继续操作。

### 2.3 不进入 3.0.1

以下问题记录但不作为 3.0.1 交付范围：

- 大规模算法重构，例如把 `probability_gap` 从软约束升级成硬约束。
- 后端全容器化或部署架构重构。
- 完整移动端重设计。
- 模型计费监控平台化。
- 基于行为反馈数据直接训练或上线新推荐策略。
- 老会话迁移全量重算。
- `sessionDetailLegacy` 体验优化和新增交互。

其中模型计费监控可以在 3.0.1 中先补最小日志字段，但报表和平台化能力放到后续版本。
行为反馈闭环在 3.0.1 中先完成事件采集和可追溯查询，策略分析、算法调参和自动优化放到后续版本。

## 3. 实施拆分摘要

### 3.1 后端

后端负责提供稳定的数据、状态和服务端行为记录能力：

- 导出顺序和序号正确。
- 候选池为空或偏少时有明确状态。
- 工作区返回候选、方案、审查、导出等状态口径。
- 支持目标位置移动和专业组组级操作。
- 记录方案调整和导出行为事件。

详细字段、接口和测试见 `docs/release-3.0.1-implementation-design.md`。

### 3.2 前端 Web

前端 Web 负责把状态和操作变成清晰、可用的工作台体验：

- 新版详情页返回会话列表。
- 方案排序、历史分数、目标位置移动、组级操作。
- 审查入口和状态展示。
- 方案篮子视觉区分、候选筛选标签优化、长列表快速定位。
- 顶部空间、回到顶端、冲稳保颜色等体验优化。

详细组件交互和前端验证见 `docs/release-3.0.1-implementation-design.md`。

### 3.3 Agent 和模型

Agent 和模型本期不是主改造对象：

- 本版本不默认改模型策略。
- 如涉及快捷回复或方案解读文案，需沿用现有 benchmark 场景验证延迟和效果。
- 可补最小调用日志字段：model、provider、scene、latency、status、errorType。

## 4. 验证计划

### 4.1 本地准生产验证

使用本机准生产拓扑：

- Web：`3088 -> 28688`
- Backend：`8090`
- Agent：`8091 -> 8009`
- Rank：`8092 -> 5001`

必须验证：

- `/assistant-pc/session`
- `/assistant-pc/sessionDetailV2`
- 新建会话初始化。
- 外部授权初始化会话。
- 方案排序、移动、删除、导出。
- 空候选/候选过少提示。

### 4.2 数据样本

至少覆盖：

- 新建 `major` 模式会话。
- 新建 `majorGroup` 模式会话。
- 历史 `_final` 已提交方案。
- 历史 `_temp` 未提交方案。
- 专项过滤导致空候选或少候选样本。
- 手动移动后导出样本。
- 用户调整后导出样本，用于验证行为事件和方案快照关联。

### 4.3 移动端边界验证

若 3.0.1 Web 改动影响共享组件，需要至少做移动端冒烟：

- 详情页能打开。
- 方案列表不横向撑破。
- 标题、冲稳保、概率、学校/专业组名称不重叠。
- PC 新增按钮不挤压移动端布局。

如果移动端也要完整适配，需要另起移动端设计文档。

## 5. 发布准入

发布前必须满足：

1. 后端测试通过，新增测试覆盖 P0/P1 核心逻辑。
2. 前端 build 通过。
3. 本地准生产演练通过。
4. 导出 Excel 序号连续。
5. 新建会话和历史迁移会话均能查看、排序、移动、导出。
6. 方案调整和导出行为能被记录，且记录失败不阻断用户主流程。
7. 前端生产包仍为 `/assistant-pc` 路径，且不包含 `ws://localhost:8000`。
8. changelog 更新 backend/frontend/agent 相关模块。
9. 文档更新包含已知限制和回滚方式。

## 7. 风险和开放问题

1. 方案排序是否只用于查看，还是允许一键应用到方案顺序，需要产品确认。
2. 专业组组级操作与组内专业操作的优先级和边界需要明确。
3. 历史分数展示在专业组模式下的口径需要统一，否则容易误导。
4. 空候选/少候选提示需要区分“系统没有数据”和“用户条件过滤过窄”。
5. 移动端是否同步适配需要单独排期，不建议默认混入 Web 修复。
6. 行为反馈事件的存储介质、保留周期和是否需要脱敏，需要在详细设计中确认。
