# Release 3.0.0 Backlog

本文档汇总当前 `3.0.0` 上线、迁移、算法和运维层面的遗留问题与待完善点。它不是新的设计方案，而是 release 收口和后续迭代的 backlog。

当前处理原则：

- P0 项作为 `3.0.0` 最终生产可用包的准入条件。
- P1/P2 项不阻塞本期发布，统一延后到后续版本修复或优化。
- 已知算法展示问题需要在产品和研发侧保留风险认知，但不继续扩大本期发布范围。

相关文档：

- `docs/production-upgrade-implementation-steps.md`
- `docs/legacy-to-v2-upgrade-migration-plan.md`
- `docs/legacy-to-v2-upgrade-migration-status.md`
- `docs/system-health-and-ops-design.md`
- `zhiyuan-server/docs/plan-generation-engine-design.md`

## 1. 当前版本锁定状态

当前代码版本号已经统一为 `3.0.0`：

| 模块 | 版本位置 | 当前值 |
| --- | --- | --- |
| backend | `zhiyuan-server/pom.xml` | `3.0.0` |
| frontend | `zhiyuan-web/package.json` | `3.0.0` |
| agent | `zhiyuan-agent/pyproject.toml` | `3.0.0` |

Release 锁定原则：

1. 发布包必须基于固定 commit，不从本地脏工作区直接打包。
2. 后端 JAR、前端镜像、Agent 镜像、备份目录和部署记录必须使用同一个 release 标识。
3. `v3.0.0` tag 应在构建验证、真实样本验证、灰度前检查和生产关键链路确认后创建。
4. 生产环境不做编译构建，只接收已经验证过的 JAR、Docker 镜像或镜像 tar。
5. 当前本地允许存在 `.env`、`tsconfig.tsbuildinfo`、临时样本 JSON 等调试文件，但这些内容不能进入 release 包。

当前线上 3.0.0 记录以 `docs/production-upgrade-implementation-steps.md` 为准：

- 后端使用 `zhiyuan-server-3.0.0-prod.service`，当前生产记录的修复版 commit 为 `2221541`。
- 前端使用 `zhiyuan-web-3.0.0-prod`，当前线上镜像记录为 `zhiyuan-web:3.0.0-amd64-wsfix`。
- Agent 使用 `zhiyuan-agent-3.0.0-prod`，镜像记录为 `zhiyuan-agent:3.0.0-amd64`。
- Rank 暂不随本次迁移升级，继续使用既有容器。

## 2. P0：发布锁定前必须收口

### 2.1 固定最终 release commit

现状：

- 3.0.0 版本号已统一。
- 生产实施文档已经记录固定 commit、构建边界、产物路径和回滚命令。
- 近期生产热修包含新建会话不触发 legacy 懒导入、前端 WebSocket 地址修复等内容。

待完成：

- 确认 `develop` 已包含所有生产热修和文档补充。
- 执行 `git status --short --branch`，确保 release tag 前没有未确认的代码变更。
- 用最终 commit 更新生产实施文档中的 release commit 记录。
- 创建 `v3.0.0` tag 前再次确认本地调试文件未进入提交或 release 包。

验收：

- `git rev-parse --short HEAD` 与构建产物、部署记录、tag 记录一致。
- release 包可以追溯到唯一 commit。

### 2.2 前端生产包路径和 WebSocket 地址复核

现状：

- 正式生产入口是 `/assistant-pc`。
- 前端生产包必须使用 `APP_ENV=production` 或等价非 `dev` 构建，使 `basePath=/assistant-pc`。
- `NEXT_PUBLIC_AGENT_WS_BASE` 是 Next.js 构建期变量，不能只在容器运行时补充。

待完成：

- 每次重新构建前端镜像前，确认 `.env.prod` 包含 `NEXT_PUBLIC_AGENT_WS_BASE=wss://www.gaotuzhiyuan.com`。
- 构建后检查产物中不存在 `ws://localhost:8000`。
- 验证 `/assistant-pc/sessionDetailV2`、`/assistant-pc/sessionDetailLegacy` 和 `/assistant-pc/session` 均可访问。
- `sessionDetailLegacy` 后续不再继续追加体验优化，新交互统一收敛到 `sessionDetailV2`。

验收：

- 浏览器侧发送消息后，Agent 日志能看到真实 `session_id` 进入处理。
- 公网 WebSocket 路径返回 `101 Switching Protocols`。

### 2.3 新建会话主链路回归

现状：

- 生产曾出现新建会话被 legacy 懒迁移逻辑污染的问题，远端已修复。
- 当前新建会话应走 V2 初始化和初始方案生成，不应把候选池全量塞入排序区。

待完成：

- 覆盖 `major` 和 `majorGroup` 两种模式的新建会话回归。
- 检查 `orderedPlanState.generationMode` 应为 `initial_auto`，不是 `legacy_plan_import / legacy_submitted`。
- 检查排序区数量与目标数量一致：专业模式看专业条目数，专业组模式看专业组 unit 数。

验收：

- 新建会话不会读取老方案 JSON。
- 候选池、草稿、排序区边界清晰，不再出现几百到几千条原始候选进入排序区。

### 2.4 真实老会话迁移抽样

现状：

- 老方案文件选择口径已修正：`_final.json` 优先，`_temp.json` 次之，无后缀原始文件只作为兜底。
- 已补充专业+大学和院校专业组两种模式的样本测试。

待完成：

- 继续用生产样本目录做小范围真实会话对账。
- 每个抽样会话尽量包含无后缀、`_temp.json`、`_final.json` 三件套，用于验证文件选择逻辑。
- 已提交历史方案应从 `_final.json` 进入排序区并锁定；提交前推荐方案应从 `_temp.json` 进入排序区；原始全量候选不应被当作优选。

验收：

- 迁移日志能明确记录 source、item/unit 数量和 generationMode。
- 单会话回滚脚本 dry-run 可用，必要时能删除对应 `planningState` 重新触发迁移。

## 3. P1：算法和产品展示遗留问题

状态：延后到 `3.0.x` 或后续规划版本处理，不阻塞 `3.0.0` 最终生产包。

### 3.0 空候选初始化失败可见性

现状：

- 生产会话 `2096`、`2104` 观察到新建会话后没有初始化方案。
- 日志显示 `/initial-plan/generate` 已被调用并返回成功，因此不是前端未触发生成。
- `2096` 原始文件 `/apps/volunnter-tmpdata/session_volunteer_2096.json` 中 14 个专业组、41 个专业全部为 `国家专项/地方专项`。
- `2104` 原始文件 `/apps/volunnter-tmpdata/session_volunteer_2104.json` 中 `schoolTotalNum=106`、`majorTotalNum=460`，460 个专业全部为 `国家专项/地方专项`。
- 用户请求中 `specialPlan=false`，当前过滤链会正确剔除专项候选，过滤后候选数为 0。

问题：

- 当前生成链路会把空候选池当作成功结果落入 `candidatePoolState`，进而生成空 `initialRecommendationState / orderedPlanState`。
- 前端看到的是“初始化成功但没有方案”，用户无法判断是资格/筛选条件导致无候选，还是系统生成失败。
- 直接放开专项候选不合理；`specialPlan=false` 时推荐专项计划会产生合规和产品风险。

待完善：

- `generateCandidatePool` 在冲/稳/保平铺结果全部为空时，应返回明确业务错误，不应静默写入空候选、空初始方案和空排序方案。
- 保留待生成状态并记录可观测操作日志，例如 `candidate_pool_empty`，便于客服和运维定位。
- 前端需要把该错误展示为用户可理解提示，例如“当前条件下没有可用志愿候选，请检查专项计划资格、批次或筛选条件”。
- 后续可继续检查上游推荐接口入参，确认为什么普通本科批请求只返回专项计划候选。

处理决定：

- 本项记录为 `3.0.x` 后续修复，不进入当前 `prod-3.0.0` 锁版代码。
- 当前 `prod-3.0.0` 以已锁定 commit 和已验证产物为准，不因该 backlog 项移动 release tag。

### 3.1 `probability_gap` 不是硬约束

现状：

- 当前初始方案生成会尝试修复相邻录取率断层，但属于 best-effort。
- 判断阈值为相邻 `admissionRatio` 差值 `> 8`。
- 修复动作需要同时改善整体 gap 指标，且不能恶化冲稳保配额偏差。
- 生产会话 `2076` 已出现 `gapFixCount=3` 后仍剩余 `unresolvedGapCount=2` 的情况。

问题：

- 产品和用户容易理解为“系统保证相邻录取率差值不超过 8”，但当前实现无法保证。
- 当候选池缺少中间梯度候选，或修复会破坏冲稳保配额时，系统会返回仍存在断层的方案。

待完善：

- 明确产品口径：`probability_gap` 是提醒项、软约束，还是生成阶段硬约束。
- 如果要升级为硬约束，需要重新设计生成策略：扩大替换窗口、允许跨 tier 小幅借位、或无法满足时返回需要人工确认的状态。
- 增加 `2076` 类似的 `majorGroup` 回归样本，覆盖“已修复但仍 unresolved”的情况。

### 3.2 `gradientOk` 与 review 结论不一致

现状：

- `orderedPlanState.summary.gradientOk` 当前更接近顺序/倒挂检查。
- `reviewState.checks.probability_gap` 才能表达相邻录取率断层。

问题：

- 可能出现 `gradientOk=true`，但 `reviewState.checks.probability_gap.passed=false`。
- 如果前端只展示 summary，会让用户误以为梯度完全通过。

待完善：

- 方案一：把 `probability_gap` 纳入 `gradientOk`。
- 方案二：把 `gradientOk` 改名为 `sequenceOk`，另增 `gapOk` 或直接展示 review 结果。
- 前端方案页优先读取并展示 `reviewState.checks.probability_gap`。

### 3.3 `majorGroup` 断层详情展示不足

现状：

- `majorGroup` 模式下 review 详情偏向展示首个断层样例。
- summary 里有剩余断层数量，但用户不一定能看到。

待完善：

- review 结果中补充断层列表或至少展示断层数量。
- 前端用用户能理解的语言展示：例如“有 2 处相邻专业组录取率跨度较大，建议重点确认这几个位置”。

## 4. P1：运维和部署完善

状态：发布必须保留当前已有健康检查和回滚命令；脚本化、一键化和观测面板延后完善。

### 4.1 健康检查脚本纳入发布流程

现状：

- 已新增 `ops/healthcheck.sh` 和 `ops/migration-status.sh`。
- 生产实施文档已记录健康检查、迁移日志观察和回滚命令。

待完善：

- 将健康检查结果作为发布前和发布后固定记录项。

- 补充失败时的处理分支：后端失败、前端失败、Agent WebSocket 失败、迁移异常分别对应不同回滚动作。

### 4.2 混合部署形态继续收口

现状：

- backend 由 systemd 托管。
- web / agent / rank 使用 Docker 容器。
- 短期不要求为了 V2 迁移改成全容器或 Kubernetes。

待完善：

- 后续可以考虑把 backend 也容器化，减少 systemd + Docker 混合部署的认知成本。
- 前端根路径部署和 `/assistant-pc` 部署需要拆成明确环境，不再依赖 `APP_ENV=dev` 规避 `basePath`。
- 镜像仓库或离线 tar 包流程需要固定，避免生产环境临时构建。

### 4.3 敏感配置管理

现状：

- `LLM_API_KEY` 等敏感信息不写入仓库文档。
- Agent 的大模型配置通过容器环境变量传入。

待完善：

- 生产 `.env`、systemd env 文件、Docker Compose override 文件需要统一纳入服务器侧备份和权限管理。
- 文档中只记录配置项名称、用途和示例占位值，不记录真实 key。
- 发布前检查提交中不包含真实 `API_KEY / token / password`。

## 6. 网页版用户反馈优先级

本节汇总 3.0.0 上线后面向网页版的产品反馈。默认先处理 PC/Web 版本；移动端是否同步适配单独评估，若适配需要补独立移动端验证。

### 6.1 P0：影响核心使用闭环或数据正确性

#### 6.1.1 导出文件志愿序号不连续

问题：

- 当前方案导出的文件里志愿序号可能不连续。
- 导出结果是用户最终留存和提交前核对的重要材料，序号错误会直接影响可信度。

处理建议：

- 后端导出时以当前排序区有效顺序重新生成连续序号，不直接复用中间状态里的历史 position。
- 覆盖普通专业模式和专业组模式导出测试。
- 对迁移导入方案、新建自动方案、手动移动后的方案分别做导出回归。

验收：

- 导出 Excel 中序号从 1 连续递增，无跳号、重号。
- 前端展示顺序与导出顺序一致。

#### 6.1.2 无候选或候选过少风险提示

关联已有 backlog：`3.0 空候选初始化失败可见性`。

问题：

- 类似四川本科 A 全是专项，用户未选择专项时会过滤到无候选或候选很少。
- 用户分数介于分数线附近时，也可能出现可选志愿较少或无可用志愿。
- 当前容易表现为“没有生成方案”或“方案很少”，用户不知道原因。

处理建议：

- 候选池生成后增加可解释的空结果/少结果状态，例如 `candidate_pool_empty`、`candidate_pool_low_count`。
- 前端用用户语言提示：专项资格、批次、分数线、筛选条件、地区/专业偏好可能导致候选不足。
- 对专项过滤、分数线边界、筛选条件过窄分别补测试。

验收：

- 无候选时不静默进入空方案成功态。
- 候选过少时页面展示明确原因和可操作建议。

#### 6.1.3 B 端会话返回路径不清晰

问题：

- 默认会话界面偏 C 端心智。
- B 端用户需要能明确回到会话列表。
- 当前详情页会话列表入口不够明显，用户不知道从哪里返回。

处理建议：

- PC/Web 详情页顶部或左上角增加稳定的“返回会话列表”入口。
- 保留现有 C 端对话体验，但 B 端工作流下优先展示会话列表导航。
- 如果存在不同入口来源，支持根据来源决定返回 `/assistant-pc/session` 或客户详情页。

验收：

- 用户从详情页一眼能找到回会话列表入口。
- 不依赖浏览器返回按钮完成核心导航。

### 6.2 P1：高频操作效率和方案可读性

#### 6.2.1 方案支持多维排序

问题：

- 当前方案查看和调整效率不足。
- 用户希望按录取率等维度排序，快速识别高风险或低风险志愿。

处理建议：

- 在方案区增加排序能力，优先支持：当前位置、录取率、院校层次、推荐系数。
- 不再提供冲稳保、专业名、学校名、分数/位次排序入口，避免入口过多影响主流程。
- 排序应区分“临时查看排序”和“改写方案顺序”。默认建议先做临时查看排序，避免用户误改最终顺序。
- 若要把排序结果应用到方案，必须有明确确认动作。

验收：

- 排序不破坏原方案顺序，除非用户确认应用。
- 支持恢复默认排序。

#### 6.2.2 方案志愿展示近三年录取分数

问题：

- 用户移动志愿时缺少近三年录取分数/位次参考。
- 当前只能基于名称、冲稳保和录取概率做判断，信息不足。

处理建议：

- 方案志愿行展示近三年分数和位次摘要，信息来自现有 `schoolHistoryScores / majorHistoryScores`。
- 默认展示紧凑摘要，展开后查看详细年份、分数、位次、计划数。
- 注意专业组模式下应优先展示组内代表专业或当前专业的历史数据口径。

验收：

- 方案区和候选区历史分数口径一致。
- 缺失年份显示“暂无”，不展示误导性 0 或 -1。

#### 6.2.3 支持指定目标位置移动

问题：

- 当前方案只能一位一位上移/下移。
- 方案数量较多时调整效率很低。

处理建议：

- 增加“移动到第 N 位”能力。
- 支持输入目标位置，也可提供常用动作：移到顶部、移到底部、移到本层开头/末尾。
- 后端移动接口应支持一次性目标位置变更，避免前端循环调用单步移动。

验收：

- 移动后 position 连续。
- 固定/锁定项规则仍生效，不能越过不可移动边界。

#### 6.2.4 专业组以组为单位删除和移动

问题：

- 专业组模式下，用户心智更接近“学校专业组”单位。
- 当前如果只能按专业条目操作，会降低效率，也容易破坏组内结构。

处理建议：

- `majorGroup` 模式下提供组级删除、组级移动、组级固定。
- 前端明确区分组操作和组内专业操作。
- 后端需要保证组内专业随组移动，组内顺序不被意外打散。

验收：

- 专业组移动后组内专业完整保留。
- 删除专业组不会残留孤立专业项。

#### 6.2.5 方案状态和审查入口

问题：

- 方案状态管理有点混乱，当前能看到“区间顺序合理”“待调整”等状态，但用户难以理解这些状态代表什么。
- 审查结果数据已经留在面板里，但没有直接触发审查的入口。
- 草稿作为单独概念立不住，用户侧应直接理解为“方案”；候选下面的篮子也应直接作为方案入口。
- 新版本没有提交状态，历史版本兼容的已提交方案只展示为历史只读提示。

处理建议：

- 明确状态分层：候选生成状态、方案状态、审查状态、导出状态。
- 前端展示组合状态，例如“方案已生成，待审查”“方案有调整，待更新”“审查发现风险，需要查看”。
- “区间顺序合理”这类技术判断应归入审查详情，不作为唯一总状态。
- 在方案面板增加“执行审查/重新审查”入口，触发现有审查接口并刷新结果。
- 前端不再展示“草稿”“排序区”“提交”等系统概念；内部 draft 数据结构只作为实现细节。

验收：

- 用户能判断当前是否已有方案、是否有方案调整、是否完成审查、是否存在风险。
- 用户可以在方案面板直接触发审查。
- 审查成功、失败、进行中的状态都有明确反馈。

#### 6.2.6 方案篮子与候选视觉区分

问题：

- 候选 tab 里的方案篮子和候选志愿条目混在一起，当前同样偏红，用户不容易区分。

处理建议：

- 候选 tab 内篮子直接命名为“方案”或“当前方案”，不再展示“草稿”。
- 方案篮子使用独立色系，建议使用蓝色或中性色，并保留明确文字标识。
- 不只靠颜色区分，避免和冲稳保、风险标签混淆。

验收：

- 用户能区分候选志愿、已加入方案、当前方案的不同状态。
- 方案篮子不会和候选条目的红色标签混在一起。

#### 6.2.7 顶部数字概览可折叠或隐藏

问题：

- 顶部统计数字占用可操作空间。
- 用户调整方案时更需要看到列表内容。

处理建议：

- PC/Web 增加折叠顶部概览能力，默认是否展开由产品确认。
- 移动端此前已隐藏顶部统计概览，若 PC 同步调整需要单独验证布局。

验收：

- 折叠状态下方案和候选可视空间明显增加。
- 关键总量和风险状态仍能通过简洁入口查看。

#### 6.2.8 方案和候选增加回到顶端

问题：

- 方案和候选列表较长，滚动后回到顶部成本高。
- 列表较长时还需要更明显的滑杆或快速定位能力，方便用户快速移动到目标区域。

处理建议：

- 方案列表和候选列表各自增加“回到顶端”按钮。
- 若列表是虚拟滚动，需要调用对应滚动容器而不是页面窗口。
- 增强列表滚动条可见性，或增加快速定位控件。
- 首版至少支持回到顶部、到底部；如成本可控，支持输入序号定位。

验收：

- 用户滚动较深后可以一键回到当前列表顶部。
- 用户能通过滑杆或快速定位减少长列表滚动成本。

#### 6.2.9 冲稳保色块按高途志愿网站统一

问题：

- 当前冲稳保色彩分层与用户已有高途志愿网站认知不完全一致。

处理建议：

- 统一为：冲=红，稳=橙，保=绿。
- 同步检查标签、色块、图例、筛选项和导出样式。

验收：

- Web 页面内冲稳保颜色一致。
- 不影响无障碍可读性，颜色外仍保留文字。

#### 6.2.10 候选筛选标签优化

问题：

- 候选筛选区当前默认展开的城市名太长，占用空间多。
- 城市标签数量较多时，用户难以快速定位目标城市，也会挤压候选列表主体内容。

处理建议：

- 城市类筛选标签默认只展示有限数量，超出部分进入“更多”。
- 增加关键词搜索，支持按城市名快速过滤。
- 如数据具备层级，优先按省份或区域分组展示城市。
- 已选城市标签需要前置或固定展示，避免折叠后用户不知道当前筛选条件。
- 筛选区默认高度可控，展开后不应遮挡候选列表主要操作。

验收：

- 城市标签默认展开不会占满候选筛选区。
- 用户能通过搜索、更多或分组快速找到目标城市。
- 已选标签清晰可见，折叠和搜索不会丢失筛选状态。

#### 6.2.11 方案调整和导出行为反馈闭环

问题：

- 当前系统缺少用户对方案调整过程的结构化记录，难以判断系统推荐哪些被保留、哪些被移动、哪些被删除。
- 后续如果要优化方案构建策略、排序策略和 Agent 规划能力，需要真实用户操作作为反馈数据。
- 导出通常表示用户对当前方案有较强认可，可以先作为正反馈事件，但不能直接等同于真实填报结果。

处理建议：

- 记录关键方案操作事件：添加候选到方案、删除志愿、移动志愿、移动到目标位置、专业组组级移动/删除、应用排序结果、导出方案。
- 事件需要包含可用于后续分析的上下文：会话 ID、操作类型、操作前后位置、志愿或专业组标识、冲稳保、录取率、专业/专业组模式、方案来源、时间戳。
- 导出时关联当时的方案快照或方案版本，便于后续分析“被导出的最终方案”。
- 行为记录应以服务端操作成功为准，记录失败不能阻断用户主流程。
- 本期先形成数据闭环，后续再基于行为数据做策略评估、算法调参和 Agent 规划能力优化。

验收：

- 完成添加、删除、移动、排序应用、导出后，可以查询到对应行为事件。
- 导出事件能关联导出时的方案内容或版本。
- 行为记录不影响方案操作成功率。

#### 6.2.12 Agent 侧方案编辑和规划链路回归

问题：

- 新版前端正在弱化“草稿”作为用户可见概念，候选下方篮子也逐步收口为“方案 / 当前方案”。
- Agent 侧此前可能仍通过草稿、排序区、review 等内部概念组织方案编辑和规划动作。
- 后续从对话触发方案调整、补位、排序、删除、重排时，需要确认与新版前端用户语言和状态流转一致。

处理建议：

- 回归 agent 工具调用链路：生成方案、查看方案、加入/移除候选、移动志愿、排序/重排、审查、导出前解释。
- 检查 agent 输出文案是否还暴露“草稿”“排序区”等系统概念。
- 检查前端卡片联动是否仍能定位到方案或候选，不再出现没有工作区入口的卡片。
- 检查从对话触发的方案调整是否会正确刷新 workspace state、审查状态和导出状态。

验收：

- 用户从对话触发方案编辑后，前端方案区状态和列表顺序正确。
- Agent 文案与前端用户侧概念一致。
- 不因为隐藏草稿入口而破坏既有 planning 工具调用能力。

### 6.3 P2：观测、成本和后续体验

#### 6.3.1 模型算力计费监控和优化

问题：

- 当前已有多模型效果和性能 benchmark，但还缺少线上持续计费监控和成本优化闭环。

处理建议：

- Agent 记录每次模型调用的 provider、model、场景、输入/输出 token、耗时、状态、错误类型。
- 按场景区分：普通问答、方案解读、意向识别、planning 工具调用、快捷回复润色。
- 增加成本报表：日级调用量、token 用量、超时率、失败率、平均耗时、P95/P99。
- 优先优化高频低价值调用：缓存、减少无效润色、压缩上下文、把可规则化回复从 LLM 中剥离。

验收：

- 能回答“哪个场景、哪个模型最贵/最慢/失败最多”。
- 能按会话追踪一次用户操作触发了几次模型调用。

#### 6.3.2 移动端是否同步适配

问题：

- 本节反馈默认面向 Web。
- 移动端若同步适配，需要单独验证空间、触控、列表性能和旧版移动入口一致性。

处理建议：

- 先完成 Web 版方案。
- 移动端单独形成适配清单，重点验证：返回会话列表、方案排序、目标位置移动、组级操作、回到顶端、顶部概览隐藏。

验收：

- 移动端不因 PC 功能增加出现标题错位、按钮挤压、横向滚动失控。

## 7. Release 3.0.0 最小收口清单

创建 `v3.0.0` tag 前，建议至少完成 P0 项；P1/P2 项已确认不阻塞本期发布：

1. `develop` 包含所有生产热修、文档和 changelog。
2. 本地工作区无待提交的 release 相关改动。
3. 后端单测和关键 planning 回归通过。
4. 前端生产包确认 `basePath=/assistant-pc`，且不包含 `ws://localhost:8000`。
5. Agent 健康接口和兼容 WebSocket 验证通过。
6. 新建会话 `major / majorGroup` 两种模式验证通过。
7. 老会话懒迁移样本验证通过，至少覆盖 `_final / _temp / original` 文件选择。
8. 生产回滚命令已验证或至少 dry-run 确认路径存在。
9. 生产部署记录更新最终 commit、产物 tag、sha256 和回滚点。
10. tag 创建后，所有模块产物使用同一个 release 标识。
