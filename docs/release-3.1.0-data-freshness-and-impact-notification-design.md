# Release 3.1.0 Data Freshness And Impact Notification Design

本文记录 3.1.0 阶段对“高途招生计划数据持续变化”的设计方案。目标是在不改变当前一次性拉取、落盘、按会话生成工作区的总体机制下，让系统具备数据刷新感知、变化影响分析和分层通知能力。

## 1. 背景

当前创建会话时会一次性拉取高途全量志愿数据，清洗后写入会话快照文件，并以该快照生成候选池、方案和工作区状态。此模式的优点是稳定、可追溯，但缺点是：

- 高途招生计划、录取率、位次等数据后续可能继续更新。
- 当前系统无法主动感知“原始快照是否过期”。
- 已生成的候选池和方案不会主动提示用户数据变化。

3.1.0 需要补齐的是“变化感知”和“变化通知”，而不是把整个链路改成实时查询。

## 2. 目标

- 保持现有创建会话主流程不变。
- 为每个会话建立可比较的数据快照元信息。
- 在数据变化时生成影响分析结果。
- 在对话层和工作区层分别给出明确提示。
- 仅对受影响条目做标记或建议，不自动覆盖用户已确认的方案。

## 3. 非目标

- 不把高途数据改成实时查询模式。
- 不自动重排或覆盖用户方案。
- 不自动删除已存在方案条目。
- 不改变当前候选池/方案生成的主体算法。

## 4. 数据快照模型

每次创建会话或刷新时，落一份快照元信息：

- `chatSessionId`
- `source`：gaotu
- `fetchTime`
- `examYear`
- `prepareType`
- `province`
- `batch`
- `subjectType`
- `score`
- `requestHash`
- `dataHash`
- `dataVersion`

其中：

- `requestHash` 用于标识“请求参数是否相同”。
- `dataHash` 用于标识“清洗后的志愿数据是否变化”。
- `dataVersion` 用于保留历史版本。

如果上游没有版本号，就以 `dataHash` 作为变化判断主依据。

## 5. 刷新触发

建议支持三种触发方式：

1. 打开会话详情或工作区时触发异步检查。
2. 用户手动点击“刷新招生计划”。
3. 定时任务仅刷新活跃会话。

刷新原则：

- 只刷新 `GOING`、近期开启或正在编辑的会话。
- 对同一 `chatSessionId` 做互斥锁，避免重复刷新。
- 新数据只更新快照，不直接覆盖方案结果。

## 6. 变化影响分析

变化类型分四级：

### 6.1 无变化

- `dataHash` 相同。
- 不通知用户。
- 只更新检查时间。

### 6.2 轻微变化

典型变化：

- 招生计划说明调整。
- 计划数细微变化。
- 历年分数补充更新。

业务动作：

- 更新候选池明细。
- 标记快照已刷新。
- 不影响当前方案结构。

通知建议：

- 对话层：`招生计划数据已更新，当前方案未受明显影响。`
- 工作区层：展示更新时间和变更数量。

### 6.3 中等变化

典型变化：

- 录取率变化。
- 位次区间变化。
- 计划数变化影响冲稳保判断。

业务动作：

- 候选池重新计算。
- 方案审查状态标记为 stale。
- 排序建议标记为 stale。

通知建议：

- 对话层：`部分院校/专业组数据已更新，建议重新审查当前方案。`
- 工作区层：列出受影响学校/专业组和变化摘要。

### 6.4 重大变化

典型变化：

- 当前方案条目下线。
- 招生计划为 0。
- 选科、体检、批次归属等约束变化。

业务动作：

- 当前方案条目标记异常或失效。
- 不自动删除。
- 生成风险提醒和待处理项。

通知建议：

- 对话层：`当前方案中有志愿已受招生计划变化影响，请尽快处理。`
- 工作区层：高亮受影响条目并提供调整入口。

## 7. 通知分层

### 7.1 对话层

对话层只输出摘要，负责回答：

- 有没有变化。
- 变化严不严重。
- 是否建议重新审查。

### 7.2 工作区层

工作区新增“通知区/变化区”，负责展示：

- 数据更新时间。
- 受影响范围。
- 变化条数。
- 变化明细。
- 操作按钮。

建议按钮：

- `查看变化详情`
- `重新审查`
- `刷新候选池`
- `稍后处理`

## 8. 差异匹配规则

建议以稳定 key 做 diff：

- `province + batch + schoolCode + majorGroupCode + majorCode`

匹配后的处理：

- 条目存在且字段变化：更新展示字段。
- 条目存在但计划为 0：标记失效。
- 条目不存在：标记下线。
- 条目新增：标记新增。

## 9. 后端落点

建议增加以下能力：

- `VolunteerDataSnapshot`
- `refreshVolunteerData(chatSessionId)`
- `detectVolunteerDataDiff(oldSnapshot, newSnapshot)`
- `buildChangeSummary(diff)`
- `markWorkspaceStale(chatSessionId)`

## 10. 前端落点

建议前端至少增加：

- 会话详情顶部提示条。
- 工作区通知区。
- 变化明细弹层或抽屉。
- 重新审查按钮。

## 11. 3.1.0 推荐实施顺序

1. 先落快照元信息和 hash。
2. 再实现刷新检查。
3. 再实现差异分析。
4. 再补对话层摘要通知。
5. 最后补工作区变化区和操作入口。

## 12. 风险与约束

- 不能自动重写用户确认过的方案。
- 刷新必须可追溯，可回看历史版本。
- 变化通知必须分层，避免打扰主对话。
- 刷新频率要限流，避免放大高途接口压力。

## 13. 结论

3.1.0 适合把“高途招生计划持续变化”做成数据快照与影响分析能力，而不是改成实时查询。这样可以在保持当前架构稳定的前提下，让系统感知变化、精准通知用户，并把风险控制在候选池和方案审查层面。
