# 对话执行引擎生产网关与 Codex 回合闭环设计

**日期：** 2026 年 9 月 8 日  
**状态：** 已实现第一阶段，待 Shadow/Readonly 灰度验收  
**适用范围：** `zhiyuan-agent` 对话执行引擎第一阶段竖切片

## 1. 背景与目标

当前项目同时存在旧版 `ChatService`/`BaseAgent` 链路和新的 Codex App Server Gateway 链路。新的 Gateway 已经具备快照、状态补丁、结构化输出、Evidence 引用和 Shadow 测试，但生产启动过程没有真正构造 `GatewayService`，因此线上 WebSocket 仍然主要走旧链路。

本设计不试图一次性重写约 8,900 行的 `service.py`，而是先建立一个可以真实运行、可验证、可回退的生产网关闭环：

```text
WebSocket
  -> GatewayService
      -> 身份与线程绑定
      -> 权威会话快照
      -> Codex App Server 回合
      -> MCP/领域工具
      -> 结构化输出与 Evidence 校验
      -> 用户回复或 Proposal/Pending
      -> 历史与事件持久化
```

第一阶段的目标是：

1. `GATEWAY_MODE=codex_shadow` 和 `GATEWAY_MODE=codex_readonly` 不再只是配置占位，而是能由生产组合根真实装配。
2. Codex 回合必须等待真实终态，并正确收集结构化输出、工具事件和终态错误。
3. 租户、会话、用户、线程、招生类型、状态版本和能力边界在整条链路中保持一致。
4. 未经 Evidence 和版本校验的事实、Artifact、Proposal 不得进入用户回复或持久化。
5. Codex 故障时不执行写操作；Shadow 模式仍以旧链路回复，Readonly 模式返回明确的可恢复错误。

## 2. 非目标

本阶段不包含：

- 一次性删除旧版 `ChatService`、`BaseAgent` 或 `service.py`。
- 开放 Codex 的方案写入、Shell、任意代码执行能力。
- 重写招生录取率、冲稳保、专业组等领域算法。
- 将 SKILL.md 或 Superpowers 作为事实来源或业务规则执行器。
- 重新设计前端卡片视觉样式。
- 引入新的持久化数据库表，除非现有接口无法支持线程绑定和幂等要求。

## 3. 设计原则

### 3.1 Codex 负责推理，不负责事实

Codex 负责理解用户意图、决定下一步读取哪些信息、组织回复和提出结构化 Proposal。招生数据、录取率、专业组事实和方案状态必须来自受治理的领域工具或后端快照。

### 3.2 技能是流程指导，不是权限

Codex skills 可以提供 profile discovery、evidence analysis、candidate recommendation、plan construction 等流程指导，但技能不能绕过 Gateway 的能力白名单、MCP 工具授权、Evidence 校验或 Proposal 编译器。

### 3.3 默认拒绝

以下情况必须拒绝输出或拒绝执行，而不是猜测、降级或使用旧缓存冒充当前结果：

- Evidence 不存在、跨租户、跨会话或跨线程。
- Evidence 的招生类型、状态版本或数据版本不匹配。
- Artifact 不属于当前快照。
- Proposal 没有经过确定性编译。
- Codex 输出缺少必需结构化字段。
- 当前能力集合不允许该操作。

### 3.4 旧链路只能作为 Shadow 基线

Shadow 模式中旧链路负责向用户返回兼容答案，Codex 结果用于评估和记录；旧链路不得读取或写入 Codex 的线程状态，Codex 也不得借 Shadow 路径执行副作用。

## 4. 目标组件与职责

### 4.1 `GatewayComposition`

新增生产组合组件，负责在 FastAPI lifespan 中装配依赖：

- `ChatService` 作为 legacy fallback。
- `CodexAppServerHarness` 及其生命周期。
- 只读领域 MCP server 或等价工具连接。
- Thread binding 注册/解析客户端。
- Snapshot loader。
- `GatewayService`。

组合组件必须提供异步关闭方法，确保应用退出时关闭 Codex 子进程、读取任务和 MCP 连接。

### 4.2 `AppServerClient`

负责 JSON-RPC 传输层：

- 启动和关闭 Codex App Server 子进程。
- 关联请求响应。
- 接收并缓存通知。
- 处理协议错误、进程退出和请求超时。

传输层不解释业务事件，也不拼装最终回复。

### 4.3 `CodexAppServerHarness`

负责 Codex 协议语义：

- 创建或恢复线程。
- 注入快照或状态补丁。
- 启动回合。
- 按 `threadId`、`turnId` 收集回合通知。
- 等待 `turn/completed`、`turn/failed`、`turn/interrupted` 等终态。
- 提取结构化输出、Evidence ledger、Artifact 和可观测事件。
- 超时时主动中断回合。

Harness 返回稳定的内部 `CodexTurnResult`，不把 App Server 原始协议泄漏给 Gateway。

### 4.4 `GatewayService`

负责单轮业务编排：

1. 校验并记录幂等的 `turnId`。
2. 解析可信 ThreadBinding。
3. 加载当前权威 Snapshot。
4. 计算相邻版本的 StatePatch；不相邻时发送完整 Snapshot。
5. 调用 Codex Harness。
6. 注入 binding scope 到输出校验。
7. 校验 TurnOutput 的 Schema、Evidence、Artifact、Proposal 和版本。
8. 根据模式决定回复、Shadow 记录或可恢复错误。
9. 只持久化已经通过校验的用户可见输出。

Gateway 不从自然语言中反向创建 Proposal、Pending 或写操作。

### 4.5 `ReadonlyDomainTools`

只提供：

- 实体解析。
- 学校/专业目录查询。
- 当前方案读取。
- 历史录取事实查询。
- 资格检查。

工具必须从可信 binding 获得租户、会话、用户、招生类型和能力集合。模型提交的身份字段只能被视为不可信输入，不能覆盖 binding。

## 5. 数据流与契约

### 5.1 回合输入

Gateway 接受：

```json
{
  "tenantId": "tenant-1",
  "sessionId": "session-1",
  "userId": "user-1",
  "turnId": "client-generated-id",
  "content": "用户原始消息"
}
```

`turnId` 必须由客户端或上游请求层稳定生成。同一 `sessionId + turnId` 重试时返回第一次已完成结果，不得重复调用模型、重复保存消息或重复执行动作。

### 5.2 Codex 回合上下文

注入 Codex 的上下文包括：

- 完整 Snapshot，或相邻版本的 StatePatch。
- 当前招生类型。
- 当前缺失事实。
- 允许的只读能力集合。
- 结构化输出 Schema。

Binding 的秘密句柄不能注入模型上下文。模型不能自行提供 `tenantId`、`sessionId`、`userId`、`threadId` 来改变工具作用域。

### 5.3 结构化输出

TurnOutput 至少包含：

```json
{
  "responseType": "text|fact|clarification|proposal",
  "message": "用户可见中文回复",
  "artifactRefs": [],
  "evidenceRefs": [],
  "uncertainties": [],
  "clarification": null,
  "proposalRef": null,
  "admissionFacts": []
}
```

其中：

- `fact` 必须引用当前回合已经签发的 Evidence。
- `admissionFacts` 必须与当前 Snapshot 的招生类型一致，并且每条事实都有匹配的 EvidenceRef。
- `artifactRefs` 必须指向当前状态版本的 Artifact。
- 只读模式禁止执行 Proposal 写入，但允许 Codex 输出经过契约校验的 Proposal 草案/引用和 `conversationAction`；确认、取消等动作必须携带 Proposal 引用和版本信息，最终执行仍由 Java Pending/CAS 重新读取并校验。
- `uncertainties` 用于明确数据不足或解释限制，不得用模糊措辞掩盖缺失证据。

## 6. 回合终态与错误处理

### 6.1 正常终态

Harness 只有在收到明确终态后才返回成功：

- `turn/completed`：返回结构化结果。
- `turn/failed`：返回稳定错误码和已收集事件。
- `turn/interrupted`：返回中断状态，不视为成功。

仅收到 JSON-RPC `turn/start` 的响应不能视为回合完成。

### 6.2 超时

回合超过配置超时时：

1. 调用 `turn/interrupt`。
2. 等待短暂终态窗口。
3. 关闭或重建异常线程，避免下一轮复用未知状态。
4. 返回 `recoverable_error`。

不使用半截模型文本作为最终答案，不写入 Proposal 或 Artifact。

### 6.3 Codex 模式行为

- `legacy`：保持当前旧链路行为。
- `codex_shadow`：Codex 与 legacy 并行；legacy 回复用户，Codex 结果只进入 Shadow 评估记录。
- `codex_readonly`：Codex 通过校验后回复用户；Codex 失败时返回结构化可恢复错误，不自动执行旧链路写逻辑。

### 6.4 绑定失败

绑定不存在、过期、撤销、能力不足或 scope 不一致时：

- 不调用领域工具。
- 不调用 Codex 回合，或立即中止当前回合。
- 不持久化模型输出。
- 返回稳定错误码，用户看到不泄露内部信息的中文提示。

## 7. 并发、持久化与幂等

第一阶段先保证单进程正确性，同时把接口设计成可替换为持久化实现：

- 使用按会话分片的锁，不使用覆盖所有会话的全局长事务锁。
- `_threads`、`_snapshots` 和 `_turn_cache` 仅作为短期缓存，不作为唯一事实来源。
- 线程绑定和 Proposal 的权威状态来自后端服务。
- 幂等记录至少包含 `tenantId`、`sessionId`、`turnId`、输入摘要、结果状态和结果载荷。
- 同一 `turnId` 但输入内容不同必须返回冲突错误，不得覆盖第一次请求。

## 8. 可观测性

每个回合记录：

- `tenantId`、`sessionId`、`turnId`、`threadId`。
- Snapshot 版本、StatePatch 是否使用。
- Codex 回合状态、耗时、工具名和错误码。
- 输出校验结果。
- Evidence ID、Artifact ID、Proposal ID 及其版本信息。
- Shadow 与 legacy 的路由结果和差异摘要。

日志不得记录用户完整隐私原文、binding 秘密句柄或未经脱敏的模型上下文。

## 9. 测试与验收门禁

### 9.1 Harness

- JSON-RPC 响应与通知可以并发到达且正确关联。
- 未收到终态时不会提前成功返回。
- `turn/completed` 能返回最终结构化输出。
- `turn/failed`、进程退出和超时均返回稳定错误。
- 超时会发出中断请求。
- 线程恢复失败不会复用未知线程状态。

### 9.2 Gateway

- 生产组合能根据配置创建 Gateway。
- Shadow 模式仍只持久化 legacy 回复。
- Readonly 模式只持久化已通过校验的 Codex 回复。
- tenant/session/thread/admissionMode/stateVersion/dataVersion 任一不匹配都会拒绝。
- 同一回合重试不重复调用或持久化。
- 同一回合 ID 的不同内容被拒绝。
- 会话之间不会因为全局锁互相阻塞。

### 9.3 领域 MCP

- 工具列表仍只有八个只读工具。
- 工具不能从模型参数覆盖可信身份。
- 无能力授权时拒绝调用。
- 未知招生单元、缺 Evidence、错误风险层级和过期版本全部拒绝。

### 9.4 回归门禁

先运行新增的 Harness/Gateway 单元与集成测试，再运行现有 `tests/` 全量测试。任何 legacy 回归失败、Evidence 校验失败或 Codex 进程资源泄漏都阻止进入下一阶段。

## 10. 发布与回退

发布顺序：

1. Fake App Server 与离线 fixture。
2. 生产组合的启动自检，但保持 `GATEWAY_MODE=legacy`。
3. `codex_shadow`，只记录评估，不改变用户回复。
4. `codex_readonly` 小流量启用。
5. 通过连续 Shadow 与 Readonly 门禁后，再单独设计写操作 Canary。

任何以下事件都触发回退：

- Codex App Server 无法启动。
- MCP 工具元数据与白名单不一致。
- binding 无法可信解析。
- Evidence 校验失败率异常升高。
- 回合终态收集不完整。
- 线程状态或幂等记录丢失。

回退只切换到 `legacy`，不删除后端已保存的 Shadow 观测数据。

## 11. 后续拆分

本规格完成后，后续工作分为独立规格：

1. Plan Review Policy 与确定性 Solver。
2. Proposal/CAS 写入、确认和 postcondition。
3. `service.py` 按状态机拆分为路由、Evidence、Proposal、Pending、History 五个边界。
4. 前端 Evidence 抽屉、错误状态和招生类型切换清理。

## 12. 当前实现与部署门禁

截至 2026 年 9 月 8 日，第一阶段已落地以下闭环：

- 生产 lifespan 按 `GATEWAY_MODE` 装配 Gateway；`legacy` 保持旧链路，`codex_shadow` 与 `codex_readonly` 启动 Codex Harness。
- Harness 等待 `turn/completed`、`turn/failed` 或 `turn/interrupted`，超时会发送中断请求；不同回合的通知按 predicate 路由，不再被全局回合锁串行化。
- 每个 Codex thread 注册短期 opaque handle；后端只保存哈希，同一租户、会话、用户可在到期前后轮换 handle，不同身份不能覆盖已有 thread binding。
- `codex_readonly` 会加载 `zhiyuan_domain` MCP。App Server 注入的 `_meta.threadId` 是 MCP 的唯一 thread 索引；模型传入的身份字段不会参与 binding 解析。
- MCP 通过受限本机 registry 取得 opaque handle，并在**每次工具调用**向后端解析所需 capability。binding 不存在、过期、撤销或无能力时不调用领域后端。

Readonly 启用前必须满足：

```bash
GATEWAY_MODE=codex_readonly
CODEX_APP_SERVER_BINDING_REGISTRY_PATH=/受限目录/zhiyuan-codex-bindings.sqlite3
CODEX_HOME=/可写目录
```

registry 文件必须只对运行 Agent 与其 MCP 子进程的服务账号可读写；不得使用共享临时目录或跨实例共享文件。多实例部署、跨进程恢复和 registry 轮换仍是下一阶段工作，当前仅允许单 Agent 实例灰度。
