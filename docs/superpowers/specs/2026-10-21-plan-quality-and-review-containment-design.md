# 方案质量修复与旧审查隔离设计

状态：**待用户确认；仅完成设计、自审与反例审查，未实施、未切换运行配置。**

审查性质：本轮为同一执行者的代码核对、自审及契约/反例审查，**非独立第三方审查**。
逐项记录见 `../reviews/2026-10-21-plan-quality-and-review-containment-design-review.md`。

日期：2026-10-21。基线：`8fefcd7` 加工作区现有成绩修复，运行样本为会话 `10042000`。
证据见 `../reviews/2026-10-21-session-10042000-plan-quality-review.md`。
本设计局部补充 J5.3/J5.5，不重做 solver、不撤销冻结确认链，不修改生产默认配置。

## 1. 目标、非目标与备选方案

### 1.1 本轮要解决什么

1. 暂停不可信的旧质量结论与其修复建议，但保留真实约束、命令完整性和事务后置校验。
2. 让用户明确否认的专项资格真正进入预览、确认、存储、候选过滤与最终方案验证。
3. 修正新方案“稳 → 保 → 冲”的错误排序，统一解读与工作台的异常判断。
4. 区分用户已确认偏好、系统推荐和默认打分；无明确专业意向时不报告“偏离用户意向”。
5. 把方案质量与执行成功分开表达，解决“已生成”等于“可报/合适/审查通过”的误读。

非目标：本轮不调整效用权重、不新增优化目标或整套事实平台、不替用户设电气硬约束、
不静默修复历史方案、不全面重建各省报考规则、不把历史数据当作 2027 年确定事实。

### 1.2 三种路径

| 路径 | 好处 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 只隐藏审查按钮 | 快 | 对话、旧卡、直接接口仍可触发；旧结果仍可能显示通过 | 不采用 |
| 关闭整个 review/执行验证 | 彻底没有旧提示 | 破坏 rerunReview 契约、冻结后置、失败审计和部分用户动作 | 不采用 |
| 服务端独立隔离旧审查 + 保留命令/资格验证 | 可回退且不把暂停说成通过 | 需覆盖后端、Agent、Web；分批验收 | **推荐** |

## 2. 先纠正问题归因

- 新 solver 已参加 `10042000` 的 prepare；排序错误不等于 solver 未部署。
- `reviewState` 有 findings，不代表已经完全摆脱旧规则：当前评价仍混用旧 checks
  映射与 context 推导。前端读 checks、部分汇总读 findings，来源仍未统一。
- Java 已有 `CreateSessionReq.specialPlan` 与 `VolunteerFilterChain` 的明确否认过滤。
  实际成绩没有该字段；Python `ScoreUpdateRequest` 也不允许传入该字段，验证为
  `extra_forbidden`。此外，Java 的空成绩更新判定未包含专项字段，卡片摘要也未展示它。
  因此不是简单“后端完全没资格字段”，也不能只给 Python 增加一个属性就声称修复闭环。
- 对“没有专项”的断言，应与“我不知道是否有资格”区分。现有策略允许未知继续探索，
  但未知不等于资格通过，更不能因为未知就替用户确认可报。
- 方案排序器按候选分数产生的 stable order 首次档位顺序建桶；stable order 是候选选择
  的确定性基线，不应兼任新方案的跨档位志愿顺序。
- 电气方向由助手建议，用户没有明确选定。宽专业方案不一定违规，但不能包装成已针对
  用户主线优化的方案，也不能后来把助手建议归因为用户硬要求。

## 3. 设计不变量

1. 暂停、未验证、信息不足均不映射为 passed、低风险或“可放心填报”。
2. 业务变更仍走 preview → pending → claim → frozen apply → postcondition → receipt。
3. 既有 `rerunReview=true` 请求与 digest 保留；暂停不得由网关篡改已冻结载荷来实现。
4. `review_check` 被暂停不等于 `user_goal` 停止；按服务端冻结来源识别，不能信任请求改名。
5. 已成功命令仍允许按 operationId 重放回执，不因当前暂停策略变成“未生效”。
6. 资格事实不等于专业偏好；资格 unknown 不默认补 false，明确 false 不被序列化丢失。
7. 同一候选身份、同一资格事实，过滤、求解、直接加入与最终校验使用同一归一规则。
8. 新方案默认顺序与存量保序是不同动作语义；修初始排序不得全局打乱用户手动顺序。
9. 默认匹配分仅可作为探索方案的排序启发，不能充当“用户喜欢”的证据。
10. `10042000` 只作只读复现样本；修复上线后也不自动重写其成绩、资格或方案。

## 4. 旧审查隔离：边界与协议

### 4.1 一个独立的服务端策略

新增 `planning.review.mode = active | paused`，环境变量为 `PLANNING_REVIEW_MODE`。
默认 `active`，仅本地受影响环境经确认后持久配置为 `paused`；非法配置启动失败，
不能悄悄回到 active。与现有 `review.fix.command/search.enabled` 正交：
**paused 优先禁止 review 来源的新动作，原开关值保留，便于审计和后续恢复。**

第一版采用启动时配置，不实现热开关。下文的“切换期间”指滚动/重启前后仍存活的请求、
旧 pending 和命令回执，不能假设所有旧事项随进程消失。
同一目标环境的所有写入实例必须采用一致策略；先排空/停止旧 active 写入实例，再开放
paused 实例的写流量。只切部分实例不构成暂停完成，不把启动配置描述为在线原子切换。

### 4.2 四层职责，不复用旧 hardFeasible 作全局背书

| 层 | paused 时 | 权威与边界 |
| --- | --- | --- |
| 身份、CAS、claim、幂等、冻结重放 | 保留 | 执行协议；失败回滚，禁止跳过 |
| 用户已确认硬要求、计数上限、资格冲突 | 保留并补齐 | 可执行约束；不是旧经验审查分数 |
| 旧经验评价及其修复建议 | 对外停用 | 内部诊断也不得泄漏成 passed 或可确认卡 |
| 方案结构解释 | 保留 | 解释实际顺序/覆盖/未知，不承诺录取 |

本省保底数量、固定学费阈值、概率差 8 等现有策略，即使旧 registry 标为 hard，
本轮也不借暂停把它们升级为所有用户动作的事务门槛。已有 solver/补入限制先保留，
不趁机放宽；其是否合理属于下一轮质量目标设计。用户明确的学费上限仍是硬要求。

### 4.3 paused 的对外投影

统一返回 `reviewState.status=paused`、`evaluationStatus=unavailable`，并新增紧凑
`availability={mode: paused, reasonCode: review_paused, policyVersion: review-containment-v1}`。
`checks/findings/proposals` 为空、`summary=null`、`hardFeasible=null`、`probesRun=0`；
不能用 0 条风险、0 条阻断冒充已审查。历史结果留在存储供审计，paused 读投影不改历史行。

不把 paused 视为 fresh/completed；`workflowStatus`、journey、快照、工具、确认续接和
工作台都必须优先读 availability。不得继续注入旧 `reviewSummary/reviewHardFeasible`，
也不得自动引导“重新审查”形成循环。计划仍可查看、解释和预览修改，但标“待核验”。

**仅后端新增字段不能先单独上线**：当前旧前端可能按 summary 缺省值当通过。后端/Agent/Web
消费者完成后一起部署、再启用 paused；Web 显示暂停说明，不显示绿色通过或旧风险总数。

所有通常读取 review 的规划状态/工作台/summary/turn-snapshot/只读工具/解释/导出投影
均走同一服务端 policy adapter。解释保留可验证的结构异常，不携带被暂停的经验 findings。
计划状态不再因为旧 review 未跑而永久卡在 pending_review；显示“方案已生成，待核验”。

投影必须是响应副本，不得原地清空存储实体或执行器随后使用的 domain state。
`PlanningWorkflowStatusBuilder` 等消费者先处理 availability，再判断 stale/summary；
不能让 null summary 落入当前“风险数为 0 → passed”的默认分支。

### 4.4 入口与存量卡矩阵

| 请求/状态 | paused 时行为 |
| --- | --- |
| review/run、review-workflow/run | 返回显式 paused，按原接口形状无变更返回；不增加计划版本 |
| review preview、旧 fix-proposals/generate | paused + 空建议，不回退旧 checks 路径 |
| review prepare、旧直接 apply、首次 review 命令执行 | 明确拒绝 `review_paused`，不修改方案 |
| user_goal、成绩、偏好、add/remove/move | 正常确认执行，保留相应硬后置，回执单列“审查暂停” |
| active 的旧 review 卡 | 禁用确认、允许取消；强行提交仍由后端拒绝，不改写卡片 digest |
| 已 claim、尚未提交的 review 操作 | 按正常失败审计终结；内部 expired + fail 可兼容，展示非超时 |
| 已成功的 operationId 重放 | 先完整鉴权与内容绑定、再按台账回执；不得被暂停误报失败 |
| 旧命令已提交但 pending applying | reconcile 读台账恢复 applied；不撤销成功、不再执行一次 |
| user_goal 已成功回执含旧 review | 保留历史执行成功；当前 review availability 覆盖展示，旧风险仅审计 |

首次执行的暂停检查放在“成功/失败台账重放分支之后、任何新方案写之前”。确认内容仍与
服务端 pending 的来源和摘要绑定。缺来源/来源冲突不得默认为 user_goal。
所有 direct/facade/inner 旧 apply 入口也必须检查，不能留绕路。

暂停拒绝的失败台账与 pending 终态不依赖旧 `ReviewFixCommandFlags`。按已绑定的 pending
来源分类，保留事务回滚后的独立失败审计，写入原因 `review_paused`；不能在方案回滚时
把失败记录也回滚掉，或让已 claim 卡一直停留 applying。无命令台账的 applying 卡走既有
claim/reconcile 规则，只终结状态、不补执行。不得新增与现有台账竞争的第二份幂等真相。

### 4.5 与强制 rerunReview 的兼容

保留请求 `rerunReview=true` 与冻结内容。统一的 review execution adapter 在 paused
时返回**未执行质量评价**的 paused 结果，不再运行旧规则或增加审查版本；命令计数、
选中集合/顺序、固定项、目标与资格后置独立执行，任何真实不满足仍回滚。

`completedSteps` 不再虚报 `review_rerun`，而是记录 `review_skipped_paused`；
Agent 明确“变更已生效，质量审查暂停”，不能因为缺 review summary 误判命令失败。
旧用户目标预览若强依赖经验 probe，本轮必须逐分支迁移：要么仅去掉该经验依赖并保留
命令硬后置，要么返回明确 blocked，禁止无条件 succeeded 占位。

正式质量声明与导出区分：允许查看或下载标注“未完成核验”的草案；明确资格冲突必须阻止
正式提交/标记可报，导出草案必须显示冲突与数据年份，不得原封不动输出“审查通过”。

## 5. 专项事实：复用现有存储，但不伪造资格

### 5.1 第一批的最小承诺

复用 `userScoreDetail.specialPlan`，Python `ScoreUpdateRequest` 增加可选
`specialPlan: bool | null`，必须是严格布尔；未带/null 表示本轮未更新，不能把 false
过滤掉。Java 的唯一存储来源不变，profile/snapshot 中是它的只读投影，不再创建第二份
可独立修改的资格真相。

| 表达/存储 | 本轮语义 |
| --- | --- |
| 明确“没有任何专项资格” → false | 排除已归一识别的国家/地方/高校专项 |
| 未回答、跳过、不知道、字段缺失 → null/缺失 | 不默认否认；相关候选标资格待核验 |
| 历史 true / 泛称“有专项” | 只表示某种资格自述，**不能推出所有专项均符合** |
| 只否认“地方专项”，未否认其他类型 | 第一批不得降级成全局 false；明确说明分类型持久更新尚不支持 |
| 用户要求把已有 false 改为“不知道” | 第一批无清空协议，不能说已清除；需明确澄清/拒绝该更新 |

第一批优先修复本会话的“明确无专项却丢失”场景；分类型资格与清空的可确认协议是独立
后续切片。在支持之前，这些情况必须显式标未支持/待核验，不能声称已处理。不能用 null
同时表示“不改”和“清空”，也不从 `physicalConstraints.specialLimits` 反推三态。

### 5.2 对话与确认

专项否认与成绩同轮时可放同一确认预览；单独修改资格也复用当前成绩更新链，**不要求用户
重输已有总分和各科**。Java 预览必须列出“专项资格：无；将排除相关专项”，文本与卡片
来自同一 summary。用户确认后才落库，卡片/文字共用 operationId/claim/幂等链。

用户在信息未齐时已说过“没有专项”，下一次预览需引用原始用户消息事实，不得因后来
只谈分数就丢失。预览审计记录来源 turn/message ID；无来源不擅自补否认。模型仅提出
草稿，确认是最终授权；没有成功回执前不得说“以后已经过滤”。

资格单独更新必须进入 Java 的有效字段判定：`specialPlan=false` 不是空请求，不要求同轮
重复提供总分/各科。已有完整成绩可直接合并预览；原成绩尚不完整仍需按既有必填规则补齐，
不能宣称资格已单独落库。summary 同时列出旧值、新值与影响；确认文本和卡片共用它。

额外风险：`CreateSessionReq.filterType` 默认 `2`，新建资格增量对象经过当前 merge 会把
既有 `filterType=3` 变成 `2`，已离线复现。实现需对 score-update 使用**入口传入字段集合**
进行补丁合并；服务端默认值不能伪装成用户输入。现有全量表单创建默认值不改。
该契约同时防止资格更新重置模式、成绩、总分、位次、专业筛选或志愿数量。

具体边界如下，不接受模型自行声明 `providedFields`：

- 仅在 score-update 的 preview/prepare HTTP 边界，从原始 JSON 的白名单字段导出实际
  非空补丁字段集，再构造内部 typed patch；不能先绑定带默认值的 `CreateSessionReq`
  再反推字段是否出现。缺失/null 不更新，各科空数组不表示清空。
- `sourceVersionGuard` 与来源证据属于上下文，不参与成绩 deep merge。request digest
  绑定规范化补丁及版本/来源；prepare 冻结合并后的完整值与补丁语义版本，执行不再从
  模型草稿或新的 DTO 默认值推导用户输入。
- 当前网关的 `userOriginalText` 不能充当已验证证据：Java 成绩 DTO 没有此字段。增加
  prepare 元数据载体，由网关基于已持久化用户消息注入来源 ID，服务端核对会话、归属和
  用户角色；ID/文本不落进成绩真相。引用跨轮旧消息同样核对，不信模型伪造的来源 ID。
- 源消息仅授权形成待确认预览，不等于更新已确认。找不到可核对的旧消息时请用户重述，
  不自动填 false；字段/证据冲突时不写库。原始对话不复制进全局日志或公开 fixture。

### 5.3 从候选到后置的同源规则

引入一处纯归一器，输出 `programRequirements`（国家/地方/高校专项等）及
`source/evidence`。优先正式代码/标签，名称中的“地方专项/国家专项/高校专项”只补
“该计划要求资格”的识别，**不能证明用户有资格**。名称含糊记 unknown，不能靠
“定向/公费/楚怡工匠”等泛词直接等价为三类专项资格。组级要求向组内专业继承，专业项
独有要求也必须核对，不能只扫校名或第一个专业。

正式字段与明确专项名称矛盾时单列 `requirement_evidence_conflict`，保留原始证据。
已有专项要求证据且用户明确全否的条目不得以“降级为 unknown”重新放入可选集合；需先
澄清候选证据，不能借 unknown 的探索放行规则绕过否认。真正缺证据的 unknown 与此区分。

该归一结果供 `VolunteerFilterChain`、候选快照/资格、solver、点名直接加入、legacy
导入验证、review facts 和最终方案后置共用；candidate-source/资格版本进入快照与
冻结事实摘要。`specialPlan=false` 且要求属于三类专项 → conflict；无资格事实 → unknown；
false 不是用户不喜欢专项，而是不能报考相关计划。

- conflict 不得进入新生成/新加入方案；现有冲突项不能被“current 豁免”绕过资格门。
- unknown 在探索候选中保留并醒目标注，不获得“资格已通过”；草案可展示，正式核验不足。
- 资格更新确认后，分数本身未变则不重查/清空位次；候选、方案、审查依赖置 stale，
  下一次方案修改需重建预览，旧 pending 版本守门继续生效。
- 资格事实落库与候选过滤失败保持当前事务原子性；不能过滤失败却回复资格已经生效。
- 存量方案仅标冲突/待核验，不自动删除；用户确认的移除冲突项动作可作为收敛修复，
  不得要求先无条件保留满容量，否则会阻断清除不合资格条目。
- 后置比较 frozen 与当前事实；选中身份缺失或资格要求发生变化 → 新预览，不重规划替换。

资格守门按动作分层，避免“当前有冲突 → 连承认事实/删除错误项都不能执行”：

| 动作 | 资格后置 |
| --- | --- |
| 确认更新资格事实 | 原子更新事实并标记存量冲突/stale，不以旧方案已含冲突为由拒绝真实事实 |
| 首版生成、加入、补齐、替换 | 最终选中项不得含已知资格冲突；存量 conflict 不能以 current/pinned 豁免 |
| 纯移除 | 允许分次减少冲突；不得新增项或新冲突，不强制维持满容量；仍守锁定与冻结身份 |
| 移动/排序 | 不解决资格冲突；有已知冲突时先要求清理，不通过换序伪装成可报 |
| 草案查看/解释/导出 | 如实展示冲突，不能标正式可报；不偷偷改选中集合 |

纯移除只依赖冻结身份与原方案归属；候选已被资格过滤掉时，不能因候选不在新池中就无法
删除原选中项。上文“身份缺失需新预览”针对会影响选入资格或身份真实性的变更，不要求
被删除项继续具有可选资格。数据库写入/状态失效需事务一致；外部候选/OSS 失败不得报告
成功，也不能声称远端副作用可由数据库事务回滚，按现有失败补偿边界验收。

## 6. 生成、排序与解释

### 6.1 明确方案定位，不把填满容量当作质量目标

| 情况 | 默认流程 |
| --- | --- |
| 无专业/城市偏好，用户说先出一版 | 标明不限专业“探索草案”，默认数量单独解释并确认 |
| 助手刚推荐多个方向，用户只说“可以” | 不自行选一个方向；可做探索草案或只问一次主线选择 |
| 用户明确接受“电气为主” | 先生成可见的偏好/覆盖预览；不能偷偷等价为“只要电气”硬筛 |
| 用户明确说“只要电气” | 走硬范围预览，确认后以其约束生成；不足则明确不足 |
| 未给新目标只要求改序/删项目 | 保留既有目标，不借动作补写专业偏好 |

不新增顶层“旅程第二状态机”。探索/方向已确认等定位从现有 confirmed objectives/
明确偏好投影；持久化的本次生成元数据记录 `purpose`、输入目标摘要与来源，供回执复核。
缺必要资格证据、数据年份不匹配或尚无正式校验时，即使方向已确认也仍是待核验草案。

当前内部 `intentScore`、preferred 没有确认来源时继续只作探索启发；不出“适合你”的
断言、不产生“非意向”审查、不偷偷加多样性约束或调权。改进效用主线需另做候选对照实验，
不能把“更少医学”当成未经确认的通用正确答案。

### 6.2 排序策略必须冻结为动作语义

在 `MutationPolicy` / solver request 增加显式排序策略，随 inputDigest、冻结结果和
回放校验保存；不以 `generationMode=legacy_import` 或条目数推测真实动作。

| 策略 | 使用范围 | 规则 |
| --- | --- | --- |
| `initial_tier_order_v1` | 首版生成，包括“空正式方案 → fill_to_count”的真实首版链 | 明确 sprint → stable → protect；同档保留既有偏好/utility 的确定性顺序 |
| `preserve_current_v1` | 普通 fill/add/replace/约束重算 | 固定 current 相对顺序；新增位置按原动作规则；不借此整版重排 |
| `explicit_move_v1` | 已支持的单项 `move_units` | 预览冻结移动项、锚点与准确新顺序，受锁定/pinned 与目标位置守门 |

首版上下文以请求意图与源版本中是否已有正式 ordered 方案共同判定，由服务端决定并冻结；
空草案/缺失 metadata 不足以证明首版。用户手排、pinned 或明确非标准顺序存在时，
不偷偷应用首版默认顺序；冲突则要求单独确认，禁止悄悄挪动 fixed 项。

默认排序只改跨档位顺序，不额外承诺同档 admissionRatio 单调，也不等价于强制“概率排序”。
单项移动与普通补齐须有独立测试，防止补齐一下全表洗牌。

当前 Agent 没有整版按档位重排的 goal；`OrderedPlanSortReq.sortField` 的 facade 直写
不等于对话已具备冻结确认能力。**第一批不新增整版重排对话动作，也不拿该直写接口绕过
确认链。** 存量可用已支持的单项 move 分次调整；整版重排需另确认 goal/schema、冻结
完整顺序、锁定冲突与幂等后置，不能先对用户承诺“一句话重排/重新生成”。

新旧 solver/ordering policy 版本必须可区分；更换排序规则后，旧未执行冻结提案不能按
新算法重算。若旧策略未声明、存在资格遗漏或版本不兼容，明确拒绝并要求新预览；
已成功命令保留幂等回执。新元数据记录实际 staged selection、frozen apply 与顺序策略，
不能把继承的 `legacy_import` 当作本次生成器名称。

至少将 `solverVersion`、`orderingPolicyVersion`、`eligibilityPolicyVersion` 和候选要求
来源版本纳入 prepare 的 inputDigest/冻结载荷，并由 apply 校验支持集。缺失或不兼容版本
必须新预览，不能只改实现方法而沿用 `ojalgo-48.4.2-j53-staged` 的旧语义。

### 6.3 单一结构诊断，而不是多个“异常”真相

新增纯结构诊断输入为实际 ordered items/units 与已声明的顺序策略：

- 档位按 sprint=0、stable=1、protect=2 检查实际逆序，未知档位输出 unknown，不能当正常。
- 单列 `tierSequence`（默认结构）、`userOrderRespected`（是否按用户授权）、
  `ratioSequence`（有数据时的经验现象），不把它们互相替代。
- 明确用户顺序允许偏离默认档位次序，但解释应说“按你的顺序，存在结构上的跨档位排列”，
  不错误报告成系统失误，也不自动修正。
- summary、解读、工作台和 Agent 取同一诊断；“有保底档位”只说明覆盖，不承诺录取安全。
- `10042000` 的“稳→保→冲”须识别为默认档位逆序；即使 review paused 也仍可提示。

### 6.4 对话完整链路

沿用现有 journey/pending/command，不新增并行状态机：

| 用户阶段 | 系统行为 | 不允许的捷径 |
| --- | --- | --- |
| 提供成绩与“没有专项” | 两类事实都进入可见摘要；信息未齐时保留可核对消息来源 | 只记分数、丢失资格，或未确认就写资格 |
| 没明确专业但要求先出方案 | 解释探索定位、数量和资格未知，形成生成预览 | 助手替用户确定电气主线，或把满容量说成最优 |
| 确认生成/修改预览 | 文本与卡片定位同一 active pending，冻结选中集合与顺序 | 用“继续”同时授权未展示的资格/方向/顺序变更 |
| 执行成功 | 回执分别说明实际变更、仍未解决的资格/结构问题和审查暂停 | 把命令 succeeded 翻译成质量审查通过 |
| 用户追问是否合理 | 展示同源结构诊断与已知资格事实，说明经验评价暂停 | 读取旧 findings 背书，或反复要求先跑暂停的审查 |
| 用户要求优化 | 清除已知不合资格项优先，方向选择由用户决定，再按现有动作预览 | 静默整版重排、重新生成，或用优化名义重置硬约束 |

有多个待确认对象或用户答复有歧义时要求明确目标，不能猜测确认范围。下一步建议只引用
当前已实现且可预览的动作；paused 是评价可用性，不是要求用户完成的新任务。

## 7. 本会话如何恢复

`10042000` 不自动改状态，不直接执行“按电气重新排”。用户后续看到：

1. 现有 45 组是不限专业探索草案，旧质量审查已暂停，不是已核验可填报方案。
2. 单独说明地方专项与“无专项”冲突，以及当前跨档位顺序问题。
3. 资格信息需重新生成可见确认预览并获得确认；旧消息可作来源，不自动迁移为已确认。
4. 用户可先明确方向，也可继续不限专业探索；修改按独立预览确认，不能以“继续”概括授权
   未展示的资格/专业/排序三种变更。
5. 资格生效后，支持先预览移除不合资格项，再按已确认目标补齐；重排需显示顺序变化。
   三者可以按已有动作分次进行；整版重排不在第一批承诺内，不新增无能力支撑的一键
   回滚/重做入口。第 1 项“已暂停”仅在 A 实际启用后使用，此前只能说建议暂停。

本会话回归以脱敏合成 fixture 固定事实，不把原始对话、凭据或大候选池拷进版本库。

## 8. 落地批次与验收

### A：审查隔离和消费者防误读

范围：ReviewPolicy / service 入口与投影、旧卡执行守门、snapshot/journey/工具、Web。
保留现有 solver/原子动作/后置；不改业务数据。A 验收通过后才允许本地 paused 配置。
交付实现自审与审查证据后，由用户确认是否定向部署；本轮设计反例审查不代替后续代码
和跨端集成审查，也不冒称已完成独立第三方审查。

### B：资格闭环、排序与解释修复

范围：ScoreUpdateRequest/严格布尔和补丁字段集、Java 预览/来源、既有过滤器与共用归一、
各写入口按动作划分的资格后置、明确排序 policy、结构诊断与新鲜度、无意向误报。
不得仅更改排序器方法而漏掉 user_goal fill 首版；不得仅改 review 标签而漏掉直接 add。
若资格补全后的 fullCount/fill 依赖旧固定补入策略导致不足，应如实 blocked，不临时放宽。

### C：质量评价与建议恢复（单独方案，不默认随 B 打开）

按“资格可行性 / 已确认偏好适配 / 结构建议 / 证据未知”统一输出，再评估是否恢复旧 probe。
恢复 active 需新规则/模型版本与新评价，不复用 paused 前缓存或旧 pending；原始旧回执仍可查。

### 验收矩阵

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| A1 | paused 下读 state/workspace/summary/snapshot/tools/解释/导出 | 无旧 passed/hardFeasible/风险总数背书；明确 paused；只读不写版本 |
| A2 | review/run、workflow、preview、generate | 形状稳定；无旧建议，不跑旧规则、不写计划 |
| A3 | active 旧 review 卡、直调 apply、伪装 user_goal | 不执行；绑定原 pending 来源；明确暂停而非超时 |
| A4 | applying 旧卡成功/失败/无台账，旧 fix flags 开/关 | reconcile 与真实结果一致，不重复执行；暂停拒绝审计不依赖旧灰度位 |
| A5 | pause 后重放先前成功 operationId | 鉴权/摘要不放松；仍 applied/replayed，无二次写 |

| A8 | 配置非法、无新前端、恢复 active | 非法拒绝；未齐套不启 paused；恢复要求新评价，不静默信任旧结论 |
| B1 | 无专项同轮成绩、跨轮保留、单独更新、false 序列化 | 可见预览、来源可追；确认前不落库；两确认入口只生效一次 |
| B2 | 既有 filterType=3/成绩/位次/模式，只更新专项 false | 其他事实保持；默认字段不参与增量覆盖；旧 pending stale |
| B3 | 缺失/null/true/仅否认地方/要求清空 false | 不推断全否或全有；未支持更新明确提示；unknown 不是 pass |
| B4 | 名称专项无标签、只有专业名专项、编码/名称冲突 | 同源归一；filter/solver/direct add/legacy/最终验证一致 |
| B5 | 无专项的 current/pinned 项含多个专项 | 可确认真实资格，能按锁定规则分次移除；候选已过滤仍可删除；不豁免新选入/正式声明 |
| B6 | prepare 后资格事实/候选变化 | 旧冻结输入拒绝，新预览；无实时重规划偷换内容 |
| B7 | 首版从 initial 与空 ordered fill 两入口 | 默认冲→稳→保；确定性；policy 与实际结果冻结一致 |
| B8 | 非标准 stable order、缺档、同分、纯 unknown | 不靠输入先后决定跨档顺序；unknown 明示，不能 silent passed |
| B9 | 存量手排/pinned/用户非标准顺序/只补数量/点名移动 | 原意图保留；无隐式整版重排，冲突明确 blocked |
| B10 | 稳→保→冲、冲→保→稳、用户授权非标准次序 | summary/解读/Agent 同一诊断；用户偏离与系统异常区分 |
| B11 | 正向意向为空而 preferred/intentscore 有分、明确意向后 | 前者不报“非意向”；后者只按已确认来源判适配 |
| B12 | 助手推荐电气后用户泛称继续、2027 用历史数据 | 不擅自写电气硬筛；探索定位、数据适用性与缺失明确 |
| B13 | 模型伪造 providedFields/来源、Java DTO 默认值、重放相同 requestId | 字段集由边界推导；证据核对；规范 digest 绑定，不接受新内容复用旧预览 |
| B14 | 升级前未执行提案、升级前已成功 operationId | 前者校验 policy/version 要求新预览；后者原回执重放，不套新 solver 二次执行 |
| B15 | 对话要求整版重排但只有 sortField facade | 明确未支持，不绕过确认直写，也不把单项移动冒充整版能力 |
| B16 | 专项正式字段与名称矛盾、组级/专业级资格不同 | 标出证据冲突并继承有效要求；明确无专项时不以 unknown 降级绕过排除 |

复用现有 Java solver/snapshot/filter/interpretation/command 回归与 Agent contract、journey、
confirmation 回归，补 Web paused/unknown/旧卡状态测试。先红后绿；只在私有 fixture 环境
做写链 E2E。原样本只读复验，不替用户确认真实成绩或方案。

## 9. 需要用户确认的产品边界

1. 同意“旧经验审查暂停，执行/资格硬校验保留”，不撤掉整个确认与执行框架。
2. 专项第一批只完整支持“明确无任何专项”；部分类型资格和清空暂不假装支持，另切片。
3. 无明确主线可先做不限专业探索草案，不擅自选择电气，不把容量填满当成质量通过。
4. 首版默认冲→稳→保，存量用户顺序不自动改；第一批只复用单项 move，整版对话重排另确认。
5. A/B 分批实现和验收，C 的新评价设计另确认；当前本地模式切换与部署也需单独授权。
