## 已确认的现状

### 1. 空候选上下文与提示存在矛盾

位置：`zhiyuan-agent/app/engine/working_set.py:165`。

没有候选时，工作集文本显示“当前没有已确认候选”，但仍无条件要求“不要说看不到候选”。临时探针通过真实 Gateway 回合，确认同一份模型输入里同时出现这两条内容，结构化候选为空、来源轮次为 null。

这会给恢复缺口下的模型相互冲突的指令；本轮只证明输入矛盾，没有调用真实模型，也没有证明某条线上回答因此产生了幻觉。空应用工作集同样不能证明原 native thread 的历史里完全没有候选。

### 2. 当前候选是滚动记忆，不是严格的“上一批”

位置：`zhiyuan-agent/app/engine/working_set.py:33`、`zhiyuan-agent/app/engine/working_set.py:114`。

候选按 entityId 合并去重，保留最近最多 24 个对象；遇到非空新实体时只更新一个 `candidateSourceTurnId`。探针先让两轮工具 payload 分别含 A/B、C，再查看第三轮真实模型输入：候选为 A/B/C，来源轮次为第二轮。

因此，单个 sourceTurnId 不能证明列表里的全部对象都来自该轮，更不能证明它们就是最后一次展示给用户的那一批。探针 payload 是假工具结果，不能把它宣称为真实 UI 展示或真实模型复述实验。

空工具结果不会清掉这份滚动记忆，来源轮次也保持旧值。探针确认了该行为，但本轮不把它直接判为缺陷：需要先区分“本次查询结果为空”与“忘掉历史可指代对象”，不能在恢复修复中顺手把两者混为一谈。

### 3. 后端有业务候选池，不等于有上一批展示记录

- Java `CandidatePoolStateDTO` 含 items 和池的来源信息，并非后端完全没有候选数据。
- `PlanningStateService.java:444` 构造 workspace 候选池时，保留池元信息，并按草案/排序方案的引用收集候选明细；这不是最近一次候选工具结果的完整快照。
- `ConversationSnapshotService.java:118` 只把池摘要放到 `preferences.candidateSummary`；Python `ConversationTurnSnapshot` 没有候选批次明细或展示轮次字段。
- `CandidateViewStateDTO.java:9` 有过滤和排序参数，没有最后展示批次、页码及其来源轮次的完整记录。
- 探针给 Gateway 输入池明细及候选摘要，确认它们不会自动恢复为工作集候选。摘要计数不能用来编造候选身份，草案/排序方案引用也不能冒充“上一批”。

### 4. 重查不是原样恢复，查询入口也有副作用差异

- `CandidatePreviewService.java:80` 使用只读状态载入，并调用推荐流水线重新构造候选；这是当前条件下的新查询，不是读取先前已展示的结果。
- Python `tools_readonly.py:1693` 保留页码、profile/data 版本和样例边界。只拿一页候选不能声称恢复了全量或上一批的相同集合。
- `PlanningStateService.java:2067` 的 candidate-pool/query 可触发 overlay 刷新；`PlanningStateService.java:9364` 存在持久化路径，不能未经确认拿它充当纯读恢复接口。
- 以当前 Java 实现为准：overlay 正常 CAS 分支保留最新版本，不能沿用 Python 旧注释断言“每次查询必然自增规划版本”。这里确认的是可能写入，不是每次调用必写或必然加版本。

## 方案取舍

### A. 先明确缺失时的降级，不增加存储（推荐下一小批）

这是对现有上下文渲染的有界修正，不改工作集字段或候选保留策略：

1. 有候选时继续优先使用已有身份和可核验来源解析指代，不让模型忽视已经拿到的对象。
2. 候选为空时，不再无条件禁止说明缺失；明确“本工作集没有候选”不等于“历史从未展示候选”。先结合当前 thread 中可用的明确对象及其来源解析，不能仅因工作集为空就强制用户重复提供信息，也不能用模糊 assistant 文本编造 ID。
3. 仅在用户当前问题确实依赖这些对象且仍无法可靠定位时，走现有只读重查或针对缺失条件澄清；重查结果必须明确是当前条件下的新结果，不能冒称原来的同一批。
4. 不在启动/重连时自动调用业务候选查询，不新增关键词意图分类器，不修改工具准入、写入确认或证据规则。

优势是改动小、无存储迁移、不增加恢复期写副作用。代价是只提供诚实且可解释的降级，不承诺原样找回上一批，也不让自动回收具备上线条件。

### B. 增加可恢复的候选批次投影

若产品要求重启/跨 worker 后仍能精确指代上一批，需要先定义独立于滚动实体记忆的批次契约：归属、工具来源、查询与数据/业务版本、批次身份、工具结果轮次、实际展示锚点、有效期，以及并发/重放时哪一代结果可覆盖。

落点还需要在业务侧持久来源与独立恢复投影之间选型，并评审旧数据迁移、跨 worker 可见性、容量和失效。仅把当前字典序列化到本机文件，或复用工件摘要台账/UI 事件缓存，不能自动满足这些要求。

本轮不选择存储方案，不设计或实现新表/新接口。B 是新的架构任务，不能混入前一批小修或先行启用清理。

### 不采用的捷径

不把完整候选池、当前查询第一页、方案中的候选引用或滚动 24 个实体直接标记为“原来的上一批”；不从摘要反解原文，不将模型对历史的猜测提升为工具授权或当前录取事实。
