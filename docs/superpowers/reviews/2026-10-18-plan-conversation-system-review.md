## 1. 评审范围与结论

本次不是继续补某个工具，而是重新审查：用户在多轮对话中如何表达要求，系统如何把要求变成可验证的方案变化，以及分析、优化、调整、确认和复查如何保持同一语义。

评审快照：

- 代码基线：`616464c`，分支 `wip/2026-09-28-p2-write-loop-green`；包含工作区已有、尚未提交的 add_units EXPAND 等改动，不将这些改动归为本次产出。
- 主设计：`docs/superpowers/specs/2026-10-18-journey-control-and-admission-interpretation-design.md`，**评审时 v5；现已 v6**（评审时 SHA-256 前缀 `c20a51b47749`）。
- 权威表：`docs/superpowers/specs/2026-10-18-plan-semantic-authority-map.md`，**评审时快照；现已随 v6 更新**（评审时 SHA-256 前缀 `36b23dcecddf`）。
- 实施计划：`docs/superpowers/plans/2026-10-18-journey-control-and-admission-interpretation.md`，**评审时 v5；现已 v6**（评审时文件修改时间 09:47:28）。
- 之前 v1–v4 的评审仅作历史背景；已经在 v5/v6 修正的问题不重复判为当前缺陷。

**结论：现有确认执行底座值得保留，但 v5 尚不能作为完整方案处理逻辑直接执行。建议先统一语义和关键对话验收，再分批接入现有代码。**

主要问题不是缺少 JourneyContext 或解读卡，而是以下边界还没有统一：

1. 一轮一个写入口，被扩大成一次只能处理一个原子意图，导致同时提出的硬要求被延后甚至遗失。
2. 约束的真实持久化、卡面承诺和“应用后是否重排”仍不一致。
3. 确认、纠正和新增条件同时出现时，缺少安全的组合语义。
4. 档位和顺序的结构性描述，被升级成“较可能录取”“滑档风险低”。
5. 审查、优化、后置校验虽然在收敛，但规则分类、目标排序和输入版本仍存在冲突。

本次只进行静态文档与源码核对，并新增本评审草案；不修改业务代码，不运行模型/数据库/端到端回归，不重启服务，不提交或部署。源码现状不等于 3201 或线上部署状态。

## 2. 应保留的设计与已有实现

- 模型负责理解和解释，Java 负责实体解析、编译、校验和执行；只读 MCP 不开放直接业务写入。
- 方案变更经过预览和确认；结果以真实执行回执为准，而不是以助手说“已完成”为准。
- 保留现有 pending revision、claim、版本守卫、operationId、事务和重放机制，不重造确认引擎。
- 区分 `planningStage`、派生旅程位置、能力授权和 pending 状态，不把四者合成一个状态机。
- 当前只有一个业务状态计数器；增加输入指纹，不另造一个未经迁移的“方案内容版本计数器”。
- 明确 unit/volunteer、校级/专业级信号、实际数量/目标数量/候选需求的区别。
- 不伪造 computed 证据，不新增重复的 `system.action` 事件，不提前删除旧 DTO/持久化字段。
- 保留 v5 的渐进迁移原则：J2 读现有 checks，评价模型经过完整 probe 清单和 golden 对照后再替换。

源码核对补充：

- `PendingPlanningCommandBizService.java:79` 已有事务、版本检查和幂等台账；`:366` 的当前 EXPAND 分支读取 frozen targets，并检查目标进入方案、没有隐式移除原条目等后置条件。不能再按旧实现断言“加入必然丢条目”。
- `PendingConfirmationBizService.java:81` 已校验 revision/CAS；`:98` 已定义 active/applying/applied 等转换。不是从零设计确认机制。
- `zhiyuan-agent/app/gateway/service.py:1906` 已有操作后的助手续接，包含一次性台账、会话锁和用户水位保护。需要补的是任务语义恢复，不是声称当前完全没有续接或并发保护。
- `zhiyuan-server/src/main/resources/db/migration/V7__add_pending_confirmation.sql:17` 对 tenant/session 有唯一约束。因此不能仅因查询没有排序，就认定会随机取到多条历史 pending。

## 3. 当前仍需修订的问题

下列优先级表示设计和后续实现的处理顺序；其中尚未落地的组件问题是**设计风险，不是已发生的生产事故**。

### F01 · P1：复合意图被拆散，执行顺序可能违背原始要求

证据：主设计 `:599` 的示例，把“加六条、太远不要、学费三万内、稳妥一点”拆开，先执行加入，其他要求留到下一轮；`:610` 只通过正文承诺后续处理。

当前 `zhiyuan-agent/app/gateway/contracts.py:383` 确实禁止 add_units 混用 scope/requirements 等字段。这是现有动作能力边界，**不能靠模型把字段硬塞进去解决**；但也不能据此丢掉用户同一句话的约束。

影响：先加的六条可能包含超预算或被排除的地区；用户说“继续”时，系统也没有结构化依据判断应继续哪项要求。还需明确“学费三万内”约束的是新增六条，还是整个方案，不能自行选择作用对象。

修订建议：

- **一轮最多一个待确认的业务变更集，不等于只能理解一个意图。**
- 一次完整解析所有要求，记录对象、硬软强度、数量、作用范围、有效期和未解决项。
- 同时表达、作用于本次操作的硬要求，必须进入本次操作的前置校验；不支持就阻断或明确协商分步，不能先执行一个可能违反它们的子动作。
- 若“太远”未定义，先解决这一关键歧义；若指定六条与明确预算冲突，说明冲突并让用户选择，不静默舍弃目标或放宽预算。
- 当前契约尚不支持安全的复合变更时，先确认并应用必要前置约束，再预览后续加入；每一步均向用户说明覆盖范围和剩余事项。
- 需要继续承诺的任务，用有界、可恢复的任务记录承载，不只靠正文或模型上下文记忆。

### F02 · P1：约束有效期和应用行为，与当前实现不一致

证据：主设计 `:607`、权威表 `:91` 要求 J4a 前 scope/学费都标“仅本次”；主设计 `:1383`、`:1393` 又要求应用约束后不重排，另给重排入口。

但当前源码存在明确的长期写入及重建行为：

- `PendingPlanningCommandBizService.java:176` 在约束命令内更新约束或学费，随后生成、补足并再次生成有序方案。
- `PlanningStateService.java:1426` 保存约束状态；`:1075` 还会持久化复合 requirements、priorityRules 和档位目标。
- `ProjectedHardRequirementSupport.java:66` 将要求合入持久化 hardConstraints。
- `ChatSessionBizService.java:216` 将学费区间写入会话成绩详情；`PlanningStateService.java:9585` 的候选过滤会读取这个区间。

因此不能把现状概括为“scope 都没持久化、只是本次有效”。缺少的是**统一且可兑现的生命周期协议**，并非完全没有持久化。

修订建议：

- 先按执行路径建立行为真值表：写到哪里、影响哪些读/生成路径、是否重排、何时失效。
- 卡面立即按真实行为说明，不能等 J4a 才修正误导性文案。
- 目标态区分 `本次调整` 和 `本会话后续规划`；未确认草稿不能成为后续有效约束。
- 不重复存储学费真值。保留或迁移现有 owner，其他对象引用其规范化投影；同一事务维护失效标记。
- 区分“只保存规划口径”和“保存口径并调整方案”；只有完整预览了后者的变化，才能在一次确认内一起执行。
- `persistTargetCount` 不是通用有效期字段，不能拿来模拟所有意图生命周期。

### F03 · P1：确认与纠正的优先级不安全，存在相互矛盾的确认规则

证据：主设计 `:484` 将“确认/取消”置于其他意图之上，纠正排在后面；`:615` 写“用户没反对即确认”，与 `:344`、`:351` 的明确确认规则冲突。

“确认，但不要加 A”“可以，预算改成两万”“不是替换，是加入”都不是对原提案的无条件确认。另一个具体偏差是 `:343` 提示 applying 时“请稍候或取消”，但 `PendingConfirmationBizService.java:110` 只允许取消 active，并不允许取消 applying。

修订建议：

1. 先识别否定、纠正和新增条件；若改变原预览内容，原卡不能直接执行，转重新预览。
2. 只在对象唯一、内容未改变、存在有效待确认提案时，将明确肯定识别为确认；沉默、未反对、“继续看看”不能作为确认。
3. 复用 pendingId/revision、frozen command 和 operationId；补齐整笔变更内容的绑定，不只绑定动作名称。
4. 取消仅适用于尚未执行的提案；执行中取消、事务回滚、执行后撤销是不同能力，未实现的不能展示为可用。
5. 不把上述逻辑变成新的关键词路由器；模型理解组合语义，协议层阻止相互冲突的动作组合。

这是文档和对话验收缺口，不据此断言当前 Java claim/CAS 已失效。

### F04 · P1：档位结构被包装成录取可能性和滑档风险

证据：主设计 `:1035` 取第一条稳/保作为 base，`:1044` 将其标成“较可能”；`:1050` 仅凭保档数量和 ratio 是否缺失，将“两条以上保且 ratio 已知”判为滑档风险低。`:969` 仍称基准路径“最常见”。

这套规则可以描述档位覆盖，不能仅因真值表自洽，就证明具有录取风险或落点预测效力。缺数据是认知不确定，不等于已证明风险高；反过来，数据齐全也不等于风险低。校级档位还不能独自证明组内专业或调剂结果。

顺序问题同样需要区分：在前序未满足的假设下讨论某条目，与断言该条目是“最有希望的录取落点”不是同一结论。当前 major/major_group 是条目粒度，不是完整的省份/年份/批次投档政策模型；`:1011` 的统一免责声明不能代替适用性判断。

修订建议：

- MVP 改为**方案结构与条件情景解读**：首个稳/保位置、保档覆盖、顺序异常、数据缺口，以及“假如前序均未满足”的条件场景。
- 删除或停用未经验证的 `likelihood_band` 和整体 `slip_risk=低/中/高`；结构警告可以保留，但字段和文案均不能冒充结果预测。
- 明确区分“数据不足”“结构覆盖不足”“资格校验失败”，不能合成一个风险标签。
- 不默认把每次方案问答都引向预测落点；回答用户所问，必要时提供结构说明。
- 真正的录取风险产品另立切片，先定义政策适用范围、结果标签、历史验证和校准标准，再决定能承诺什么，不能以补几句 caveat 代替验证。

这里的判断来自规则的输入和输出不匹配；本评审没有验证实际录取效果，也不提供录取概率结论。

### F05 · P1：统一评价的规则分类仍存在冲突，预算硬约束可能被降级

v5 已补齐 14 个旧 check 的目标映射，不能再沿用旧评审说“只列七个”。但主设计 `:896` 规定 soft 只能是 notice/info，`:917`、`:919`、`:921`、`:923` 又允许 soft/action；`:913` 要保留“缺省份仍 passed=true/warn”，与该节未知硬校验和 passed=true 的约束不一致。

还有语义问题：学费低一点是软偏好，学费不得超过三万是硬约束，不能因为都来自 high_tuition check 就固定归为 soft。政策更新、调剂告知也不是可由优化器“优化消失”的偏好目标。`safety_guard` 的安全底线在目标层级与 probe 表中还需明确到底属于哪种强度。

修订建议：

- 分类依据是规则性质和用户确认的强度，不是旧 check 名称或旧 category。
- 分开保存 `结果状态(pass/fail/unknown/not_applicable)`、`规则强度`、`展示严重度`、`是否有可用修复动作`，避免让一个 severity 字段承担四个职责。
- 预算上限、资格、政策数量上限等进入硬校验；档位分布、覆盖目标是否硬性，由明确协议决定。
- 安全启发式、专业偏好和政策告知分开；不将所有 warning 自动编译成新约束，也不让“修复”暗中改变用户目标。
- 为每种模式/动作列出必需 probe 集；仅“本次跑过的 hard 全通过”不足以证明必需校验没有漏跑。
- 旧语义兼容通过映射和 golden 差异报告处理，不能同时要求保留旧行为又强行通过不相容的新 schema。

### F06 · P2：最小变更与软效用的排序冲突，“一个求解器所有动作”范围过大

证据：主设计 `:646` 是结构→变更成本→软效用，`:659` 是结构→软效用→变更成本，`:698` 又强调 adjust 最小变更。按不同顺序实施，“预算调整”可能只替换两条，也可能重做大半个方案。

同时，精确移动一个条目、锁定一个条目、零删除 EXPAND，不需要与重新生成整表一样进行全局搜索。共用一个求解器不能自动保证语义统一，反而可能放大动作影响范围。

修订建议：统一**输入、目标解释、校验、预览、执行与回执**，允许使用不同的动作规划器。精确编辑走确定性逻辑，选集/补足/重优化才使用搜索。

- 先保证资格、已确认硬约束、锁定和动作允许的变更边界。
- 再满足本次明确任务目标；软优化须定义可解释的改善目标，不能以“最小变更”为由永远返回不变。
- 调整默认最小必要变更；首建和“重新做一版”允许不同变更预算。
- 非本次目标相关的效用提升不能无限压过变更成本；目标排序、容差和 tie-break 在预览时冻结。
- 不同 profile 的取舍要体现在回执中，不能只藏在 solver 权重里。

### F07 · P1：计划中的进程缓存键缺少用户会话作用域

证据：主设计 `:1231` 为进程内候选 join 索引规定的键只有 planVersion、candidateSourceVersion、dataVersion、objectiveModelVersion。不同会话完全可以拥有相同的局部版本号。

如果按该描述直接实现全局 LRU，可能复用其他会话的个性化候选索引；这既影响结果正确性，也有跨会话数据混用风险。**目前是在设计中发现，不能表述为已经证实的线上泄露。**

修订建议：个性化缓存以受信 tenant/session 和候选输入指纹隔离；索引包含适用的模式/overlay 依赖；结果缓存另包含方案、目标和规范化反事实参数。容量按字节和条目数双重限制。只有明确设计成公共、不可变数据缓存的对象，才可另行共享。

### F08 · P2：版本开始统一，但缺少“本次计算究竟用了什么”的完整凭据

证据：主设计 `:935` 的 evaluationVersion 包含 evaluatedStateVersion 和内容摘要，这是进步；但还需规定摘要来自计算时输入，而不是读取时的新状态。源码 `PlanningStateService.java:2871` 记录审查前的版本，`:2905` 再增加状态版本，证实“当前 stateVersion”不能直接等同评价输入版本。

修订建议：

- 为每次评价、预览和解读绑定不可变输入清单：方案摘要、有效目标摘要、画像/政策依赖、候选来源及 overlay、数据快照、相关算法版本。
- 评价输入清单必须和结果一起生成并保存；不能把旧 findings 与当前摘要重新拼出一个“新版本”。
- 写执行继续保留现有 CAS，不能因方案内容没变就自动跨版本执行旧确认。
- 只读结果按依赖判断有效性：仅保存 review 元数据不等于方案内容变化；画像、目标、候选和政策改变却可能使同一方案内容的旧结论失效。
- 评价前后比较和反事实比较，除被研究的变化外使用同一输入基线，避免把候选刷新造成的差异当成调整收益。

### F09 · P2：交付顺序尚未形成从用户入口到落地结果的闭环

主设计 `:433` 起的能力目录把首建、删除、替换等标为 planned，这是诚实的能力边界；但完整用户示例又依赖这些能力，当前实施顺序则以 J2 解读为先。不能以解读工具/卡片完成，代替“用户可以完成方案处理闭环”。

建议先确定语义协议和当前可用路径，再按端到端场景交付。结构性只读解读可以并行形成独立切片，但不能先上线未经验证的风险结论，也不能对用户暴露尚未接通的操作按钮。

另有数量术语冲突：权威表 `:89` 明确 summary.targetCount 实际是 requiredCount 的别名，`:153` 又把 targetCount 泛称为用户确认目标。必须逐字段注明所属 DTO，不应全局替换同名字段。

## 4. 统一方案的选择

| 路线 | 优点 | 主要问题 | 建议 |
|---|---|---|---|
| 只补 prompt、旅程路由和解读卡 | 改动小，较快可见 | 生命周期、复合要求、执行影响范围仍不一致 | 仅适合短期文案/保护性修正 |
| 渐进统一语义主干，保留现有执行器 | 可以复用确认、事务和测试，逐场景验证 | 需要先明确契约与兼容边界 | **推荐** |
| 全量重写为统一工作流引擎和单一 solver | 概念上集中 | 迁移面大，容易把确定性编辑复杂化 | 不建议作为本轮目标 |

推荐方案不是再增加一套平行业务状态，而是让现有对象通过同一条可追溯的语义链路协作：

```text
用户消息 + 受信快照
  → 完整意图草稿 / 当前任务
  → 作用域、实体、强度、有效期、冲突解析
  → 动作编译 + 动作规划器
  → 同一输入基线上的评价 + 独立后置校验
  → 冻结变更预览
  → 明确确认 / 修订 / 取消
  → 现有事务执行 + 幂等回执
  → 当前基线上的复查 / 条件情景说明
  → 下一步建议或任务结束
```

只读分析、比较、反事实在评价后直接返回，不进入 pending 或方案写入。审查持久化可能更新元数据和 stateVersion，不能把它等同于纯函数；但它不应偷偷改变方案内容。

### 4.1 六个职责边界

| 边界 | 负责 | 不负责 |
|---|---|---|
| 权威上下文 | 读取并标识画像、政策、方案、有效约束、候选来源 | 推断用户想要什么 |
| 对话意图与任务 | 解析完整要求、指代、歧义、依赖和未完成项 | 将未确认偏好写成有效业务约束 |
| 命令编译与规划 | 将受支持意图变成受限变更，选择精确编辑或搜索 | 越过授权范围“顺便优化” |
| 评价与后置校验 | 共享事实和规则定义，检查结果和变更边界 | 因 warning 自动改变用户目标 |
| 预览与执行 | 冻结完整 diff、绑定确认、事务执行、幂等回执 | 确认后偷偷用新输入重新求解另一版 |
| 解释与续接 | 基于当前评价和真实回执说清取舍、缺口、下一步 | 把结构信号说成经过验证的录取预测 |

这些是职责，不要求每格新建一个服务、表或框架。

### 4.2 状态归属：不重造第二套真值

| 对象 | 建议权威归属 | 约束 |
|---|---|---|
| 已确认画像、有效约束、工作/有序方案 | 现有 Java 业务状态 | 复用 owner，兼容旧字段 |
| 有界当前任务与尚未完成要求 | Java 会话持久化元数据，按需扩展现有载体 | 记录 taskId、原始回合、语义草稿、剩余项、关联 pending/operation；不是另一份方案 |
| pending 状态与确认 revision | 现有 pending 服务 | 不再在 journey/task 复制一套可写 pending 状态 |
| operation 和执行结果 | 现有命令台账/回执 | 恢复先查询结果，不以超时推断未执行 |
| 评价和解释 | 带计算时输入清单的派生产物 | 不反向成为业务约束真值 |
| journey 与模型 working_set | 权威对象的有界投影 | 不能作为可靠任务账本或第二个业务数据库 |

任务状态只表达未完成/待补充/受阻/完成/取消；是否等待确认或正在执行，由关联 pending/operation 派生。只需要恢复当前任务和有限剩余项，不引入通用 DAG 工作流引擎。

### 4.3 写操作的统一契约

冻结的预览至少回答：

1. 为什么改：对应哪个用户回合、哪个任务、哪项明确目标。
2. 按什么口径改：新旧有效约束、作用对象、有效期、数量单位。
3. 改哪些内容：新增、移除、替换、顺序和组内专业变化，不能只显示总数差。
4. 不改什么：锁定项、原有成员、允许变更数量和其他保护边界。
5. 有什么代价：预算/覆盖/档位/偏好变化、未满足项、数据缺口和替代方案。
6. 基于什么输入：状态守卫及计算时依赖指纹。
7. 如何执行：受支持命令、冻结内容摘要、确认 revision 和 operation 关联。

一张卡可以描述一笔有边界的复合事务，前提是服务端真实支持全部操作、预览完整、整体回滚和后置条件完整。**不直接放宽当前 add_units 契约来冒充已支持复合事务。**

业务事务内只执行已冻结、可核对的变更。执行前依赖变化就重新预览；重试返回同一 operation 的回执，不生成另一版。写后复查失败与方案写入失败分别记录：方案已提交但复查不可用时，不应把整笔业务谎报为“没改成”。

## 5. 动作的默认变更边界

以下是推荐目标语义，不是当前全部已支持的能力清单。

| 用户动作 | 默认允许 | 默认禁止 | 关键验证 |
|---|---|---|---|
| 分析/审查 | 读事实、评价、给选项 | 自动修复或更改有效目标 | 评价输入一致，告知缺口 |
| 假如删掉/换成 | 对副本分析 | 创建写 pending、修改真实方案 | 基线一致，明确只读；未支持的反事实不假装已算 |
| 首次生成 | 在已确认口径下选集和排序 | 未确认就写入正式方案 | 模式、资格、数量、硬要求 |
| 加入 | EXPAND、保留原成员 | 静默替换、裁剪、放宽现有精确配额 | 目标全部进入、零删除；满额/配额冲突先协商 |
| 补到 N | 默认只补差额 | 以补齐为名删换已有项 | 实际计数按模式；N 小于当前数不能伪装成补齐 |
| 删除 | 移除明确目标 | 自动补回、删除其他项 | 删除集合准确，解释覆盖变化 |
| 替换 | 明确移出/移入 | 顺带重做未授权区域 | 完整双向 diff、锁定保护 |
| 移动/重排 | 改授权范围内顺序 | 改成员、组内专业或其他约束 | 成员集合不变，位置绑定准确 |
| 锁定/取消锁定 | 改被点名对象的保护状态 | 自动改成员 | 锁的粒度和后续行为明确 |
| 改预算/范围 | 保存口径；或明确预览后的局部重规划 | 不告知就大幅重建 | 有效期、作用对象、全量影响、冲突 |
| 优化一下 | 围绕明确问题给最小必要调整预览 | 默认重做整表或自动采纳全部审查建议 | 改善目标、变更预算、未满足项 |
| 重新做一版 | 在显式授权下扩大搜索和变更范围 | 覆盖用户锁定或放宽硬要求 | 与旧版对比；新授权仍需确认 |

首建和交付前应完成对应的必需硬校验。已有方案的局部修复若只减少违规、仍有其他未解决问题，必须区分“本次修复成功”和“整体方案已达标”，不能以局部成功冒充完整通过；允许哪些修复在不完整上下文下执行，需要动作级白名单，而不是对所有 unknown 一刀切。

## 6. 用户对话闭环

### 6.1 标准旅程

1. **探索**：先回答咨询；无关问题不强行拉回填表。需要个性化方案时才收集省份、年份、批次、选科、成绩/位次等必要事实。
2. **确认口径**：区分“最好在本省”和“只考虑本省”，区分预算偏好与上限；明确本次还是后续有效。画像更新也复用现有确认链，不静默生效。
3. **看候选**：允许比较学校/专业/费用，保留候选批次与实体引用。此阶段不自动把展示过的候选加入方案。
4. **首建预览**：必要事实齐备且能力可用后，编译目标、生成方案预览，列明数量单位、覆盖和缺口；用户确认后才进入正式方案。
5. **分析**：先回答“哪里有问题、为什么”，按事实校验、结构和偏好分组；不把每个提示都当必须修。
6. **比较/反事实**：解释指定变化的条件影响；明示“还没修改”。若该类反事实能力未接通，只提供有依据的定性说明或明确不可计算。
7. **调整预览**：理解完整新要求，检查与旧约束/锁定的冲突，默认最小必要变化；无法满足时给冲突和选项，不自动降级硬条件。
8. **确认执行**：纯确认执行对应 revision；附带新条件则重新预览。遇到过期输入转恢复，不自动跨版本套用旧同意。
9. **回执复查**：准确区分已应用、无变化、执行失败、输入过期、复查不可用；说明改了什么、没改什么、剩余任务。
10. **收尾**：用户认可后可进入最终核对；导出/定稿只有能力实际存在才展示。数据更新、官方计划变化和重新补录成绩应触发影响提示，不自动改表，更不承诺实际录取。

这不是强制线性向导。用户可随时返回比较、咨询或调整；当前任务和已确认方案不能因话题切换而无故丢失。

### 6.2 关键复合对话示例

以下是设计验收用的示例对话，不是对真实会话测试结果的宣称。

**例 A：同时加候选、限地区、限学费**

- 用户：“这六条加进去，太远的不要，学费三万内，稳妥点。”
- 助手：一次提取全部要求；只追问影响执行的歧义，例如“这次预算限制新增条目，还是整个方案？太远是指哪些地区？”；可结合已有明确上下文给一个可确认的解释，不机械重复提问。
- 用户明确范围后，系统先检查六条与预算/地域/现有配额是否冲突；冲突时指出具体条目及可选处理，不先加入后再删除。
- 当前执行器不支持复合修改时，解释分步依赖；任何“稳妥”预设在未支持前不宣称已经生效。
- 后续“继续”读取任务剩余项，进入下一项只读或预览；不等价于批准下一次写入。

**例 B：看完风险后希望优化**

- 用户：“看看方案有什么问题。” → 评价，不写；说明两个超预算、一个顺序异常和若干政策告知之间的区别。
- 用户：“优化一下，尽量别动太多。” → 以明确预算等目标为前提，给局部调整预览；若只存在软提示，说明推荐改善目标供确认。
- 助手：写清“替换哪些、顺序动哪些、保留哪些”，给前后对比；告知未解决项，而不是只说总分提高。
- 用户：“确认，不过 A 不要动。” → 不执行原卡，重新检查 A 的保护要求并出新版；新要求不可行则解释冲突。

**例 C：先假设，再决定是否修改**

- 用户：“去掉最后一个保档会怎样？” → 只读分析，说明剩余保档覆盖、顺序和未知项，不用没有验证过的“滑档概率升高多少”。
- 用户：“那就删掉它。” → 解析到刚才那个稳定 ID 和对应方案基线，生成删除预览，而不是对当前列表重新取“最后一个”。
- 用户确认 → 执行、回执、按当前输入复查。若删除能力尚未实现，明确不可执行，不先承诺后报错。

**例 D：执行期间网络断开**

- 用户确认后断线，重连先恢复 pending/operation 的真实状态。
- 仍在 applying：显示处理中；不展示当前不支持的“取消执行”。
- 已应用但回执丢失：按同一 operation 重放结果；不再执行一次，不凭消息缺失认定失败。
- 续接让路给新用户消息时，不代表业务回滚；之后可按持久化任务和回执继续说明剩余事项。

### 6.3 必须覆盖的非顺畅路径

| 用户或系统情形 | 正确处理 |
|---|---|
| “继续”“接下来呢” | 根据当前任务推进只读/澄清/预览；若存在待确认卡，提示其状态，不自动确认 |
| “可以”“就按这个” | 只有明确承接唯一有效预览且无新条件时，才能确认；不能全局关键词触发 |
| “确认，但……” | 新条件优先触发修订，不能先执行后处理条件 |
| “这批的第二个”“上面那个” | 绑定候选批次、实体和版本；无法唯一解析才追问 |
| 有 pending 时问无关问题 | 正常回答，不消费确认、不自动作废原卡 |
| 有 pending 时修改成绩/选科/批次 | 走对应确认链；变更生效后将依赖旧事实的预览/评价标记失效 |
| “之前的预算取消” | 作为有效约束变更预览，不只在正文说“记住了” |
| 新要求与锁定/精确配额冲突 | 列出冲突及选项；不自行解锁、不裁剪加入目标 |
| 可行候选不足或费用未知 | 区分确实无解和数据不足；不自动放宽上限、不把未知当零费用 |
| 用户接受某项结构风险 | 只记录可接受的取舍，不能覆盖资格或政策硬限制 |
| 旧卡点击、重复确认、多端并发 | 复用 revision/CAS/operation；过期则重新预览，重复则重放同一结果 |
| 方案已应用但复查失败 | 如实返回业务已应用与复查不可用两个状态，允许补做只读复查 |
| 数据刷新或新政策导致旧结论不适用 | 展示失效原因和影响，恢复后重新评价；不静默改方案 |

## 7. 渐进推进顺序

以下是拆分建议，不是本次已经执行的实现计划；用户确认统一语义后，再为各批次编写可执行计划。

| 批次 | 目标 | 可验收结果 |
|---|---|---|
| A：语义与保护边界 | 修订 F01–F05 的口径；核对真实持久化/重排行为；定义任务、确认和能力边界 | 同一句话不丢硬要求；卡面与执行一致；不输出未经验证的录取风险 |
| B：当前可用路径闭环 | 在已有 add/fill/scope/score 等路径接通完整要求、任务剩余项和真实回执 | 复合要求可解释地阻断或分步；“继续”和失败恢复不丢任务 |
| C：统一评价输入与规则 | 定义不可变输入清单、规则状态/强度、必需 probe；旧新评价 shadow 对照 | 所有旧 check 可追溯；未知不伪装通过；规则变更逐条解释 |
| D：按动作收敛规划与执行 | 复用现有 compiler/validator，分别接入首建、替换、删除、重排等能力 | 每个动作有冻结 diff、变更预算、后置条件和幂等回执 |
| E：统一优化策略 | 候选有效视图统一；明确首建/增量/重做的目标 profile 和排序 | 同一口径下生成、调整、审查一致；局部调整不无故大换血 |
| F：增强解读与产品化 | 用已统一的评价提供结构对比和受支持的反事实；风险模型另行验证 | 解释可追溯；不把增加卡片视为完成方案闭环 |

兼容策略：

- 不推倒已有 EXPAND 修复，不批量重命名已持久化字段，不将未完成能力写成已支持。
- 优先修正行为承诺和确认边界，再迁移数据结构；迁移期间新旧结果 shadow 比较，不让两个执行器同时写同一真值。
- 结构解读可形成独立只读切片，但需先完成 F04/F07/F08 的语义和隔离约束；不必等待统一 solver，也不能继续使用原风险真值表作为业务正确性证明。
- 新的规范获批前，10 月 18 日主设计、权威表和计划均视为待对齐，不能仅修改其中一份后直接按其余两份实施。

## 8. 验收方式

### 8.1 语义与对话验收

- 将第 6 节转为逐轮 fixture：输入消息、权威快照、完整意图、待补充项、允许动作、是否业务写入、预览和回执的期望。
- 重点覆盖复合要求、指代、混合确认、话题切换、继续、撤销约束、候选不足和能力未实现；不只覆盖标准 happy path。
- 模型语义提取、契约校验、执行器结果分别验收；对手写 fixture 的自检不能证明模型会正确路由。
- 固定记录模型/提示词版本，用离线回放检查结构化行为；涉及确认、硬约束和指代的路由变更，再做独立受控模型评测，不将不稳定的网络调用混成普通单元测试。

### 8.2 系统不变量

- 未明确确认，不改变方案、画像或有效约束；只读反事实不得创建写 pending。
- 预览的成员/顺序/约束变化与实际结果一致；输入变化不能静默重新求解。
- 加入不隐式删除；重排不改成员；锁定不能被局部优化绕过；按模式正确计数。
- 当前任务的硬要求不能因动作协议不支持而被静默丢弃。
- 同一 operation 的重复请求至多产生一次业务效果；超时恢复以台账为准。
- 评价和解释只能引用自己的计算输入，旧结果不能被新摘要重新认证。
- 个性化缓存不能跨 tenant/session 混用，反事实结果不能复用其他反事实参数。
- 修复建议不能自行升级为有效约束，结构提示不能冒充经过验证的录取概率。

### 8.3 发布依据

先记录当前行为基线，再比较变更前后：未授权写入、隐式删除、硬要求遗漏、错误确认、重复执行、缓存串会话等安全事件在验收场景中必须为零。任务完成率、澄清次数、修改条目数、可恢复率、耗时则基于实际样本比较，不在没有基线时编造提升百分比。

模型评测、Java/Python/Web 定向测试、事务/并发测试、真栈会话验收各自提供证据，互不冒充。本次静态评审没有执行这些测试，也不据此给出上线通过结论。
