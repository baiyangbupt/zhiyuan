# 对话执行引擎核心能力建设路线图

**日期：** 2026 年 9 月 8 日  
**优先级：** 对话效果、上下文利用、工具编排、结构化结果、方案交互  
**当前基线：** Gateway/Codex 回合闭环和上下文工作集基础能力已完成；真实模型已通过候选指代、缺参数澄清和完整历史查询验收

## 一、总目标

把系统从“旧链路中混合大量规则和工具调用”升级为：

```text
用户表达
  -> 对话理解与任务识别
  -> 上下文工作集构建
  -> 执行计划与缺口判断
  -> 工具调用循环
  -> 事实/证据整理
  -> 方案或回答生成
  -> 对话状态沉淀
```

模型负责理解、选择路径、调用工具和组织表达；确定性代码负责状态读取、参数归一、事实整理、Proposal 编译和结果后处理。

## 二、能力阶段

### 阶段 A：对话执行网关与回合闭环【已完成核心实现】

**目标：** 建立可运行的 Codex 执行容器，而不是直接改写旧 ChatService。

**已完成：**

- Gateway 生产组合根和 legacy 回退。
- Codex App Server 回合终态收集。
- 会话级回合幂等与输入冲突处理。
- Snapshot / StatePatch 注入。
- 结构化 TurnOutput、Evidence、Artifact 校验。
- 只读 MCP 工具和可信上下文链路。
- Shadow 固定回放 18 例通过，四项硬门禁为零。

**当前结论：** 可以承载后续能力建设；暂不把安全灰度和多实例恢复作为当前主线。

### 阶段 B：统一对话上下文工作集【下一主阶段】

**目标：** 模型每轮看到的是结构化、分层、可更新的上下文，而不是只看到长历史或一次性快照。工作集是业务状态投影，不负责替代 Codex 做意图识别或任务规划。

**核心对象：** `ConversationWorkingSet`

建议字段：

- `turn_goal`：本轮用户真正想完成的事。
- `task_family`：`intake`、`query`、`explore`、`plan_review`、`plan_mutation`、`confirmation`、`clarification`。
- `explicit_entities`：本轮明确提到的学校、专业、地区、分数、方案对象。
- `conversation_references`：如“刚才那个”“这几个”“去掉它们”的指代解析。
- `confirmed_facts`：成绩、选科、画像、方案、历史约束。
- `working_facts`：本轮工具返回但尚未成为长期状态的事实。
- `missing_slots`：完成当前任务所缺的信息。
- `candidate_actions`：允许的下一步动作及其前置条件。
- `pending_decision`：等待用户确认的 Proposal 或澄清问题。
- `last_tool_results`：按工具、实体、版本和时间组织的最近结果。
- `answer_contract`：本轮必须回答什么、哪些内容不能推断。

**实现顺序：**

1. 从现有 `RequestContext`、`ConversationPhase`、`PlanningSummary`、最近 Intent 结果构建工作集。
2. 从历史 `routeObservability` 和工具返回中恢复指代与上一轮任务。
3. 将工作集作为 Gateway 注入 Codex 的独立上下文块。
4. 工具返回后增量更新工作集，而不是只追加原始 JSON。
5. 对旧 ChatService 保持适配器，避免一次性重写 `service.py`。

**验收：**

- “那几个学校”“刚才的专业”“去掉它们”能恢复上一轮实体。
- 用户换话题时旧任务不会污染新任务。
- 同一事实不会因历史重复而重复调用工具。
- 缺失关键字段时先澄清，不调用不完整查询。

### 阶段 C：任务识别与执行计划【阶段 B 稳定后】

**目标：** 模型不再靠 prompt 猜下一步，而是先形成轻量执行计划。

**任务计划字段：**

- `objective`：用户目标。
- `steps`：读取上下文、实体解析、领域查询、比较/审查、生成回复。
- `required_tools`：完成目标所需工具。
- `completed_steps`：已完成步骤与证据。
- `blocked_steps`：缺失字段、状态不够新、用户未确认等阻塞。
- `finish_condition`：何时可以结束本轮。
- `user_visible_next_step`：需要澄清或确认时展示的下一步。

**首批任务族：**

1. 分数/分数线查询。
2. 学校、专业、地区信息查询。
3. 职业方向探索。
4. 当前方案概览与审查。
5. 方案调整预览。
6. 用户画像采集与确认。
7. 待确认 Proposal 的确认/取消。

**关键规则：**

- 查询任务优先补齐查询参数，再调用领域工具。
- 探索任务先解释适配关系，再给学校/专业例子。
- 方案操作先读取现状，再生成预览，不直接执行。
- 多目标请求拆成有序子任务，避免一次调用大量无关工具。
- 工具结果不足时计划进入 `needs_clarification` 或 `insufficient_data`，禁止编造补全。

### 阶段 D：工具编排与结果合成【阶段 C 并行】

**目标：** 从“模型调用若干工具”升级为有预算、有去重、有依赖关系的工具循环。

**核心能力：**

- 工具前置条件检查。
- 工具参数从实体和工作集确定性填充。
- 相同实体、相同版本、相同参数结果复用。
- 并行执行互不依赖的只读查询。
- 工具失败后的有限重试和替代路径。
- 结果按事实、比较、建议、限制分层。
- 将事实绑定到 evidence/artifact，不让模型凭记忆拼接数字。

**优先优化工具族：**

- `score_query_tool`
- `school_info_tool` / `school_compare_tool`
- `major_info_tool` / `major_compare_tool`
- `admission_fit_match_tool`
- `plan_query_tool` 对应的当前方案读取能力
- `explore_direction_tool`
- `intent_state_tool` 的预览与确认链路

### 阶段 E：方案交互与 Proposal 生命周期【阶段 D 稳定后】

**目标：** 形成完整的“理解要求 → 生成预览 → 用户确认 → 执行 → 后置验证”对话循环。

```text
用户要求
  -> 需求归一
  -> 当前方案读取
  -> Proposal 生成
  -> 影响说明 / 风险说明
  -> 用户确认或修改
  -> 后端执行
  -> 重新读取方案
  -> 结果回执
```

**重点能力：**

- 追加、替换、删除、重排、补齐数量、调整冲稳保目标的语义区分。
- “不要民办”与“只要公办”的极性和约束强度区分。
- 方案已有内容、用户本轮要求、历史偏好三者合并。
- 预览内容冻结，用户确认后不可重新解释成另一套操作。
- 执行后必须回答实际变化、未变化原因和剩余风险。

### 阶段 F：对话质量评估与主链路迁移【最后】

**目标：** 用真实对话效果而不是单一工具成功率评价引擎。

**指标：**

- 首轮目标识别正确率。
- 关键实体恢复正确率。
- 不必要工具调用率。
- 缺参数时澄清正确率。
- 事实 Evidence 覆盖率。
- 用户要求与最终动作一致率。
- Proposal 预览与执行一致率。
- 多轮指代消解成功率。
- 用户可理解性和重复解释率。
- P50/P95 回合耗时与失败恢复率。

**迁移顺序：**

1. Shadow 对比，不改变用户答案。
2. 指定场景 Readonly：查询、探索、方案只读审查。
3. 小范围 Proposal 预览，不执行写操作。
4. 经过确认的受控执行。
5. 新 Gateway 成为主链路，旧 ChatService 只保留兼容回退。

## 三、当前实现位置

- 阶段 A：核心实现完成，专项测试和固定 Shadow 回放已通过。
- 阶段 B：已新增 `app/engine/working_set.py` 并接入 Gateway。当前保存最新 Snapshot、已校验 Evidence、招生事实、Artifact、Proposal 引用、上一轮响应元数据，以及工具返回的稳定候选实体；候选集合带 Snapshot/阶段作用域，阶段或招生模式变化时失效。真实模型已通过“那几个学校”的候选指代和缺参数澄清，以及完整参数下两所学校历史分数查询；工具调用、实体 ID、Evidence、`fact` 响应类型均已被轨迹和语义评估正确识别。
- 阶段 C：已开始建立跨工具、跨轮次的统一执行计划骨架；当前只注入状态驱动的目标、标准步骤、阻塞信息和完成条件，仍由 Codex 根据用户原话确定任务类型和具体工具，不用关键词规则替代模型规划。
- 阶段 D：已建立只读工具契约、参数规范化、前置缺口检查、稳定调用键、重复调用识别和结果按 Evidence/实体 ID 归并能力；已增加依赖有序的工具批次报告，可区分完成、阻塞、重复、失败和部分成功；当前仍不拦截模型调用或自动驱动重试。
- 阶段 E：旧链路已有较完整的 pending / Proposal / confirm 机制，下一步应将其状态投影给新引擎，而不是重新实现一套写入链路。
- 阶段 F：已有对话回归、Shadow fixture 和指标模块，但需要围绕任务完成度重新组织。

### M4：对话结果合成

- 已扩展 `TurnOutput`，统一提供 `executionStatus`、`limitations`、`nextStep`、`uncertainties` 和澄清字段。
- 已新增 `app/engine/result_synthesis.py`，将真实工具批次的 `partial/blocked/failed` 状态确定性映射到最终输出，不修改事实和 Evidence 内容。
- 工具部分成功时明确说明覆盖范围；参数或前置条件阻塞时输出补参下一步；工具失败时禁止伪装成完整事实结果。
- 语义评估夹具已增加部分成功和阻塞结果场景，并检查 `executionStatus`、`limitations`、`nextStep`。
- `TurnTrace` 已同步输出上述结果合成字段，便于离线回归区分“事实内容正确”和“执行状态表达正确”。
- 真实语义烟测的事实场景现在同时要求领域工具调用和 Evidence；模型若绕过工具直接生成 `fact`，评估明确失败，不再被自然语言表面正确性掩盖。
- 新增混合读写语义场景：同一轮同时查询历史分数和修改方案时，允许只读查询继续，但禁止 `plan_apply`，并要求输出阻塞状态、澄清和下一步。
- 让 Codex 输出引用结构化 evidence/artifact，而不是自由拼接数据。
- 增加多轮、混合目标、工具失败和数据不足回归案例。
