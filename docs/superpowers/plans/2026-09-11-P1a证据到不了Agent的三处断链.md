# P1a 的证据到不了 Agent：三处断链实测

> 日期：2026-09-11
> 起因：给 `2026-09-11-P1a上游版本契约实测与dataVersion改设计.md` 做影响面核查时，顺手查"Java 签出来的证据被谁消费"
> 影响：P1b 的实际改动面（比原估计大，且重心在 Python 侧不在 Java 侧）
> 结论：**Java 签发的证据在生产链路上一次都到不了模型。** 三处断链互相独立，逐处都有行号，任一处不修都白修。

---

## 一、为什么去查这条链

`P1a-evidence-ledger/REVIEW.md` 第四节第 2 条写的是：

> 生产取数路径 `GaotuService.java:603/617` 走不带 `EvidenceScope` 的重载（等价于不签发），**唯一会签发的调用方是 inner 下的 `GaotuClientDebugController`**。

这句话的**事实部分对，推论部分错**。我当时把"inner 下的 debug controller"读成了一个调试用的旁路，于是把"接会话上下文到生产取数路径"理解成一件 Java 侧的活。

实际查下来：**那个 debug controller 就是 Agent 的生产取数入口。** 名字叫 Debug，干的是正事。真正不签发的原因在别处，而且不止一处。

## 三、三处断链

### 断链 1：scope 根本没上路，Java 收到的恒为空

四跳里每一跳都把 scope 丢了一点：

| 位置 | 情况 |
|---|---|
| `server.py:209-212` | 构造 `InternalClientBackend` 时只传 `tenant_id` / `chat_session_id`，**没传 `thread_id`**——而 binding 里有（`tools_readonly.py:290` 就在用 `self.binding.thread_id`） |
| `tools_readonly.py:366-370` | `get_history()` 只转发 6 个业务参数，backend 自己存着的 `tenant_id` / `chat_session_id` 也没往下传 |
| `internal_client.py:1699-1706` | 函数签名里就没有 scope 的位置 |
| `internal_client.py:71-77` | `HttpClient.post` **没有 `params` 形参**，只有 `headers`。JSON 体里的键不会绑定到 Java 的 `@RequestParam` |

于是 Java 侧恒为 `EvidenceScope.of(null, null, null)`，`EvidenceLedgerService.sign()` 在 `:76-86` 判 scope 不完整，返回 `null`，**不签发**。

**所以 REVIEW 第 2 条的结论对、归因错。** 不签发不是因为 `GaotuService.java:603/617` 走了不带 scope 的重载——那条路是 Java 内部调用方走的，Agent 根本不经过。**要改的是 Python 侧，不是 Java 侧。**

### 断链 2：信封在证据被读到之前就丢了

`tools_readonly.py:334-336`：

```python
@staticmethod
def _data(response: Any) -> Any:
    return response.get("data") if isinstance(response, dict) and "data" in response else response
```

P1a 把 `evidence` 和 `dataVersion` 挂在**信封层**（`ResponseDTO`），`_data()` 只取 `data` 子对象，两者一并丢弃。

这一处的要害在于：**它独立于断链 1。** 即便 scope 接通了、Java 真的签发并落了库、证据也确实随响应回到了 Agent，它仍会在下一个函数调用里被扔掉。然后 `tools_readonly.py:262` 取不到 `source_evidence`，落进 `:277-296` 的自铸分支，产出 `admission-unit:…:unknown`——**正是整个 P1 要废除的那个东西**。

台账里有记录、模型引用的却是自铸 ID，P1c 的核验会判 `unknown` → 硬失败。也就是说断链 2 不修，把 P1c 接上去的结果是**整轮 fail closed，而台账看起来一切正常**。

### 断链 3：形状不对，`admission.get_history` 在真实 backend 上结构性返回 `insufficient_data`

`ResponseDTO<List<QuerySchoolMajorScoreLineRes>>` 的 `data` 是 **JSON 数组**。`_data()` 交出一个 list，而 `_admission_envelope()` 第一件事是（`tools_readonly.py:215-221`）：

```python
if not isinstance(result, dict):
    return error("insufficient_data", "admission backend returned no structured data", ...)
```

list 不是 dict → 恒真。**不是数据不够，是形状不对**，但错误码说的是前者。

### 附带发现：`major_group` 模式下 `groupCode` 被要来又被扔掉

`tools_readonly.py:109-111` 在 `major_group` 模式下强制要求模型提供 `groupCode`，否则 `needs_clarification`。但 `get_history()`（`:366-370`）只读 `areaId` / `batch` / `schoolId` / `majorId` / `year` / `subjectType`——`groupCode` 经 `**arguments` 收下后**静默丢弃**。

后果是查回来的数据不对应模型问的那个专业组。这一条不在证据链上，但同属"接口之间形状没对齐"，P1b 顺手一起修。

## 四、为什么三层验证都没照出来

三层都真实有效，但边界在同一个地方止住：**没有任何一条覆盖"真实 backend 适配器产出的形状"**。

| 验证层 | 覆盖了什么 | 为什么漏掉 |
|---|---|---|
| 单测 `test_domain_mcp_tools.py:378-391` | 唯一碰 `InternalClientBackend` 的用例 | 测的是 `get_current_plan`，桩返回 `{"code":0,"data":{"items":[]}}`——`data` 是**对象**，`_data()` 交出 dict，正好绕开断链 3 |
| 单测 `:395` 起的全部 admission 用例 | `_admission_envelope` 的归一化逻辑 | 用手写 `Backend` 桩，直接返回 `{"dataVersion":"v17","admissionFacts":[…]}`——**那是消费者期望的形状，不是 `InternalClientBackend.get_history` 的实际产出** |
| 语义冒烟 | 模型能否正确使用工具 | 跑的是夹具 MCP（T005 里 `dataVersion=semantic-fixture-1` 那个），完全不经过 `InternalClientBackend` |
| P1a 端到端验收 | Java 侧签发与四态 | 直接打 `/internal/evidence/**` 与 inner 接口，不经过 Agent |

每一层都在自己的边界内是对的。缝隙在层与层之间，而缝隙正好就是这条链。

## 五、P1b 要做什么

四件事，**顺序不能乱**。

### 1. scope 上路（Python + Java 一起改）

三处都要动：`server.py:209-212` 补 `thread_id=binding.thread_id`；`tools_readonly.py` 的 backend 方法带上 scope；`internal_client.py` 的两个函数加 scope 参数。

**传输通道建议走 header，不走 query string。** 理由有两条：`HttpClient.post` 已有 `headers` 形参而没有 `params`，加 `params` 要改公共方法、影响面比这次大；而且 scope 是环境上下文不是查询条件，放 header 语义更对。Java 侧相应把三个 `@RequestParam` 改成 `@RequestHeader(required = false)`。

### 2. 信封别丢

`_data()` 要保留 `evidence` / `dataVersion`，或者让走 `GaotuClient` 的那几个方法不经过 `_data()`、把信封整体交给 `_admission_envelope`。

### 3. 形状对齐

让 **backend 适配器**负责把 `data` 数组包成 `_admission_envelope` 期望的 `{"admissionFacts": [...], "dataVersion": ..., "evidence": [...]}`，而不是去改 `_admission_envelope` 让它兼容两种形状。适配器的职责本来就是形状转换，改这一侧改动面小、职责清楚，也不会让归一化逻辑长出分支。

### 4. 最后才删自铸分支（设计文档 5.1）

**必须先修好 1–3 再删。** 先删会让 `admission.get_history` 从"返回自铸证据"变成"返回无证据"——两种都不对，但后者会让 `fact` 输出直接 fail closed，把一个静默的错误放大成全线挂。

## 六、验收必须带的对照

每条正向检查配一条能证伪它的反向对照（`tasks/README.md` 规则 4）：

- **scope 上路**：Java 侧日志断言 `tenantId` / `chatSessionId` / `threadId` 三项非空。**对照**：故意不传 `threadId`，Java 必须不签发——证明这条链真的在起作用，而不是 Java 忽略了 scope 照签。
- **证据穿透**：一次真实 `admission.get_history` 之后，工具结果里的 `evidenceId` 必须以 `ev_` 开头。**对照**：同一次调用后直接查 `evidence_ledger` 表，必须有对应行。**只看返回值不够**——返回值可能正是 Agent 自铸的，那个分支产出的 ID 长得也挺像。
- **形状**：真实 backend 上 `admission.get_history` 的 `status == "ok"`。**对照**：改之前先跑一次留档（现在必然是 `insufficient_data`），作为"修好了"的判别性证据。没有这个前置留档，改完看到 `ok` 也说不清是修好了还是本来就好。
- **补一条单测**：用**真实信封形状**（`{"code":0,"msg":"ok","data":[…],"dataVersion":…,"evidence":[…]}`）喂 `InternalClientBackend.get_history`，断言产出能被 `_admission_envelope` 吃下且 `evidence` 未丢。这条正是现在缺的那条——它要是早在，断链 2 和 3 都不会存在。

## 七、方法论

上一份笔记的结论是"替身能证明代码按设计工作，不能证明设计与外部世界相符"，那次替我作证的是假上游。这次是**假 backend**，同一个形状的错误换了个对象。

更精确的说法是：**这些桩的形状是照着消费者的期望写的，不是照着生产者的实际产出写的。** 于是它们证明的是"消费者能吃下它期望的东西"——一句同义反复。`test_domain_mcp_tools.py` 里那些 `Backend` 桩返回 `{"dataVersion": "v17", "admissionFacts": [...]}`，而真实的 `InternalClientBackend.get_history` 返回一个数组，两者之间没有任何一条测试。

可操作的推论：**桩的形状要从真实生产者那一侧取，不要从消费者的期望那一侧编。** 具体到本仓——任何替 `internal_client` 作桩的测试，返回值都应当是一次真实响应的留档（手抄也行），而不是"应该长这样"。已补进 `tasks/README.md` 第六节。
