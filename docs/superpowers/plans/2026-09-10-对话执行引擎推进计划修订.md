## 零、本次核查发现的三处偏差

既有计划的阶段结论部分基于过时或未经代码验证的判断。以下三处需要先纠正，否则会把工作量投到错误的地方。

### 偏差 1：Java 执行闭环已实现，不是"待补"

总计划 M5 记载「尚未衔接规划命令执行与 complete/fail」「待补：确认后的命令执行」。实际代码：

- `zhiyuan-server/src/main/java/com/ytell/zhiyuan/service/biz/PendingPlanningCommandBizService.java`
  `execute()` 已完整实现：`operationId` 幂等去重与结果重放 → `validatePendingOwner`（要求 pending 处于 `applying`、pendingId/claimToken 匹配、租约未过期）→ 锁定 planning-state 数据行并 CAS 校验 `expectedPlanVersion` → 分发 4 种命令类型 → `UnifiedPlanPostconditionValidator.validate` 后置校验 → 持久化可重放结果。
- `PendingConfirmationBizService.java` 的 `resolveTransition` 显式枚举全部状态转移，`CLAIM_LEASE_MILLIS` 5 分钟租约，`validateClaimOwnership` 强制所有权校验。
- `validatePlanChangeProposal` 还做三层版本交叉校验（`expectedPlanVersion` == `applyReq.sourceVersionGuard` == `userGoal.sourceVersionGuard`）。

**结论**：缺的是 Gateway→Java 的调用接线与真实 E2E 验证，不是 Java 实现。P2 工作量应据此下调。

### 偏差 2：跨回合的权威证据台账不存在

完成标准写「所有招生事实均可追溯到权威 Evidence」。实际：

- `zhiyuan-server/src/main/java/com/ytell/zhiyuan/service/biz/ConversationSnapshotService.java:177`
  `fillEvidence()` 是空方法体，注释明写"do not synthesize or infer references here"，`snapshot.getEvidence()` 恒为空列表。
- `zhiyuan-agent/app/engine/working_set.py:77` 从 `snapshot.evidence` 取证据 —— 恒为空；跨回合证据实际来自 Agent 进程内存中上一轮 `TurnOutput.evidence_refs` 的累积。
- `zhiyuan-agent/app/gateway/service.py:718` 构建的 `evidence_ledger` 来自本回合 turn events（含 MCP 工具结果），`validate_turn_output` 会用它校验模型的 `evidenceRefs`。

**准确表述**：**回合内有事实门禁**（模型 evidenceRefs 必须对上由真实工具结果构建的 ledger），**跨回合没有权威证据台账**。证据 ID 由 Agent 进程自建，Java 从不签发、从不校验、不留审计记录，因此无法复验历史回合的事实、无法检测证据失效。

这是当前架构最实质的缺口，也是 P3 流程门禁能否成立的前提。

### 偏差 3：新引擎的"真实验证"程度被高估

- `tests/integration/test_gateway_composition.py`、`test_shadow_gateway.py` 全部用 `MagicMock`/`AsyncMock` 构造假 codex harness，从不拉起真实子进程。验证的是组合逻辑正确性，不是真实模型交互能力。
- 真实 codex 交互仅有 `scripts/codex_semantic_smoke.py`、`scripts/codex_app_server_poc.py` 两个手动脚本，**不被任何 `.sh`/`.yml` 引用**。
- 仓库**没有 CI**（无 `.github/workflows`），全部测试靠人工触发。

**结论**：M6 长期卡住不是偶然。质量门禁需要与 P0 同步建设，否则每次模型侧变动都要人工重跑。

### 附带发现：两块死代码

- `zhiyuan-agent/skills/` 下 7 个 `SKILL.md`（career_path_chat / explore_chat / intake_chat / intent_detect / plan_chat / plan_query / score_query）**不是孤儿**（此处曾误判）：生产 `ZhiyuanAgent` 确实不传 `skill_dirs`，但 `examples/demo_agent.py:61` 传了 `skill_dirs=["./skills"]`，而该脚本在 `AGENTS.md:31`、`CLAUDE.md:39` 中被记为可运行示例，并有 `tests/integration/test_agent_integration.py:62` 覆盖。**不能删**，只需修正 `CLAUDE.md` 中"技能按需加载"这一容易被读成生产机制的描述。

### 编译器缺口（仍散落在流程与提示文案里）

1. **资格类硬约束无独立校验器**：单科要求、色盲色弱、性别、语种限制目前只是 `majorPlanTags` / `mustSubjects` 标签，靠 `special_enrollment` 审查规则生成风险提示文案，没有结构化 pass/fail 校验。
2. **选科匹配两套实现**：`PlanValidationService.checkMajorSubjectAvailability`（基于 `MajorProfileManager.getSelectLimit()` 做 OR-of-AND）与 `VolunteerFilterChain.isSubjectFiltered`（解析"物和化"中文字符串）逻辑相近但未合并，存在不一致风险。
3. **办学性质仅为软信号**：`matchesSchoolNature` 进 `futureDevelopmentScore` 软打分，只有用户显式提硬要求时才经标签 DSL 升格为硬约束。

### rank 层可解释性

`zhiyuan-rank/services/recommendation.py`（约 1450 行）：熵权法算基础分 + 规则化加减分链算意向修正 + 调和平均合成 `volunteer_score`（用调和平均是为了强调"不能有短板"）。

## 二、P0：解除模型阻塞（已定性，2026-09-10 修正）

### 原定性作废

本节原写「M6 卡在 DeepSeek `/responses` 复杂回合断流」，并给出 `cargo build -p codex-responses-api-proxy` 的构建步骤。**两处都不成立**：

- 构建步骤不可执行：系统 cargo 1.72.1，codex-rs 要求 1.95.0 + edition 2024，且无 rustup。
- 断流的定性是错的。见下。

### 实测定性（T001 采集，`docs/superpowers/tasks/T001-sse-capture/`）

用 Python 透传代理夹在 codex 与 DeepSeek 之间抓到完整现场，22 个 dump：

1. **不存在断流。** 复杂回合请求在 60–400ms 内被上游以 HTTP 400 拒绝，**从未进入流式阶段**。10 次协议运行 + 1 次不经代理的直连对照，错误逐字相同：

   ```
   Invalid json schema: field `anyOf`: field `anyOf`: missing field `type`
   ```

2. **流式链路是好的。** 对照实验 S3b：同一复杂场景、同一上下文与 MCP 工具，仅把 schema 换成手工简化版，3/3 完成，7 条流最长 9.736s / 691 chunk，全部以 `response.completed` + `CLEAN_EOF` 正常收尾。

3. **真正的阻塞**：`zhiyuan-agent/app/gateway/service.py` 的 `TURN_OUTPUT_SCHEMA` 有 24 个 `anyOf` 节点不带 `type`（Pydantic 为 `Optional[X]` 生成的标准形态），DeepSeek 的 Responses 实现比 OpenAI 校验更严，直接拒收。

### 上游已知的两条 schema 约束

| 约束 | 来源 | 当前是否满足 |
|---|---|---|
| `anyOf` 节点必须带 `type` | 10 次协议运行的 400 | **否**，24 处违反 |
| `required` 必须覆盖对象全部 `properties` | S3 探测的 400 | 是，由 `_strict_model_schema()` 强制，不得退化 |

### P0 未完全清零：schema 之后还有一层（2026-09-10 补记）

T003 的验收条件（`status=completed` ×6）由设计会话写错，它量的是 codex 回合是否收尾，不是场景是否跑通。补跑语义评估后，同一批运行 4/6 `evaluation.passed == false`。复盘查出两件独立的事：

2. **`mcpCalls` 仪表从来没有读数。** codex 不把 `ZHIYUAN_SEMANTIC_MCP_TRACE` 传给 MCP 子进程，夹具 `record()` 每次早退。此前据此得出的"MCP 调用被拦下"结论方法上不成立（结论碰巧方向对，但证据是坏的）。

### P0 仍未清零：T005 之后还有第三层（2026-09-11 补记）

T005 已判定 `ACCEPTED_WITH_FOLLOWUP`（`docs/superpowers/tasks/T005-mcp-execution/REVIEW.md`）：只读工具确实执行了，`mcpCalls` 仪表确实有读数了。但复核时独立重跑 `reference-complete-history` **8 次得 7 过 1 挂**，挂的那一次暴露出第三层，与前两层互相独立：

**`turn/start` 的原生 `output_schema` 在 DeepSeek 上不保证结构化输出。**

那一次的现场：`status=completed`、`errorCode=null`、`errors=[]`、`mcpCalls=2`（工具执行正常）、`elapsedMs=9189.6`，但 `output=null`。从 `item/agentMessage/delta` 重建模型原文（2810 字）后看清：模型先写了一段中文说明加一张 Markdown 表格，**最后**才补一段 ` ```json … ``` ` 围栏。`app/harness/codex.py:302` 的 `_parse_json_object()` 只在字符串**以** ` ``` ` 开头时剥围栏，前面有散文就不剥，`json.loads` 抛错返回 `None`。判别性对照证实内容本身合规：同一条消息切掉前置散文只喂围栏块，立刻解析出 `dict` 且 `responseType='fact'`。

两条结论要分开记：

1. **产品层**：模型会时不时把合规 JSON 包在散文里。harness 取不到 output 的那一回合，在真实 Gateway 里就是**废回合**——用户问了、模型答了、系统当没听见。这不是 T005 的锅（T005 的边界是工具执行与仪表），但它是 P0 的第三层阻塞。
2. **仪表层**：`scripts/codex_semantic_smoke.py:247` 在 output 取不到时**整个 `evaluation` 键不写入**。缺键与 `passed == false` 现象不同，但任何写成 `d.get('evaluation', {}).get('passed')` 的检查都会把前者读成假值而不报错。这是规则 4 第二问的又一个实例：**缺失的键比零值更危险**，已补进 `tasks/README.md` 规则 4。

两件事归入 **T008**（`docs/superpowers/tasks/T008-output-extraction/TASK.md`）。
