# 对话执行引擎生产网关与 Codex 回合闭环实施计划

> **面向执行 Agent：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`，按任务逐项实施本计划；所有步骤使用复选框跟踪状态。

**目标：** 在保留旧链路可回退能力的前提下，完成生产 `GatewayService` 组合、Codex 回合终态收集、可信 binding 传递和只读输出校验闭环。

**架构：** 以现有 Codex App Server 第一阶段计划为基础，不重写 `service.py`。新增生产组合根负责生命周期和依赖装配；Harness 将 JSON-RPC 请求响应与异步通知收敛为稳定的 `CodexTurnResult`；Gateway 负责租户、会话、线程、招生类型、状态版本、Evidence 和 Artifact 的最终边界校验。Shadow 模式仍由 legacy 回复用户，Readonly 模式只允许通过完整校验的 Codex 回复。

**技术栈：** Python 3.10、FastAPI、asyncio、Pydantic、pytest、Codex App Server stdio JSONL、只读 Domain MCP。

**规格：** `docs/superpowers/specs/2026-09-07-对话执行引擎生产网关与Codex回合闭环设计.md`

## 全局约束

- 不删除或回退现有 `ChatService`、`BaseAgent`、WebSocket 兼容协议和已存在的未提交用户改动。
- 不开放 Shell、文件写入、Git、浏览器、网络搜索、子 Agent 或任意代码执行能力。
- 不信任模型提供的 `tenantId`、`sessionId`、`userId`、`threadId` 或能力集合。
- 不从自然语言回复反向创建 Proposal、Pending、Artifact 或写操作。
- 所有事实、录取数据和风险结论必须有当前回合 Evidence 或权威 Snapshot 支撑。
- 不在本计划中改造招生算法、Solver、Proposal/CAS 写入链路或前端视觉。
- 不提交 Git commit；每个任务用测试和 `git diff` 作为检查点。
- 每个生产代码变更必须先有对应失败测试，再实现最小修复。

## 验收标准

- `GATEWAY_MODE=codex_shadow` 启动时 `app.state.gateway_service` 非空。
- `turn/start` 只返回 `inProgress` 时，Gateway 不会提前返回成功。
- `turn/completed` 后才能产生 Codex 成功输出。
- Codex 失败、超时、进程退出和 binding 失败不会持久化未验证回复。
- 跨租户、跨会话、跨线程或跨状态版本 Evidence 全部被拒绝。
- 只读 MCP 工具不允许模型伪造身份或调用写能力。
- 同一回合重试不重复执行；不同输入复用同一回合 ID 会失败。
- 不同会话可以并发执行，不被单个会话的模型耗时阻塞。
- legacy 默认模式和现有 WebSocket 协议保持兼容。
- 完整测试集无新增失败；若存在已有无关失败，必须在验收记录中单独列出。

### Readonly 多实例前置条件

- 现有后端仅保存 opaque handle 的哈希，MCP registry 仅在本地保存原 handle；新实例不能、也不应从哈希恢复原 secret。
- 多实例/进程重启恢复需要后端增加“经 Gateway 机器身份认证后重新签发短期 handle，并吊销旧 handle”的契约。不得仅凭 tenant、session、user、thread 等业务参数签发或恢复 binding。
- 在该契约和机器身份边界落地前，只允许单实例 `codex_readonly` 小范围验证；禁止作为多实例生产部署方案。
