## 一、问题的准确表述

修订计划里写的是「跨回合的权威证据台账不存在」。代码级核查后，准确的说法比这更严重：**证据 ID 是 Agent 进程自己造的，并且自己给自己盖了「authoritative」章。**

三处代码构成完整的自证闭环：

### 1. Agent 自铸 evidenceId 并自贴权威标签

`zhiyuan-agent/app/mcp_server/tools_readonly.py:195-203`：

```python
if not evidence and result.get("dataVersion"):
    evidence = [{
        "evidenceId": f"ev-{name}",          # ← ID 就是工具名
        "sourceLevel": "authoritative",       # ← 自己盖章
        "dataVersion": result["dataVersion"],
        "limitations": limitations,
    }]
```

`evidenceId` 等于工具名，**不含任何查询参数**——同一个工具用不同参数查两次，产出同一个证据 ID。

同文件 `:277-296` 的 admission 分支同理，且更宽松：

```python
"evidenceId": f"admission-unit:{fact['admissionUnitId']}:{data_version or 'unknown'}",
"sourceLevel": "authoritative",
"source": "zhiyuan-server.admission",
"scope": {"tenantId": ..., "sessionId": ..., "threadId": ...},   # ← scope 也是 Agent 自己填的
```

`dataVersion` 缺失时直接写字符串 `'unknown'` 进 ID。

全仓只有这两处写 `sourceLevel: "authoritative"`（`grep` 确认，`contracts.py:23` 定义了 `authoritative` / `computed` / `planner_experience` 三值）。也就是说：**「权威」这个标签目前 100% 由 Agent 进程自己颁发，Java 从未参与。**

### 2. 校验器很严，但它校验的是 Agent 自己造的账

`app/gateway/output_validation.py:118-155` 的逐条检查其实相当完备——`evidence_not_found`、`stale_state`、`evidence_mismatch`、`admission_mode_mismatch`、session/thread/tenant 三重 scope 校验（`strict_scope=True` 时要求 scope 字段必须存在）、以及 `admission_evidence_missing`（事实必须有配对的引用）。

问题不在校验逻辑，在被校验的账本从哪来。`app/gateway/service.py:770-785`：

```python
evidence_ledger = _by_id(
    _collect_records([turn.get("evidenceLedger", []), turn.get("events", [])], ...),
    "evidenceId", "evidence_id",
)
```

账本来自**本回合的工具结果**，而工具结果里的证据条目正是上面第 1 条自铸的。模型引用了什么，就拿自铸的账去对——**闭环整个在 Agent 进程内合上，Java 不签发、不校验、不留痕**。

这不是说校验没用：它能挡住模型凭空编 ID（模型确实编过，实测见 T005 探针记录）。它挡不住的是「Agent 层面的证据本身不可信」。

### 3. 跨回合走的是进程内存，而且会覆盖权威快照

`app/engine/working_set.py:77` 的 `from_snapshot()` 正确地从 `snapshot.evidence` 取证据。但 `app/gateway/service.py:547` 紧接着：

```python
working_set = ConversationWorkingSet.from_snapshot(snapshot)      # ← 读了 snapshot.evidence
previous_working_set = self._working_sets.get(str(session_id))
if previous_working_set is not None:
    ...
    working_set.evidence_refs = list(previous_working_set.evidence_refs)   # ← 又盖掉
```

现在 `snapshot.evidence` 恒为空（`ConversationSnapshotService.java:177` 的 `fillEvidence()` 是空方法体，注释写明 "do not synthesize or infer references here"），所以这行覆盖看起来无害。**但它是个埋着的坑：Java 一旦开始填 snapshot，这行照样会把权威数据盖成进程内存。** P1 必须连它一起改。

### 已有的、设计要保留的防线

不要在重构中把这些拆掉：

| 防线 | 位置 |
|---|---|
| 夹具数据不得升格为招生事实 | `output_validation.py:76-91`（`non_authoritative_admission_fact`） |
| 跨线程证据拒收 | `tools_readonly.py:165-174` |
| `dataVersion` 缺失则整体降级为 `insufficient_data` | `tools_readonly.py:298, 314` |
| 事实结构校验 | `validate_admission_fact` |
| 三重 scope + stateVersion 校验 | `output_validation.py:126-145` |

第三条尤其重要：它意味着「没有数据版本就不算 ok」这个原则已经落地了，P1 是把同样的原则推到证据签发上。

## 二、设计原则

1. **权威性来自签发者，不来自标签。** `sourceLevel: "authoritative"` 只有 Java 签发的记录才配得上。Agent 不得写这个值。
2. **Agent 不能凭本地信息造出一个能通过校验的证据 ID。** 因此 ID 必须由 Java 生成且不可预测，校验必须回到 Java。
3. **区分「从未成立」和「当时正确但已失效」。** 前者是伪造或 bug，必须硬失败；后者是正常的数据演进，应触发重查。这是修订计划 P1 验收里明写的一条。
4. **fail closed 不降级。** 解不回的引用不允许改写成"参考往年分数"这类无引用表述——那正是 P3 要 grep 禁掉的反模式。
5. **不为 P1 重写现有校验器。** `output_validation.py` 的逐条检查保留，只把「账本从哪来」换掉，并加一个失效维度。

## 三、EvidenceRef 权威 schema

`ConversationEvidenceDTO`（`zhiyuan-server/.../model/dto/planning/ConversationEvidenceDTO.java`）**已经定义好 11 个字段**，只是从未被填过：

```
evidenceId, sourceLevel, dataVersion, admissionMode, admissionUnitId,
groupCode, algorithmVersion, stateVersion, scope, observedAt, limitations
```

这个形状基本够用，补三个字段：

| 新增字段 | 类型 | 作用 |
|---|---|---|
| `paramsDigest` | `String` | 查询参数规范化后的 SHA-256。让「同一个问题又问了一遍」可判定，也是失效重查时的比对键 |
| `expiresAt` | `String`（ISO-8601） | 新鲜度上限。到期不等于错，等于"新鲜度未知，必须重查" |
| `sourceSystem` | `String` | 取数来源（如 `gaotu.schoolMajorScoreLine`）。失效判定按 `(来源, 参数摘要)` 比对内容摘要（2026-09-11 勘误前写的是"按来源分别比对上游版本"） |

`paramsDigest` 的规范化规则必须固定下来，否则同一查询会算出不同摘要：**键按字典序排序 → 值转字符串 → 空值与缺失键一律剔除 → UTF-8 → SHA-256 → 取前 32 位十六进制**。这条规则写进 Java 侧一个工具方法，Agent 侧不需要复算（Agent 不参与签发）。

`evidenceId` 格式：`ev_` + ULID。选 ULID 而不是自增或参数哈希，理由有两条——时间有序便于按会话分页和 TTL 清理；不可预测使 Agent 无法拼出一个"看起来对"的 ID 去碰运气。

**不做密码学签名。** 权威性靠「回 Java 查得到」建立，不靠签名验签。加签名要管密钥轮转，收益只在「Java 不可达时仍能离线验证」这一种场景，而那个场景下正确的行为是 fail closed，不是离线放行。

## 四、Java 侧

### 4.1 签发时机

在领域查询返回处登记，**必须与取数在同一次读取内**，否则 `dataVersion` 和 `observedAt` 就是编的。

落点是 `zhiyuan-server/src/main/java/com/ytell/zhiyuan/manager/gaotu/GaotuClient.java`（322 行）的查询方法：

| 方法 | 行 |
|---|---|
| `getBatchList` | `:121` |
| `queryProgramByLimitNum` | `:266` |
| `querySchoolMajorScoreLine` | `:277` |

这三个方法都返回 `ResponseDTO<…>`，签发挂在这层包装上最自然：`ResponseDTO` 已经是"数据 + 元信息"的容器，证据是又一项元信息。**不要在各个 BizService 里分别接**——那会漏，而且漏掉的那个正好就是不带证据的路径。

签发即写入台账，返回 `ConversationEvidenceDTO` 挂在查询结果上，随内部接口回到 Agent。

### 4.2 存储

需要一张表。证据是每次读都产生、按会话堆积的高频数据，不适合塞进 planning workspace state。

```
evidence_ledger
  evidence_id      varchar(40)   PK
  tenant_id        bigint        NOT NULL
  chat_session_id  bigint        NOT NULL   ┐
  thread_id        varchar(64)              ├─ 复合索引 (tenant_id, chat_session_id)
  source_system    varchar(64)   NOT NULL
  params_digest    char(32)      NOT NULL   ─── 索引 (chat_session_id, source_system, params_digest)
  data_version     varchar(64)   NOT NULL   ─── 2026-09-11 起语义为「`data` 子对象的内容摘要」，不是上游字段
  algorithm_version varchar(64)
  admission_mode   varchar(32)
  admission_unit_id varchar(64)
  group_code       varchar(32)
  state_version    int
  scope_json       json
  limitations_json json
  observed_at      datetime      NOT NULL
  expires_at       datetime      NOT NULL   ─── 索引，供清理
```

`data_version` 设 `NOT NULL`：算不出版本就**不签发**，让调用方走 `tools_readonly.py:298` 已有的 `dataVersion_missing` 降级路径。这样"无版本证据"这个类别从根上不存在。

**"算不出版本"在勘误后指什么**（2026-09-11）：原指"上游没给 `dataVersion` 字段"，现指 **`ResponseDTO.data` 为 null 或不可序列化**。列名与 `NOT NULL` 约束都不变，fail-closed 方向也不变，变的只是取值来源：

- 算：`data` 子对象的规范化 JSON（键排序，数组保持上游给的顺序）→ SHA-256 → 前 32 位十六进制。
- 不算：**信封全部排除**。上游信封里的 `timestamp` 每次调用都变，算进去就等于给每条记录发一个一次性版本号，下一次同源查询必然让它 `stale`，系统退化成永久 fail-closed。这条有实测依据，不是洁癖。

除此之外还要多一张 `evidence_source_version` 表存"该 `(来源, 参数摘要)` 最近一次观测到的内容摘要"——**它是 `stale` 能被构造出来的前提**。只有台账一张表时，"当前版本"只能取自台账自身，被核验的记录会同时充当基准，`stale` 在定义上不可达。这是本文 4.2/4.3 之间的一处遗漏，P1a 实现时发现并补上了。它的键**必须**是 `(source_system, params_digest)`：内容摘要天然按参数分，按来源单行就是让所有参数共用一个格子，后一次查询挤掉前一次，全体立刻 `stale`。

清理按 `expires_at` 定时删。保留窗口取多长取决于「历史回合事实要能复验多久」——建议 30 天起步，理由是志愿填报是一个季度内完成的业务，30 天覆盖单次咨询周期，同时不让表无限增长。这个值需要产品侧确认。

### 4.3 失效判定

`observedAt` / `expiresAt` 只解决新鲜度。真正的失效是**同样的查询现在返回了不同的数据**：按 `(source_system, params_digest)` 取最近一次观测到的内容摘要，与记录里的比。

四态，直接对应修订计划的验收要求：

| 状态 | 判定 | 语义 |
|---|---|---|
| `valid` | 记录存在 + 未过期 + 内容摘要与最近观测一致 | 可引用 |
| `stale` | 记录存在 + 内容摘要与最近观测不一致 | **当时正确，现已失效** → 必须重查 |
| `expired` | 记录存在 + 已过 `expiresAt` | 新鲜度未知 → 必须重查 |
| `unknown` | 查不到记录 | **从未成立** → 伪造或 bug |

`stale` 与 `unknown` 的区分是这张表存在的核心理由。没有台账，两者在现象上一模一样。

**勘误后 `stale` 的语义反而更强**（2026-09-11）：原判定是"上游宣称的版本号变了"，依赖上游诚实报版本——而它根本不报；现判定是"我们自己观测到同一查询返回了不同数据"，是事实而非转述。

`valid` 与 `expired` 的分工不变：摘要比对回答"变没变"，`expiresAt` 回答"多久没看了"。两个问题互相独立，所以两个字段都留着。

### 4.4 校验接口

```
POST /internal/evidence/verify
  { "tenantId":…, "chatSessionId":…, "threadId":…, "evidenceIds": [...] }
→ { "results": { "<id>": { "status": "valid|stale|expired|unknown",
                            "sourceSystem":…, "paramsDigest":…,
                            "dataVersion":…, "observedAt":…, "expiresAt":… } } }
```

批量，**一个回合一次调用**（当前回合引用的全部 ID 一起提交）。逐条调用会把 Java 往返次数放大到与事实条数同阶。

返回体带上 `paramsDigest` 和 `sourceSystem`，让 Agent 在 `stale` 时能把"该重查什么"精确告诉模型，而不是只说"证据失效了"。

### 4.5 `fillEvidence()`

`ConversationSnapshotService.java:177` 从空方法体改为：按 `(tenantId, chatSessionId)` 取本会话**当前 `valid`** 的证据集合填入 snapshot。

只放 `valid`：snapshot 是给模型看的"你现在可以引用什么"，把 `stale` / `expired` 放进去等于邀请模型引用失效数据。

注释里那句 "do not synthesize or infer references here" 保留并加强——现在它有了真正的实现来对照，含义从"暂不实现"变成"只透传，不推断"。

## 五、Agent 侧

### 5.1 停止自铸证据（`tools_readonly.py`）

删掉 `:195-203` 和 `:277-296` 两处合成分支。Java 没给证据时，**不造**，走已有的降级路径：`limitations` 追加 `evidence_unavailable`，`:314` 的 `result_status` 逻辑自然落到 `insufficient_data`。

> **2026-09-11 补：这一步必须排在链路打通之后。** 实测查明 Java 签出来的证据在生产链路上一次都到不了模型，三处断链互相独立（scope 没上路 / 信封被 `_data()` 拆掉 / `data` 是数组而归一化只吃 dict），详见 `2026-09-11-P1a证据到不了Agent的三处断链.md`。**先删自铸分支**会让 `admission.get_history` 从"返回自铸证据"变成"返回无证据"——两种都不对，但后者会让 `fact` 输出直接整轮 fail closed，把一个静默错误放大成全线挂。顺序：接通 scope → 保住信封 → 对齐形状 → 才删。

配一条单测：任何工具结果里出现 `sourceLevel == "authoritative"` 而 `evidenceId` 不以 `ev_` 开头，即失败。这条测试是防回归的关键——自铸证据是个"看起来能跑"的失败模式，很容易被后来的人以"补个默认值"的名义加回来。

再配一条（2026-09-11 新增，**它正是现在缺的那条**）：用**真实信封形状**喂 `InternalClientBackend.get_history`，断言产出能被 `_admission_envelope` 吃下且 `evidence` 未丢。现有 admission 单测全部用手写 `Backend` 桩返回消费者期望的形状，于是三处断链一处也没照出来。

### 5.2 跨回合证据改走 snapshot（`service.py:547`）

```python
working_set.evidence_refs = list(previous_working_set.evidence_refs)   # 现状：进程内存盖掉权威
```

改为：**以 snapshot 为准，进程内存只做交集**。即 `from_snapshot()` 拿到的权威集合是上界，进程内存里有而 snapshot 里没有的一律丢弃（那说明 Java 已判定它不再 `valid`）。

其余四行（`candidate_entities` / `admission_facts` / `artifact_refs`）不在 P1 范围，不动。

### 5.3 校验从"对本回合账本"升级为"对 Java 台账"（`output_validation.py`）

保留 `:118-155` 现有逐条检查不变，在其**之前**插入一次批量核验：把 `output.evidence_refs` 的全部 ID 提交 `/internal/evidence/verify`，按返回状态分流（见第六章）。

`evidence_ledger` 参数保留，语义收窄为「本回合工具结果的自洽性检查」；权威性由新的核验步骤负责。两层都要过。

## 六、fail-closed 边界

这是整个设计里最容易做错的地方，所以逐态写死：

| 核验状态 | Gateway 行为 | 理由 |
|---|---|---|
| 全部 `valid` | 继续现有校验链 | — |
| 任一 `unknown` | **硬失败**，`OutputContractError("evidence_not_authoritative", <id>)`，整轮作废，不重试 | 台账里没有就是没发生过。重试只会让模型再编一遍 |
| 任一 `stale` / `expired`，且被 `fact` 类输出引用 | **拒绝本轮输出**，把失效 ID + `sourceSystem` + `paramsDigest` 回注给模型，要求重查后重新作答；重查上限 **1 次**，仍失败则整轮 fail closed | 失效是正常数据演进，值得给一次重查机会；但不能无限循环 |
| 任一 `stale` / `expired`，仅被非 `fact` 输出引用 | 剥离该引用，输出继续 | 非事实表述不承载招生数据，无需重查 |
| Java 不可达 | **硬失败**，不放行 | 验证不了就不能盖权威章。这里放行等于把 fail-closed 改成 fail-open |

最后一条要写进注释并配单测。「依赖不可用时放宽校验」是个非常自然的手滑，而它恰好摧毁整个设计的目的。

重查上限选 1 次而不是 P3 的 5 轮：证据失效重查是确定性操作（同样参数再查一遍），一次不成说明是系统问题，不是模型问题，再试无益。

## 八、验收

按 `tasks/README.md` 规则 4 写——每条都能证伪，零值都有对照：

**P1a**（已于 2026-09-11 由设计会话独立重跑验收，四态全部真实构造出来并正确区分；判定见 `tasks/P1a-evidence-ledger/REVIEW.md`）
- 同一查询参数连续两次 → 两个不同的 `evidenceId`，相同的 `paramsDigest`。（反向对照：改一个参数值 → `paramsDigest` 必须变）
- 版本取不到时 → **不产生台账记录**，查询结果带 `dataVersion_missing`。（对照：能取到时必须产生记录）
- 人工把一条记录的 `data_version` 改成与当前观测不一致 → `verify` 返回 `stale`，不是 `unknown`。（对照：删掉记录 → 必须返回 `unknown`）
- 把 `expires_at` 改到过去 → 返回 `expired`。

> **这四条的验收是在替身上做的**（`zhiyuan-server/scripts/evidence_fake_upstream.py`），因此它们证明的是"代码按设计工作"，不是"设计与真实上游相符"。后者实测为假，见本文开头的勘误。**四条验收本身仍然有效**——换成内容摘要后逐条仍可跑，只是第二条的"版本取不到"从"上游没给字段"变成"`data` 为 null"。

**P1b**
- **（勘误新增，且必须带对照）响应内容的稳定性**：`getBatchList` / `querySchoolMajorScoreLine` / `queryProgramByLimitNum` 三个接口各用**同一组参数连调两次**，`data` 摘要必须相同；**对照**：故意换一个参数（如 `year` 2025→2024），摘要必须不同。没有这条对照，"两次相同"也可能是摘要算法坏了恒返回同一个值——那正是 `mcpCalls` 恒为 `[]` 的翻版（`tasks/README.md` 规则 4）。若某接口两次不同，**先贴原始 diff 定位是哪个字段在动**，再决定排除该字段还是换机制；不要直接排除，排掉的可能正是真实变化。
- **（勘误新增）版本表的键**：同一 `source_system`、两组不同参数各签一条证据，第二条签发后第一条必须仍为 `valid`。（对照：把键退回按 `source_system` 单行，第一条必然变 `stale`——这条对照能证明键确实起作用了）
- `fillEvidence()` 只放 `valid`：构造一条 `stale` 记录，断言它**不出现**在 snapshot 里。（对照：同会话另一条 `valid` 记录必须出现）
- 单测：任何工具结果中 `sourceLevel == "authoritative"` 且 `evidenceId` 不以 `ev_` 开头 → 失败。
- 单测：进程内存里有一条 snapshot 中不存在的 `evidence_ref` → 回合开始后它必须已被丢弃。

**P1c**
- 模型引用一个不存在的 ID → 整轮 `evidence_not_authoritative`，且**用户侧没有任何自然语言兜底输出**。（这条是 fail-closed 的实质验收，光看错误码不够，要断言输出为空）
- 引用一条 `stale` 证据 → 恰好触发 1 次重查；把上游版本固定成永远不一致 → 第二次仍失败后整轮 fail closed，**不是无限重试**。
- 停掉 Java 或让 verify 返回 5xx → 整轮硬失败。（这条必须真的把依赖打断来测，不能用 mock 断言"如果不可达就失败"——那只测了 mock）
- 历史回合复验：第 3 回合产出的事实，在第 7 回合能重新核验，且能区分 `stale` 与 `unknown`。

## 九、不做

- 不做证据的密码学签名（理由见第三章末）。
- 不做多实例共享台账缓存。台账在 DB，Agent 每回合查一次，够了。
- 不把 `admission_facts` / `candidate_entities` / `artifact_refs` 的跨回合来源一起改。它们有各自的正确性论证，混进来会让 P1 无法收敛。
- 不重写 `output_validation.py` 现有的逐条检查。
- 不在 Java 不可达时提供任何降级放行开关。
