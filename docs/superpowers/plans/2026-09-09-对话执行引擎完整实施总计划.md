# 对话执行引擎完整实施总计划

> 日期：2026 年 9 月 9 日
> 目标：围绕最新产品路线，形成可理解、可执行、可验证、可本地部署的高考志愿咨询对话系统。

## 一、总体原则

1. Codex/模型负责用户交互、上下文理解、指代解析、澄清、确认判断、任务分派、工具选择和 Proposal 草案。
2. Gateway 负责上下文投影、协议校验、Evidence/版本/引用校验、结果合成和能力边界，不通过关键词重判自然语言意图。
3. MCP 负责工具暴露、参数协议和业务结果传输，不承担最终事实权威。
4. Java/后端负责权威事实、Proposal/Pending 持久化、版本、CAS、事务和最终状态。
5. 历史分数、招生事实、录取率、风险档位严格分层；缺少权威字段时不得补全或升级。

## 三、核心用户流程边界

| 流程 | 模型职责 | Gateway 职责 | Java 职责 |
|---|---|---|---|
| 探索候选 | 理解偏好、选择工具 | 校验工具和上下文 | 返回权威候选 |
| 查询历史分数 | 补全参数、选择学校 | 校验参数和 Evidence | 返回历史数据 |
| 生成方案 | 组织 Proposal 草案 | 校验引用和范围 | 保存权威 Pending |
| 用户确认 | 输出 confirm action | 校验 Proposal/version | CAS 和事务执行 |
| 用户取消 | 输出 cancel action | 校验 Proposal/version | 取消 Pending |
| 约束变化 | 解释影响、生成新草案 | 失效旧引用 | 更新权威状态 |

## 六、完成标准

- 用户可以自然表达、追问、指代、改口、确认和取消。
- 模型可以自主完成任务理解和工具编排，Gateway 不通过关键词接管流转。
- 所有招生事实均可追溯到权威 Evidence。
- 非权威或不完整数据不会被升级成招生事实。
- 写入必须经过结构化动作、Proposal/version 校验和 Java CAS。
- 本地可启动完整链路并进行真实用户会话。
- 每个核心用户流程都有可重复回归和失败报告。
