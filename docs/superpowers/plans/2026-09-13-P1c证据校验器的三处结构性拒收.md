# P1c：证据校验器会结构性拒收 Java 权威证据（三处）

> 日期：2026-09-13
> 依据：对 `app/gateway/output_validation.py`、`app/gateway/service.py` 的逐行核查
> 触发：为裁决 P1a 跟进项 4（`threadId` 严松不一）而查 thread 的语义，顺藤查出三处更严重的
> 性质：设计结论。直接改写 P1c 的范围，并回答了一个悬着的口径问题

---

## 零、一句话

**P1b 把证据变成真的之后，`output_validation.py` 会把它们全部拒收。** 三处独立的检查，每一处都足以单独让 `fact` 回合全线 fail closed；其中一处（第 5 条）**直接否掉 P1 的头号验收目标**。

三处今天都看不出来，原因完全一致：**证据现在是每回合自铸的，带的永远是当前值，所以这三个检查恒真。** 它们不是"已经验过的安全网"，是"还没通电的安全网"，而通电方向是反的。

编号接着 `2026-09-11-P1a证据到不了Agent的三处断链.md` 往下排。

## 一、断链 4：snapshot 里的证据进不了校验器的账本

`app/gateway/service.py:770-781`：

```python
evidence_ledger = _by_id(
    _collect_records(
        [
            turn.get("evidenceLedger", []),
            turn.get("events", []),
        ] if isinstance(turn, Mapping) else [],
        "evidenceLedger", "evidence", "evidenceRefs", "evidence_refs",
    ),
    "evidenceId", "evidence_id",
)
```

账本**只**来自本回合的 codex turn events。`working_set.evidence_refs`——也就是 P1b-3 要用 `fillEvidence()` 从 Java 台账填进 snapshot 的那批权威证据——**一条都不在里面**。

于是 `output_validation.py:126-127`：

```python
entry = evidence_ledger.get(evidence_id)
if entry is None:
    raise OutputContractError("evidence_not_found", evidence_id)
```

**P1b-3 把权威证据摆到模型面前请它引用，模型引用了，校验器立刻以"查无此证"整轮作废。**

与断链 2 同型：生产者往一个地方放，消费者从另一个地方取。断链 2 是 `_data()` 把信封拆了，这一条是账本压根没接 snapshot 这一路。

## 二、断链 5：`stateVersion` 等值检查让跨回合引用在定义上不可能

`app/gateway/output_validation.py:137-146`：

```python
entry_state = _field(entry, "stateVersion", "state_version")
if entry_state not in (None, ""):
    parsed_state = int(entry_state)
    if parsed_state != snapshot.snapshot_version:
        raise OutputContractError("stale_state", evidence_id)
if reference.state_version is not None and reference.state_version != snapshot.snapshot_version:
    raise OutputContractError("stale_state", evidence_id)
```

两个条件都要求 **等于当前 `snapshot_version`**。

- `ConversationEvidenceDTO` 有 `stateVersion` 字段，`EvidenceLedgerService.sign()` 记的是**签发那一刻**的值。
- `snapshot_version` 取自 `workspace.getVersion()`，**规划工作区每发生一次写入就推进**。

所以：第 3 回合签发的证据（`stateVersion=5`），只要第 4 回合改了一次方案（`snapshot_version→6`），到第 7 回合被引用时必然 `stale_state`，整轮 fail closed。

### 为什么这一条最严重

`2026-09-10-对话执行引擎推进计划修订.md` 第三章 P1 验收原文：

> 历史回合的事实可被重新校验，能明确区分"当时正确但现已失效"与"从未成立"。

设计文档第八章 P1c 验收原文：

> 历史回合复验：第 3 回合产出的事实，在第 7 回合能重新核验，且能区分 `stale` 与 `unknown`。

**这正是 P1 存在的理由。** 而 `:143` 这一行让它在定义上不可能——不是"有 bug 导致偶尔失败"，是**只要中间发生过任何一次工作区写入就必然失败**。

### 语义上这一条也是错的

`stale_state` 在这里被用来表达两件不同的事：

| 真正要问的 | 正确的判定依据 |
|---|---|
| 这条证据引用的**上游数据**过期了吗 | P1a 的四态核验（内容摘要比对），**这才是 `stale`** |
| 这条证据是在**旧的工作区状态**下签的吗 | 与证据是否可信**无关** |

第二个问题的答案是"是的，那又怎样"。用户第 3 回合查到的浙江某校投档线，不会因为第 4 回合往方案里加了一所学校就变得不可引用。**工作区版本推进的是"我们的方案"，不是"招生数据"。** 把两者绑死，等于宣布"用户每改一次方案，之前查过的所有事实全部作废"。

`artifact_refs` 那边（`:168-171`）用同一个检查是**对的**——产物确实绑定在产生它的那个工作区版本上。**证据不是产物。**

## 三、断链 6：`threadId` 等值检查 + thread 是进程内存里的易失值

### 事实

`app/gateway/service.py:372`：

```python
self._threads: dict[str, str] = {}
```

纯进程内 dict，`__init__` 里初始化为空，**从不持久化、从不恢复**（全文 grep 只有 `:372` / `:654` / `:663` 三处）。

`:654-663`：

```python
thread_id = self._threads.get(str(session_id))
if not thread_id:
    created = await self.codex.create_thread(...)
    thread_id = str(created.get("thread", {}).get("id") or "")
    self._threads[str(session_id)] = thread_id
```

于是 thread 的真实语义是：**一个 session 一个 codex 会话线程，懒创建，进程级缓存。** 它不是业务概念，是 codex harness 的实现细节。

**Gateway 一重启，映射表空了，同一个 session 会拿到一个全新的 thread。**

### 后果

`app/gateway/output_validation.py:131-133`（`strict_scope=True` 在 `service.py:809`，生产唯一调用点）：

```python
entry_thread = _scoped_field(entry, "threadId", "thread_id")
if (strict_scope and thread_id and entry_thread in (None, "")) or (thread_id and entry_thread not in (None, "", thread_id)):
    raise OutputContractError("evidence_scope_violation", evidence_id)
```

**一次 Gateway 重启 → 所有在世会话的存量证据全部 `evidence_scope_violation` → 在 fail-closed 规则下每个 `fact` 回合全线挂**，直到用户把所有东西重查一遍。

一次普通发版就能触发。

### 两条路都堵死

P1b-3 的 `fillEvidence()` 往 snapshot 里填证据时，`scope.threadId` 填什么都不对：

| 填法 | 结果 |
|---|---|
| 填台账里记的（签发时的 thread） | 重启后 `entry_thread not in (None,"",thread_id)` → 拒收 |
| 不填 | `strict_scope and thread_id and entry_thread in (None,"")` → 拒收 |

**所以这不是"P1b-3 该填哪个值"的问题，是这个检查本身对证据不适用。**

## 四、裁决：thread 不是证据的隔离边界（P1a 跟进项 4 结案）

P1a 复核留下的问题是：`EvidenceLedgerService.verifyOne()` `:167-170` 只在双方 `threadId` 都非空时才校验线程，而 Agent 侧 `strict_scope=True` 要求必须存在——**Java 比 Agent 松，要不要统一到严的那边？**

**答案是：统一到松的那边，并且写进注释。** 依据是上面第三节的事实，不是偏好：

1. **thread 与 session 是 1:1 的**，不存在"同一会话的两个线程"，所以"跨线程泄露"这个威胁在当前架构下不存在。
2. **thread_id 是进程易失的**，把它当隔离边界，边界会在每次发版时自己消失又重建。**一个会随进程重启而改变的标识符，不能承载安全语义。**
3. 真正的隔离边界是 `(tenantId, chatSessionId)`，Java 侧**一直强制**（`verifyOne()` `:163-166`，P1a 第 8 步验收已证明换会话必 `unknown`）。

具体动作：

- **Java 侧 `verifyOne()` 保持现状**，在 `:167-170` 加注释写明"线程不是证据的隔离边界，见本文；隔离由 `(tenantId, chatSessionId)` 承担"。
- **Agent 侧 `output_validation.py:131-133` 的证据线程检查取消**（`:175-176` 的 artifact 线程检查**保留**，产物确实是线程内的）。
- `ConversationEvidenceDTO.scope.threadId` **字段保留**，作为审计信息记录"这条证据是在哪个线程下签的"，但**不参与准入判定**。记录与判定分开，这是两件事。

## 五、为什么三处今天都看不见

同一个原因，一句话：**证据现在是每回合自铸的。**

`tools_readonly.py:277-296` 每回合现造，`stateVersion` 填 `self.current_state_version`（= 当前），`scope.threadId` 填 `self.binding.thread_id`（= 当前），`evidenceId` 就在本回合的 turn events 里。于是：

| 检查 | 今天 | P1b 之后 |
|---|---|---|
| 账本里找得到吗（断链 4） | 恒真——本回合刚造的 | 假——来自 snapshot |
| `stateVersion` 等于当前吗（断链 5） | 恒真——填的就是当前 | 假——签发时的旧值 |
| `threadId` 等于当前吗（断链 6） | 恒真——填的就是当前 | 重启后为假 |

**三个检查今天全部恒真，所以三条代码路径从来没有真正执行过判定。**

这和 `mcpCalls` 恒为 `[]` 是同一类错误的两面：那次是仪表没通电、读数恒定，被当成"测到了零"；这次是校验器没通电、判定恒过，被当成"已经验证过的安全网"。

**恒真的检查和坏掉的检查，在测试里长得一模一样。**

### 由此产生的一条新规则（已补进 `tasks/README.md`）

> **迁移设计时，要专门去找"现在永远通过"的检查。** 它们不是已经生效的防线，是还没接上被检查对象的空转防线，而接上之后的方向可能是反的。判别办法：问"有没有一种输入能让这个检查失败？"——如果在当前代码里构造不出来，这个检查就还没有被验证过，不管它写得多严。

这条与已有的两条并列：替身不能替外部系统作证（`plans/2026-09-11-P1a上游版本契约实测与dataVersion改设计.md`）、桩的形状要从生产者那一侧取（`plans/2026-09-11-P1a证据到不了Agent的三处断链.md`）。三条都是同一个母题的分支：**验证的对象和真实的对象不是一回事。**

## 六、P1c 的范围因此扩大

原 P1c（设计文档 5.3 + 第六章）是"在现有逐条检查**之前**插入一次批量核验，按四态分流"。现在要多做三件事，**且它们必须排在批量核验接入之前**——否则接上去的第一件事就是全线拒收：

| # | 动作 | 文件 |
|---|---|---|
| 1 | 账本合并 snapshot 的权威证据，不只本回合 turn events | `service.py:770-781` |
| 2 | 删掉证据的 `stateVersion` 等值检查（**artifact 的保留**） | `output_validation.py:137-146` |
| 3 | 删掉证据的 `threadId` 等值检查（**artifact 的保留**） | `output_validation.py:131-133` |

第 2、3 条是**删检查**，方向上是放松，必须说清楚为什么这不是把 fail-closed 改成 fail-open：

> **它们删掉之后，"这条证据还作不作数"这个问题由 P1a 的四态核验回答，而那是一个真正会失败的判定**（`stale` / `expired` / `unknown` 都已在 P1a 验收里被真实构造出来）。删掉的是两个**恒真因而从未做过判定**的检查，换上一个会真的说"不"的。**防线是变强了，不是变弱了。**
>
> 反过来说，如果先接四态核验、不删这两条，结果是**两道门都关着**，`fact` 回合永远出不去——那不是更安全，那是功能不存在。

### 验收要带的对照（否则验不出上面这句话是真的）

- 删掉 `stateVersion` 检查后，**构造一条真的失效的证据**（改内容摘要），断言它仍然被拒——证明拒收能力来自四态核验而不是那个检查。
- 删掉 `threadId` 检查后，**换一个 session** 引用同一 ID，断言仍是 `unknown`——证明会话级隔离没被一起删掉。
- 跨回合正例：第 3 回合产出证据 → 第 4 回合做一次工作区写入让 `snapshot_version` 推进 → 第 7 回合引用它 → **必须通过**。这一条是 P1 头号目标的直接验收，**在当前代码上必然失败**，可以先写成 xfail 用来确认它确实失败，再修到通过。
