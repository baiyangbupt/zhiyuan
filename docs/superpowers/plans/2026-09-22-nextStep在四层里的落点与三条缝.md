# `nextStep` 在新架构四层里的落点，与三条缝

> 日期：2026-09-22。来源：一次架构问询（"`nextStep` 的系统设定与 codex 的上下文轮转、
> 技能注入是不是整合的？它是历史版本里的东西"）。**结论：契约层整合、运行时与用户可见层不整合。**
> 本文只记事实与选项，**未做任何裁决**。

---

## 一、四个层各自的落点（逐处核过）

| 层 | `nextStep` 的处境 | 证据 |
|---|---|---|
| **模型可见契约** | **整合，但三处重复** | `TURN_OUTPUT_SCHEMA`（结构：required + `["string","null"]`）；`skills/codex/developer_instructions.md`（语义："没有下一步时填 `null`"）；**5 个 SKILL.md**（`admission-fact-analysis` / `plan-final-review` / `candidate-recommendation` 等，逐技能指导） |
| **工具契约** | **不在里面** | `app/engine/tool_orchestration.py` 全文件 0 命中——`render_tool_contracts()` 不讲输出字段 |
| **网关加工** | 整合 | `app/engine/result_synthesis.py`（工具失败时补/降级）、`app/engine/turn_trace.py`（进 trace，量具读它） |
| **Java 业务状态** | **完全不知道它** | `zhiyuan-server` 全仓 `nextStep`/`next_step` **0 命中** → 不进快照、不进消息表、跨回合无状态 |
| **前端** | **不展示** | `zhiyuan-web` 0 命中；compat 终态帧的正文只取 `reply`（`message`），字段不在帧里 → **模型写了，用户看不到** |

跨回合的"下一步"实际由 **codex 原生 thread 的记忆**兜着（模型上一轮说过的话在 rollout 里）。
**thread 一旦重建（A7 的 rollout 丢失分支）或换会话，它就丢了**——而这正是新架构里
本该由状态承担的那部分。

## 二、三条缝

1. **同类概念没收敛，四处各写各的**：
   - `nextStep`（本文主角）；
   - `clarification` + 原生问答卡（A4：结构化、可交互、有 expiry、能跨 resync）；
   - `proposalRef` / `conversationAction`（写流程的"下一步"）；
   - **`app/engine/execution_plan.py` 的 `userVisibleNextStep`——每回合注入模型的"下一步"提示**
     （`execution_plan.py:46/55/84/100` 算出，`service.py:952-961` 把整个执行计划骨架
     作为 context item 塞进模型输入）。
     > **勘误（2026-09-22 当天）**：本文初版写它是"零消费者的死字段"，**错了**。
     > 它在 Python 侧确实没有消费者，但它的消费者是**模型**——所以它不是死代码，
     > 而是**第二条对模型说的"下一步"**（第一条是契约里的 `nextStep`，那条是**模型说给我们**的）。
     > 两者之间**没有任何一致性检查**：我们算一条告诉它，又要求它产出一条，谁也不校谁。

2. **职责错位（实测）**：P2c 那次跑里，模型把"请回复确认是否删除 plan-1 的第 3 个条目"
   写在 `nextStep` 里——那本该走原生卡（需要用户做一个选择）。因为前端不渲染 `nextStep`，
   **用户在界面上其实没被告知**，只有 `message` 的散文里说了。

3. **技能层是"重复"而不是"分层"**：同一套字段语义同时写在 developer instructions、
   5 个 SKILL.md 与 schema 三处。改一处漏两处的漂移风险，与 2026-09-22 那起
   `artifactType` 事故（契约是 Literal、schema 只写 string）同源。

### 补测（2026-09-22 当天）：两条"下一步"到底有多不一样

从最近 60 条 rollout 里把**注入的 `userVisibleNextStep`** 与**模型产出的 `nextStep`** 都取出来逐条比：

```text
58/60  两者不同
 2/60  没解析出模型输出（提取失败，不计入）
 0/60  逐字相同
```

抽两条看差异的**性质**——不是矛盾，是**冗余且详略不同**：

```text
注入（我们算的，来自执行计划骨架）：向用户澄清缺失信息：province、score、rank
产出（模型写的，领域相关）        ：用户补齐省份、选科组合、年份后，下一轮按 admission-fact-analysis 走：
                                   先列北大在该省的招生单元与各单元选考科目要求，逐条判定可报/不可报
```

也就是说：**我们每回合给模型一个"下一步"，模型每回合又回一个"下一步"，两者的详略与措辞都不同、
互不校验**。这为第三节那条"谁是权威"的裁决提供了实测依据（不再只是设计上的重复）。

> 提取过程中的两次自我更正，一并留痕：初版说这个字段是"零消费者的死字段"（**错**，它注入模型）；
> 中间又一度说两条"打架"（**证据不足**，当时那次统计的提取条件写错、根本没取到模型输出）。
> 现在这条是**逐条核对过提取结果**才写的。

## 三、选项（属设计裁决，本文不选）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A：接线成一等状态** | 前端渲染 + Java 快照/工作集持久化 | 两个仓库各改一处；收益是跨回合、跨 thread 重建都不丢 |
| **B：收敛到原生卡** | "需要用户做选择"一律走 A4 的卡；`nextStep` 只留信息性提示（那就该并回 `message`，字段可退场） | 中；与 A4/A5 已有的状态、expiry、resync 一致 |
| **C：降级为量具字段** | 明确它**不面向用户**，只作评估/可观测信号，写进契约文档 | 最小；但冗余仍在 |

**执行侧的倾向（供裁决参考，含当天勘误）**：B + C 的组合——需要用户回应的事走卡
（A4/A5 已经建好了状态机），`nextStep` 在接线之前至少明确标成量具字段，免得下一个人以为
用户在界面上能看到它。

初版还建议"先删掉 `user_visible_next_step` 这个死字段"，**该建议基于错误前提，撤回**
（见第二节勘误：它注入模型，不是死代码）。对应地，多出一条要一并裁决的：
**（i）`nextStep`（模型说给我们）与（ii）`userVisibleNextStep`（我们说给模型）谁是权威**——
现在是两条各说各的、互不校验。选项同属上表（A/B/C）：接线成状态时应当**只留一条**。
