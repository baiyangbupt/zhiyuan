验收第 6 条要三个上游接口各做「同参数连调两次摘要相同」+「换参数摘要不同」。结果：

后两条为什么判"未验证"而不是"通过"，实现方自己说清楚了：**空数组的摘要是个常量**（`4f53cda…`，两个接口上各自独立出现、值一致），于是"两次相同"必然成立、"换参数不同"必然不成立——**这条对照在空数据上不具备判别力。**

**这正是本轮反复在查的那件事，而且是实现方自己识别出来的。** 对着两问过一遍：

> 1. 有没有一种输入能让这个检查失败？——在空数据上，**没有**。
> 2. 能让它失败的输入正是我们想防的行为吗？——不适用，第 1 问已经否了。

**它完全可以报"两次摘要相同 ✅"然后收工，报告会好看得多。** 它没有，而且明确拒绝用 `evidence_fake_upstream.py` 补位。这条守的是这个仓库用 P1a 换来的规矩：**替身能证明代码按设计工作，不能证明设计与外部世界相符。**

**所以摘要机制的真实证据强度要如实记账**：

- **摘要函数本身是确定的**——这条证据充分。验收 1 做了**变异验证**（去掉键排序、给数组排序，确认两条断言真的会 FAIL，再还原），验收 5 做了**键对照**（把 WHERE 退回单键，先签的证据由 `valid` 变 `stale`）。两处都主动构造了失败，不是只看绿灯。
- **真实上游内容在非空数据上稳定**——**只有 1/3 个接口证明了。** 另两个接口不是"验过了没问题"，是**没验过**。

两者是不同的断言，报告第四节末尾那句说明把这一点分得很清楚。

## 四、它顺手堵了一个"改了等于没改"的洞

偏离第 2 条，**任务书没写，但必须做**：`verifyOne` 的批量核验缓存原本按 `sourceSystem` 汇总。版本表键改成「来源 + 参数」之后，缓存键不跟着改的话——

> 同一批核验里，第二条记录会拿到第一条的当前版本。**版本表键改了，但被缓存架空。**

而且**单测照样全绿**，因为单测一批里通常只有一个来源。

已独立确认堵上了（`EvidenceLedgerService.java:181-188`）：

```java
String cacheKey = entity.getSourceSystem() + " " + entity.getParamsDigest();
```

**这是本任务里实现方最有含量的一笔。** 它不是执行指令，是发现了一个"照任务书做完、测试全绿、而改动实际不生效"的路径——正是这轮在系统性排查的那个形状。

偏离第 3 条（把 `evidence_fake_upstream.py` 里 `/__control/version` 和 `payload["dataVersion"]` 注入删掉）**同样是主动的、同样正确**：那个替身在伪造一个**上游根本不存在的契约**，P1a 的误判正源于此。留着它，这次端到端会在假契约上再次通过。**它认出了这是同一个陷阱的第二次。**

## 六、复核中查出的新隐患：V15 之后所有旧证据会判 `stale`，而 `unknown` 永远产不出来

**不是 P1b-1 的缺陷**，但 P1b-1 让它第一次变得可达且有后果，因此记在这里。

事实链（均独立核实）：

1. `V15__evidence_source_version_params.sql` 是 **`DROP TABLE` + 重建**（主键改 `(source_system, params_digest)`）。
2. 该表由 `V14__evidence_ledger.sql` 首建，**没有任何外键**；`evidence_ledger` 存的是签发那一刻的快照拷贝，与版本表**无行级绑定**。所以 DROP **不会**破坏已签发证据的行本身。
3. 但 `currentDataVersion()`（`EvidenceLedgerService.java:218-229`）**查不到记录时返回空串 `""`**，于是比对必然不等，`verifyOne` 落到 **`STATUS_STALE`**。

**后果**：V15 跑完，在每个 `(source_system, params_digest)` 组合被下一次真实取数重新观测之前，**所有已签发的旧证据核验一律报 `stale`**。fail-closed 之下，等于全部作废。

**今天安全**，条件明确：证据台账**从未进过产线**（唯一会签发的调用方是 inner 下的 debug controller）。**把这个条件写下来，是因为它一旦不成立，这条就从"无害"变成"一次迁移让全部在世证据失效"。**

### 但真正的问题不是 DROP，是"查不到"和"变了"共用了一个状态

四态核验有 `valid` / `stale` / `expired` / **`unknown`**。**`unknown` 恰恰就是为这种情形准备的**，而 `currentDataVersion()` 返回空串把这条路绕过去了：

| 真正要问的 | 该给的答案 | 现在给的 |
|---|---|---|
| 当前版本和你签的那份不一样 | `stale` | `stale` ✅ |
| **我根本没有当前版本的记录** | **`unknown`** | **`stale`** ❌ |

**又是同一个形状**：两个不同的问题共用一个答案槽，其中一个把另一个吃掉了——与断链 5（`stateVersion` 把"方案版本"当"招生数据版本"）、成因 4（`executionStatus` 把"工具跑成功了吗"当"诉求满足了吗"）**同型，这是第三次**。

代价是诊断被污染：版本表被清空之后，系统报出来的是"上游数据变了"，而真相是"我丢了自己的版本记录"。**两者的处置完全不同**，而现在分不出来。

**归 P1c-2**（四态核验接入），不单开任务。

## 七、摘要算法：SHA-256 截断到 128 位

`MessageDigest.getInstance("SHA-256")`，取十六进制串前 32 字符（`DIGEST_HEX_LENGTH = 32`）= **128 bit**。外观与 MD5 全串同长，**算法不是 MD5**，这一点核过了。

**这个用法没问题**，写一句是防止下一个人误读：它是**内容版本比对**，不是防篡改绑定。128 位截断的生日界约 2⁶⁴，对"上游内容变没变"这种**非对抗**判定绰绰有余。**但不要在没重新论证的情况下，把它当成密码学意义上的完整性证明去用。**
