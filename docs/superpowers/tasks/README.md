# 任务分派与回收协议

> 适用范围：设计会话（Claude Opus 5，负责设计与评审）向实现会话（DeepSeek 等，负责执行）分派任务的全过程。
> 本文是该流程的唯一权威。任务书与本文冲突时以本文为准。

---

## 一、这个协议解决什么问题

T001 / T002 两个任务在协议建立前执行，暴露了三个真实缺陷：

1. **结果靠聊天转述回流。** 实现方把结论打在对话里，人再粘贴给设计会话。中间丢了状态词、丢了文件清单、丢了验收原始输出。设计会话拿到的是二手摘要，无法复核。
2. **全量测试的预存在失败没有基线。** T002 跑完单测有 2 项失败，实现方无从判断是不是自己弄坏的，设计会话也要重新查一遍才敢下结论。
3. **实现方的事实与推断混在一起。** T001 做得对（只列事实、不给建议），但这靠的是任务书里临时写了一句，不是制度。

因此本协议的核心不是模板好看，而是三件事：**报告落成文件、验收贴原始输出、事实与推断分离。**

## 二、目录约定

```
docs/superpowers/tasks/
├── README.md                  ← 本文，协议
├── LEDGER.md                  ← 台账，一行一任务，唯一状态来源
├── _templates/
│   ├── TASK.md                ← 任务书模板
│   └── REPORT.md              ← 报告模板
└── T0NN-<ascii-slug>/
    ├── TASK.md                ← 设计会话写，派发前冻结
    ├── REPORT.md              ← 实现会话写，路径由任务书写死
    └── REVIEW.md              ← 设计会话写，回收判定
```

任务 ID 从 `T001` 起单调递增，永不复用。目录 slug 用 ASCII 短横线，标题写中文放在 `TASK.md` 里。

## 三、生命周期

| 步 | 动作 | 谁做 | 产物 |
|---|---|---|---|
| 1 | 建目录、写任务书、跑派发前自检 | 设计会话 | `TASK.md` |
| 2 | 登台账，状态 `DISPATCHED` | 设计会话 | `LEDGER.md` 一行 |
| 3 | 执行，只读 `TASK.md`，不依赖任何会话上下文 | 实现会话 | 代码改动 |
| 4 | 写报告到任务书指定路径 | 实现会话 | `REPORT.md` |
| 5 | 复核：逐条重跑验收、核对文件清单、判定 | 设计会话 | `REVIEW.md` |
| 6 | 更新台账终态；通过则由设计会话统一提交 | 设计会话 | `LEDGER.md` |

**实现会话在第 3 步只能看 `TASK.md`。** 任务书必须自足：背景、已核实的环境事实、步骤、陷阱、验收、边界、报告路径，全部写在里面。实现方需要回头问才能开工，说明任务书没写够，这是设计会话的责任。

## 四、状态词

### 实现方声明（写在 `REPORT.md` 的 `status`）

| 状态 | 含义 |
|---|---|
| `DONE` | 验收全过，无偏离 |
| `DONE_WITH_CONCERNS` | 做完了但有偏离或存疑项，必须逐条说明偏离内容与判断依据 |
| `BLOCKED` | 被挡住，附原始报错，不猜原因 |
| `NEEDS_CONTEXT` | 任务书信息不足，说明缺什么 |

实现方**不得**自评通过与否。`DONE` 只是"我认为验收过了"，不是结论。

### 设计方判定（写在 `REVIEW.md` 的 `verdict`）

| 判定 | 含义 |
|---|---|
| `ACCEPTED` | 复核通过，改动可提交 |
| `ACCEPTED_WITH_FOLLOWUP` | 主体通过，遗留项另开任务，ID 写进 `REVIEW.md` |
| `REJECTED` | 不通过，说明具体哪一条不成立，退回或重开任务 |
| `SUPERSEDED` | 任务前提已被新事实推翻，不再执行 |

**`BLOCKED` 不等于失败。** T001 报 `BLOCKED`（没采到断流现场），但它的对照数据直接推翻了 P0 的诊断前提，判定为 `ACCEPTED`。判定看的是产出是否可信、是否推进了认知，不是任务目标是否达成。

## 五、四条硬规则

### 规则 1：报告是文件，不是聊天消息

任务书必须在「报告」一节写死绝对路径，形如：

```
把报告写到 /root/dev/zhiyuan/docs/superpowers/tasks/T0NN-<slug>/REPORT.md
```

回收动作就是读这个文件。聊天里的摘要只作提示，不作依据。**报告文件不存在 = 任务未交付**，无论对话里说了什么。

### 规则 2：验收贴原始输出

每条验收命令必须在报告里贴出**未经编辑的原始输出**。"全部通过"、"符合预期"这类转述一律不接受。命令没跑就写没跑，不要写预期结果。

### 规则 3：事实与推断分离

报告只写观察到的事实：改了什么、命令输出是什么、报错原文是什么。

**不写修复建议、不写下一步计划、不写根因推测。** 定性和方案属于设计会话。实现方观察到异常现象，如实记录现象本身即可。

### 规则 4：验收指标必须能证伪

T003 的验收条件是我写的：「两个场景各连续 3 次 `status=completed`」。它过了 6/6，但 `status=completed` 只说明 codex 这一回合正常收尾，**不说明场景真的跑通了**。同一批运行的语义评估实际 4/6 失败。用一个永远会亮绿灯的指标去验收，等于没验收。

同一次复盘还翻出更隐蔽的一种：脚本里的 `mcpCalls` 恒为 `[]`，我据此在 T003 的 REVIEW 里写下"MCP 工具调用被拦下"。实测发现 codex 根本不把 `ZHIYUAN_SEMANTIC_MCP_TRACE` 传给 MCP 子进程，夹具里的 `record()` 每次都早退——**这个仪表从来就没有读数，`0` 不是观测结果，是它坏了**。工具其实执行了。

因此写验收条件时逐条问：

- **这条指标失败时会是什么样子？** 想不出失败长什么样，它就不是验收条件。
- **零值 / 空列表能自证吗？** `count == 0`、`list == []`、`grep` 无输出，都必须能区分"确实没有"和"根本没测到"。至少配一次已知非零的对照。
- **缺失的键比零值更危险。** T005 复核时撞上一次：`scripts/codex_semantic_smoke.py` 在模型输出解析失败时**根本不写** `evaluation` 键，于是 `d.get('evaluation', {}).get('passed')` 读出 `None`——不报错、不为真、看起来就像一次普通的不通过。判定脚本必须先断言键存在，再判它的值；`KeyError` 炸出来比静默假值好。
- **它量的是目标，还是目标的必要条件？** "请求被接受"是"任务完成"的必要条件，不是充分条件。验收要压在目标上。

## 六、派发前，设计会话必须自检

写任务书时我出过两次错：先断言 7 个 skill 是孤儿（实际被 `examples/demo_agent.py` 加载且有测试覆盖），又差点让人删掉 `test_keyword_matchers.py`（它是一个在跑的生产模块的唯一测试覆盖）。任务书里的错误会被实现方忠实执行，因此派发前逐条过：

- [ ] **删除类改动**：每个待删文件都 `grep` 过全仓引用了吗？被测试引用 ≠ 可删——先确认那个测试没有在覆盖别的生产模块。
- [ ] **同名冲突**：待删符号在生产代码里有没有同名但无关的定义？（如 `PlanAction` 在 `app/zhiyuan_agent/tools.py:85` 是另一个类型）
- [ ] **已知失败基线**：全量测试当前有哪些预存在失败？逐条列进任务书，否则实现方无法区分"我弄坏的"和"本来就坏的"。
- [ ] **环境事实**：版本、路径、端点可达性等已核实的事实，全部列进任务书并标注"不要重新调查"，避免实现方重复踩坑。
- [ ] **关于外部系统的断言，标明是实测的还是假设的。** P1a 的任务依据是"上游响应带 `dataVersion` 字段"——那是我假设的，实现方照做、在替身上九步验收全绿，而真实上游根本没有这个字段（实测见 `plans/2026-09-11-P1a上游版本契约实测与dataVersion改设计.md`）。替身能证明代码按设计工作，不能证明设计与外部世界相符。凡是写"上游会返回 X"，要么先自己调一次，要么在验收里留一条"用真实调用确认 X"，**不要让替身替外部系统作证**。
- [ ] **桩的形状要从生产者那一侧取，不要从消费者的期望那一侧编。** 上一条的同一个错误换了个对象：`test_domain_mcp_tools.py` 里的 `Backend` 桩返回 `{"dataVersion":"v17","admissionFacts":[…]}`，而真实的 `InternalClientBackend.get_history` 返回一个 JSON **数组**——桩是照着消费者期望写的，于是它证明的是"消费者能吃下它期望的东西"，一句同义反复。真实链路上三处断链因此全部漏检（见 `plans/2026-09-11-P1a证据到不了Agent的三处断链.md`）。**任何替内部服务作桩的测试，返回值都应当是一次真实响应的留档（手抄也行），而不是"应该长这样"。**
- [ ] **迁移设计时，专门去找"现在永远通过"的检查。** 它们不是已经生效的防线，是还没接上被检查对象的**空转**防线，而接上之后方向可能是反的。判别办法只有一句：**"有没有一种输入能让这个检查失败？"**——如果在当前代码里构造不出来，这个检查就从未被验证过，不管它写得多严。`output_validation.py` 对证据的三处检查（在账本里找得到、`stateVersion` 等于当前、`threadId` 等于当前）今天全部恒真，因为证据是每回合自铸的、填的就是当前值；P1b 让证据变成跨回合的真东西之后，三条**全部转为恒假**，会把 `fact` 回合全线拒收（见 `plans/2026-09-13-P1c证据校验器的三处结构性拒收.md`）。这与 `mcpCalls` 恒为 `[]` 是同一类错误的两面：那次是仪表没通电、读数恒定；这次是校验器没通电、判定恒过。**恒真的检查和坏掉的检查，在测试里长得一模一样。**

  **同一个形状已经撞到第五次**（`mixed-read-write` 场景的 `forbidden_tool_names={"plan_apply"}`：只读夹具的 `tool_list()` 压根没声明 `plan_apply`，于是这个场景的头号主张"模型被要求写入时不会真的写"**从来没被真正测过**——那把枪不在桌上）。**这类检查最爱藏在"负向断言"里**：`forbidden_*`、`assert not ...`、`assert x == []`、`grep` 无输出。写负向断言时必须多问一句：**这个东西有没有可能出现？** 不可能出现，断言它不出现就是同义反复。修法通常不是删检查，而是**把枪放上桌**——夹具声明 `plan_apply` 但拒绝执行，模型看得见却不碰，才叫克制。

  **但第五次这个例子暴露了上面那句判别办法本身有漏洞，值得单记一笔。** 细查发现：夹具的 `call_tool()` 是**先 `record()` 再分发**的，未知工具名也照记不误；而模型确实偶尔会去调没声明过的工具（T005 run 3 就调了不存在的 `admission.get_current_plan`）。所以严格说，`forbidden_tool_names={"plan_apply"}` **不是不可能失败**——模型哪天幻觉出一个 `plan_apply` 调用，它就会亮红灯。

  **于是"有没有一种输入能让这个检查失败？"这一问，在这里会回答"有"，然后把它放行——可它仍然是个空转的检查。** 因为能让它失败的那种输入（幻觉调用一个没见过的工具）**不是我们想防的那种行为**（拿到写工具之后真的去写）。一个从不克制、只要给了写权限就立刻动手的模型，在今天这套夹具下照样满分通过。

  所以判别办法要补一句，**两问连着用**：

  > 1. 有没有一种输入能让这个检查失败？
  > 2. **能让它失败的那种输入，正是我们想防的那种行为吗？**

  第 1 问答"没有"，是死检查；第 1 问答"有"、第 2 问答"不是"，是**更难发现的空转检查**——它有过红灯的可能，所以看起来是活的，但它守的门跟我们要守的不是同一扇。
- [ ] **问一句：如果被测方做出「更安全但不同」的选择，这条验收会不会判它失败？** 会的话，这条验收在训练一个更差的系统。`mixed-read-write` 场景要删除方案里的"第三个"，而那个 `school-3` 无名、不在候选集、没有任何工具能读到它。场景要求 `response_type="fact"`、`clarification_required=False`、必须给出删除提案。于是：**问"第三个到底是哪所学校"的那次运行被判失败，闭着眼给一个一无所知的实体生成删除提案的那次被判通过。** 同一个仓库里 P3 流程门禁的立意正是"写操作要先确认"，这条验收在往反方向拉（见 `plans/2026-09-13-P0第二条验收条mixed-read-write的四个成因.md` 第三节）。

  这与规则 4 的"指标要能证伪"是**两件事**：那条问的是"它会不会永远通过"，这条问的是"它通过的时候，奖励的是不是我们真正想要的行为"。**一个既能失败、又指向错误方向的验收，比一个恒真的验收更危险**——恒真的至少不会把系统往坏处推。

- [ ] **"连续 n 次通过"这类判据，先算一下它的分辨力。** 这是验收缺陷的第三类：**能失败、方向也对，但分不出好坏**。P0 的验收条是"连续 3 次 `evaluation.passed == true`"。T008 复核时我跑了 10 次，前 3 次全过——**字面满足了**。但这条判据在被测系统真实可靠性为 95% 时有 **85.7%** 的概率通过，90% 时 72.9%，85% 时仍有 61.4%。**它区分不了 85% 和 100%，而这两者是完全不同的两个系统。**

  凡是涉及模型输出、网络、真实端点这类**天生带抖动**的被测对象，判据都要写成**带分母**的形式（"20 次中至少 19 次"），不要写成"连续 n 次"。连续 n 次是个**下界很松的判据**：它只排除掉了"烂到几乎每次都挂"，剩下的全放行。

  报数时同样：**19/20 要连着置信区间一起报**（Wilson 95% CI 是 [76.4%, 99.1%]）。20 个样本区分不了 80% 和 99%，把"95%"当成已知量拿去做后续判断，是给自己造一个精度不存在的数。

- [ ] **写完一条验收条，问一句：这个数字，从交付物的哪个字段读出来？** 这是验收缺陷的**第四类**，前三类问的是"这条判据好不好"，这一类问的是"这条判据**够得着吗**"。

  T009 任务书同时写了两句互相打架的话：验收第 4 条要求"**在同一次运行里**统计 `item["text"]` 是 `str` 的有几个、是 list 的有几个"，而交付物规格只让 `agentMessages` 带 `itemId` / `text` 两个字段——**形状信息按我自己定的规格根本不会被留下来。** 实现方于是只有两条路：超范围加字段，或者走交付物之外的一次性临时探针（它选了后者，并如实报为偏离）。

  **两条都是偏离，而且都是我造成的偏离。** 判别办法就一句：对着交付物规格逐条问"这个观测从哪个字段、哪条输出里读出来"，答不上来就改——要么把字段补进交付物规格，要么把验收条明确改成"允许一次性探针"并说清它跟主验收不是同一次运行。

- [ ] **边界**：明确列出不要动的目录和文件，尤其是大文件和正在演进的模块。


- [ ] **验收指标**：每条都过一遍规则 4 的三问——失败什么样、零值能否自证、量的是不是目标本身。
- [ ] **报告路径**：写死绝对路径了吗？

## 七、回收时，设计会话必须做

- [ ] 报告文件存在，且状态词是四态之一
- [ ] **自己重跑一遍验收命令**，不采信报告里的输出（报告输出用于比对差异，不用于替代复核）
- [ ] **重跑次数要够看出抖动。** T005 的门禁报告跑 3 次全过，我跑 8 次是 7 过 1 挂——低频抖动只跑一遍是看不见的。真实端点、涉及模型输出的验收，至少跑到能给出分母（"n 次中 m 次"），不要只报一次结果
- [ ] **复核里引用的每个数字，确认它的仪表是活的**（规则 4）。不要拿一个没验证过的观测值去下结论——T003 的 REVIEW 就是这么写错的。
- [ ] **观察本身要复核，观察的推论更要复核——尤其是我自己加上去的那句推论。** T008 复核时实现方报了一条事实：`item/completed` 事件的 `text` 是空串。事实没错，**我把它的含义放大了**，在 REVIEW 里写成"无法从 payload 回看模型写了什么"，还据此开了 T009。实测一查：671 个 delta 片段一直原样落在同一个 payload 里，拼起来就是完整原文，字节不差。**正文从没丢过，丢的只是拼好的那一份。** 按错的说法 T009 是"补采数据"，按实测是"把碎片拼好存一份"，范围差一个量级。

  实现方守规则 3（只列事实、不定性）是对的，**定性是设计会话的活**——所以定性错了也是设计会话的账。写 REVIEW 时凡是出现"因此"、"于是"、"这说明"，回头对着原始数据再验一遍那一跳。**我复核了它报的每一个数字，却没复核自己给那些数字加上的那句解释。**
- [ ] `git status` 核对实际改动文件 == 报告声明的清单，多出来的文件逐个问清楚

### 口头派发的任务怎么判边界

T006 / T007 由设计会话口头派发，没有 `TASK.md`。实现方的处理是对的：按 `LEDGER.md` 的标题界定范围，并把"本任务没有任务书"写进偏离节。补一条规则：
