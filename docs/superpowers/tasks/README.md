# 任务分派与回收协议

> 适用范围：设计会话（Claude Opus 5，负责设计与评审）向实现会话（DeepSeek 等，负责执行）分派任务的全过程。
> 本文是该流程的唯一权威。任务书与本文冲突时以本文为准。

---

## 一、这个协议解决什么问题

T001 / T002 两个任务在协议建立前执行，暴露了三个真实缺陷：

1. **结果靠聊天转述回流。** 实现方把结论打在对话里，人再粘贴给设计会话。中间丢了状态词、丢了文件清单、丢了验收原始输出。设计会话拿到的是二手摘要，无法复核。
2. **全量测试的预存在失败没有基线。** T002 跑完单测有 2 项失败，实现方无从判断是不是自己弄坏的，设计会话也要重新查一遍才敢下结论。
3. **实现方的事实与推断混在一起。** T001 做得对（只列事实、不给建议），但这靠的是任务书里临时写了一句，不是制度。

因此本协议的核心不是模板好看，而是三件事：**报告落成文件、验收贴原始输出、事实与推断分离。**

## 二、目录约定

```
docs/superpowers/tasks/
├── README.md                  ← 本文，协议
├── LEDGER.md                  ← 台账，一行一任务，唯一状态来源
├── _templates/
│   ├── TASK.md                ← 任务书模板
│   └── REPORT.md              ← 报告模板
└── T0NN-<ascii-slug>/
    ├── TASK.md                ← 设计会话写，派发前冻结
    ├── REPORT.md              ← 实现会话写，路径由任务书写死
    └── REVIEW.md              ← 设计会话写，回收判定
```

任务 ID 从 `T001` 起单调递增，永不复用。目录 slug 用 ASCII 短横线，标题写中文放在 `TASK.md` 里。

## 三、生命周期

| 步 | 动作 | 谁做 | 产物 |
|---|---|---|---|
| 1 | 建目录、写任务书、跑派发前自检 | 设计会话 | `TASK.md` |
| 2 | 登台账，状态 `DISPATCHED` | 设计会话 | `LEDGER.md` 一行 |
| 3 | 执行，只读 `TASK.md`，不依赖任何会话上下文 | 实现会话 | 代码改动 |
| 4 | 写报告到任务书指定路径 | 实现会话 | `REPORT.md` |
| 5 | 复核：逐条重跑验收、核对文件清单、判定 | 设计会话 | `REVIEW.md` |
| 6 | 更新台账终态；通过则由设计会话统一提交 | 设计会话 | `LEDGER.md` |

**实现会话在第 3 步只能看 `TASK.md`。** 任务书必须自足：背景、已核实的环境事实、步骤、陷阱、验收、边界、报告路径，全部写在里面。实现方需要回头问才能开工，说明任务书没写够，这是设计会话的责任。

## 四、状态词

### 实现方声明（写在 `REPORT.md` 的 `status`）

| 状态 | 含义 |
|---|---|
| `DONE` | 验收全过，无偏离 |
| `DONE_WITH_CONCERNS` | 做完了但有偏离或存疑项，必须逐条说明偏离内容与判断依据 |
| `BLOCKED` | 被挡住，附原始报错，不猜原因 |
| `NEEDS_CONTEXT` | 任务书信息不足，说明缺什么 |

实现方**不得**自评通过与否。`DONE` 只是"我认为验收过了"，不是结论。

### 设计方判定（写在 `REVIEW.md` 的 `verdict`）

| 判定 | 含义 |
|---|---|
| `ACCEPTED` | 复核通过，改动可提交 |
| `ACCEPTED_WITH_FOLLOWUP` | 主体通过，遗留项另开任务，ID 写进 `REVIEW.md` |
| `REJECTED` | 不通过，说明具体哪一条不成立，退回或重开任务 |
| `SUPERSEDED` | 任务前提已被新事实推翻，不再执行 |

**`BLOCKED` 不等于失败。** T001 报 `BLOCKED`（没采到断流现场），但它的对照数据直接推翻了 P0 的诊断前提，判定为 `ACCEPTED`。判定看的是产出是否可信、是否推进了认知，不是任务目标是否达成。

## 五、四条硬规则

### 规则 1：报告是文件，不是聊天消息

任务书必须在「报告」一节写死绝对路径，形如：

```
把报告写到 /root/dev/zhiyuan/docs/superpowers/tasks/T0NN-<slug>/REPORT.md
```

回收动作就是读这个文件。聊天里的摘要只作提示，不作依据。**报告文件不存在 = 任务未交付**，无论对话里说了什么。

### 规则 2：验收贴原始输出

每条验收命令必须在报告里贴出**未经编辑的原始输出**。"全部通过"、"符合预期"这类转述一律不接受。命令没跑就写没跑，不要写预期结果。

### 规则 3：事实与推断分离

报告只写观察到的事实：改了什么、命令输出是什么、报错原文是什么。

**不写修复建议、不写下一步计划、不写根因推测。** 定性和方案属于设计会话。实现方观察到异常现象，如实记录现象本身即可。

### 规则 4：验收指标必须能证伪

T003 的验收条件是我写的：「两个场景各连续 3 次 `status=completed`」。它过了 6/6，但 `status=completed` 只说明 codex 这一回合正常收尾，**不说明场景真的跑通了**。同一批运行的语义评估实际 4/6 失败。用一个永远会亮绿灯的指标去验收，等于没验收。

同一次复盘还翻出更隐蔽的一种：脚本里的 `mcpCalls` 恒为 `[]`，我据此在 T003 的 REVIEW 里写下"MCP 工具调用被拦下"。实测发现 codex 根本不把 `ZHIYUAN_SEMANTIC_MCP_TRACE` 传给 MCP 子进程，夹具里的 `record()` 每次都早退——**这个仪表从来就没有读数，`0` 不是观测结果，是它坏了**。工具其实执行了。

因此写验收条件时逐条问：

- **这条指标失败时会是什么样子？** 想不出失败长什么样，它就不是验收条件。
- **零值 / 空列表能自证吗？** `count == 0`、`list == []`、`grep` 无输出，都必须能区分"确实没有"和"根本没测到"。至少配一次已知非零的对照。
- **缺失的键比零值更危险。** T005 复核时撞上一次：`scripts/codex_semantic_smoke.py` 在模型输出解析失败时**根本不写** `evaluation` 键，于是 `d.get('evaluation', {}).get('passed')` 读出 `None`——不报错、不为真、看起来就像一次普通的不通过。判定脚本必须先断言键存在，再判它的值；`KeyError` 炸出来比静默假值好。
- **它量的是目标，还是目标的必要条件？** "请求被接受"是"任务完成"的必要条件，不是充分条件。验收要压在目标上。

## 六、派发前，设计会话必须自检

写任务书时我出过两次错：先断言 7 个 skill 是孤儿（实际被 `examples/demo_agent.py` 加载且有测试覆盖），又差点让人删掉 `test_keyword_matchers.py`（它是一个在跑的生产模块的唯一测试覆盖）。任务书里的错误会被实现方忠实执行，因此派发前逐条过：

- [ ] **删除类改动**：每个待删文件都 `grep` 过全仓引用了吗？被测试引用 ≠ 可删——先确认那个测试没有在覆盖别的生产模块。
- [ ] **同名冲突**：待删符号在生产代码里有没有同名但无关的定义？（如 `PlanAction` 在 `app/zhiyuan_agent/tools.py:85` 是另一个类型）
- [ ] **已知失败基线**：全量测试当前有哪些预存在失败？逐条列进任务书，否则实现方无法区分"我弄坏的"和"本来就坏的"。
- [ ] **环境事实**：版本、路径、端点可达性等已核实的事实，全部列进任务书并标注"不要重新调查"，避免实现方重复踩坑。
- [ ] **边界**：明确列出不要动的目录和文件，尤其是大文件和正在演进的模块。
- [ ] **验收指标**：每条都过一遍规则 4 的三问——失败什么样、零值能否自证、量的是不是目标本身。
- [ ] **报告路径**：写死绝对路径了吗？

### 当前已知失败基线（2026-09-11，`zhiyuan-agent/scripts/run_unit_tests.sh`）

```
FAILED tests/unit/test_dialog_quality_gate.py::test_final_action_explicit_clone_sources_have_volunteer_fixture
FAILED tests/unit/test_ops_release_smoke.py::test_release_smoke_supports_production_and_dev_web_base_paths[None-/assistant-pc/session]

```

第一条因 `zhiyuan-server/data/tmp/session_volunteer_*.json` 本地夹具缺失（94 条），第二条与 web base path 有关。两条都与 codex 引擎链路无关。

通过数 2026-09-10 为 1699，T005 新增一条回归测试后为 1700。基线变化时更新本节，并在此记下差额来自哪个任务——否则下一个实现方无法区分"新增用例"和"漏跑用例"。

## 七、回收时，设计会话必须做

- [ ] 报告文件存在，且状态词是四态之一
- [ ] **自己重跑一遍验收命令**，不采信报告里的输出（报告输出用于比对差异，不用于替代复核）
- [ ] **重跑次数要够看出抖动。** T005 的门禁报告跑 3 次全过，我跑 8 次是 7 过 1 挂——低频抖动只跑一遍是看不见的。真实端点、涉及模型输出的验收，至少跑到能给出分母（"n 次中 m 次"），不要只报一次结果
- [ ] **复核里引用的每个数字，确认它的仪表是活的**（规则 4）。不要拿一个没验证过的观测值去下结论——T003 的 REVIEW 就是这么写错的。
- [ ] `git status` 核对实际改动文件 == 报告声明的清单，多出来的文件逐个问清楚
- [ ] 边界清单里的文件确实没被动过
- [ ] 全量测试的新增失败逐条对照已知基线
- [ ] 写 `REVIEW.md`，更新 `LEDGER.md` 终态
- [ ] 通过后由设计会话提交。**实现会话一律不 commit**，这条写进每份任务书

### 口头派发的任务怎么判边界

T006 / T007 由设计会话口头派发，没有 `TASK.md`。实现方的处理是对的：按 `LEDGER.md` 的标题界定范围，并把"本任务没有任务书"写进偏离节。补一条规则：

**没有 `TASK.md` 时，边界依据是 `LEDGER.md` 的标题，且报告必须显式声明这一点。** 复核时不能用"任务书里没写"来指责实现方越界或漏做——没写是设计会话的欠账。

但这只是兜底。口头派发的代价在 T006 / T007 上已经显形：两份报告都得自己猜边界，而"猜对了"是运气不是制度。**能写任务书就写**，哪怕只有五行。
