# 3.0.2 高考年份与历年分数信息调整方案

更新时间：2026-06-06

## 背景

当前生产版本处于 3.0.2 版本线上运行阶段，后续需要进行 2026 新年度数据升级。排查发现系统内没有统一的年度开关，年度信息由多个入口共同决定：用户采集流程、普通新建会话、外部初始化会话、候选池生成、详情页展示和导出。

本次先聚焦两个问题：

1. 用户采集信息和初始化会话中，高考年份是否能够正确进入 2026。
2. 前端详情页中的招生计划年份、历年分数信息是否仍存在 2025 固定展示或年度语义不准确的问题。

## 当前排查结论

### 1. 用户采集流程年份默认值存在问题

位置：`zhiyuan-server/src/main/java/com/ytell/zhiyuan/service/FlowConfigService.java`

当前逻辑：

- 无用户已有高考年份时，`examYear` 默认值使用 `Year.now() + 1`。
- 在 2026-06-06 运行时，新用户采集默认年份会变成 `2027`，不符合当前 2026 年度升级目标。
- `loadExamYearField()` 当前生成的年份选项从下一年开始，即 2027、2028、2029、2030。
- 选项结构不一致：第一项使用 `code/name`，后续项使用 `value/label`。

影响：

- 用户信息采集页可能默认展示或保存 2027。
- 前端采集页多处按 `code/name` 读取选项，后续 `value/label` 项可能无法正常展示或回填。
- 后续创建会话时，如果该采集结果进入 `CreateSessionReq.examYear`，会导致候选池按错误年份请求。

修正方案：

- 客户采集流 `collect-flow` 的年份选项也应对齐主站 `/hl-wish/ci/memberWhitelist/noToken/commonInfo`，使用其 `examYearList`。
- 将 `examYearList` 转换为采集流统一需要的 `code/name` 结构，例如 `{ "code": "2026", "name": "2026年" }`。
- 无用户已有 `examYear` 时，默认选择 `examYearList` 第一项，即主站当前优先年份。
- 只有当 `commonInfo` 请求失败或返回空时，才兜底为当前年份起的 4 年。
- 保留用户已有 `examYear` 的不可编辑逻辑，避免影响历史已采集用户。

### 2. 个人中心、初次登录和普通新建会话已依赖高途年份接口

位置：

- `zhiyuan-web/src/pageComponents/customer/UserInfoModal/index.tsx`
- `zhiyuan-web/src/pages/userCenter/index.tsx`
- `zhiyuan-web/src/pageComponents/session/ModalForm/index.tsx`

当前逻辑：

- 初次登录用户信息弹窗、个人中心、新建会话弹窗的年份下拉均来自 `/hl-wish/ci/memberWhitelist/noToken/commonInfo`。
- 创建会话时会从表单字段 `examYear` 进入请求。
- 一分一段接口请求会带 `year: form.getFieldValue('examYear')`。
- 主站 token 登录时，高途 `getUserInfoByToken` 返回的 `examYear` 会同步保存到本系统 `userScoreOb.examYear`。

验证结果：

- 线上 `commonInfo` 返回 `2026、2027、2028、2029`。
- 使用线上 token 请求 `/gaotu-assistant-bot/chat/user/info`，当前用户 `userScoreOb.examYear=2026`。

影响：

- 这三类前端入口已经与主站年份列表对齐。
- 当前不一致点集中在后端 `collect-flow` 自己生成年份选项。

实施要求：

- `collect-flow` 也改为复用 `commonInfo.examYearList`，保证与主站逻辑一致。
- 若高途返回顺序不是按当前年度优先，需进一步评估默认选择策略。

### 3. 外部初始化会话没有年度兜底，必须由调用方传入 2026

位置：

- `zhiyuan-server/src/main/java/com/ytell/zhiyuan/web/controller/IntegrationSessionController.java`
- `zhiyuan-server/src/main/java/com/ytell/zhiyuan/service/biz/IntegrationSessionService.java`
- `zhiyuan-server/src/main/java/com/ytell/zhiyuan/service/biz/ChatSessionBizService.java`

当前逻辑：

- 外部初始化接口 `/integration/session/initialize` 和 `/integration/v1/session/initialize` 复用统一创建会话逻辑。
- `generateAllExpertAIProgram` 请求中会设置 `year = createSessionReq.examYear`。
- `batch / areaId / score / subjects / subjectType / prepareType` 均来自请求或前置采集数据。

影响：

- 外部接口如果仍传 2025 的 `examYear` 或 2025 批次线，会直接影响候选池生成。
- 不能只改 `examYear`，`batch.code / batch.score / batch.pos / batch.level / prepareType` 必须来自 2026 批次政策数据。

实施要求：

- 对外文档样例需要使用 2026 年份和 2026 批次数据。
- 外部调用方接入前必须用 2026 样例做一次真实初始化验证。

### 4. V2 详情页存在硬编码 `2025招生计划`

位置：`zhiyuan-web/src/pageComponents/sessionDetailV2/WorkspacePanel/index.tsx`

当前发现：

- 候选/方案专业行中存在两处固定展示 `2025招生计划`。
- 这会在 2026 会话中继续展示 2025，语义错误。

修正方案：

- 后端会话详情 `ChatSessionVo` 补充 `examYear`。
- 前端详情页 `sessionDetailV2/index.tsx` 从 `getSessionDetailApi` 响应保存 `examYear`。
- `WorkspacePanel` 新增 `examYear` 入参。
- 将固定 `2025招生计划` 改为 `${examYear}招生计划`。
- 当会话详情缺失 `examYear` 时，前端兜底使用当前年份，避免页面空展示。

### 5. V2 详情页历年录取分数线按上游年份展示

位置：`zhiyuan-web/src/pageComponents/sessionDetailV2/WorkspacePanel/index.tsx`

当前逻辑：

- 历年分数列来自候选数据中的 `majorHistoryScores` / `schoolHistoryScores`。
- 展示年份由数据里的 `year` 动态排序生成，不是固定 2025。

验证结果：

- 使用线上 token 只读请求 `workspace-state` 抽样 sessionId=2747。
- 候选池前 5 条学校和专业历史年份均为 `2025、2024、2023`。
- 该会话是 2026 年度数据场景，历史年份结果符合预期。

处理结论：

- 历年录取分数线不做前端年度推断或过滤，直接按上游返回的 `year` 字段展示。
- 前端只负责动态渲染数据年份，数据准确性由上游候选数据保证。
- 本次前端详情页重点修正 `2025招生计划` 硬编码，不调整历年分数展示逻辑。

### 6. Legacy 详情页也有年份语义需要后续确认

位置：`zhiyuan-web/src/pageComponents/sessionDetailLegacy/index.tsx`

当前发现：

- Legacy 页招生计划标题使用历史分数中的最新年份作为 `${latestYear}招生计划`。
- 如果历史分数最新年份为 2025，2026 会话下标题可能仍显示 `2025招生计划`。

处理建议：

- 如果 3.0.2 生产主入口已切 V2，Legacy 可作为低优先级兼容项。
- 若仍有用户可能进入 Legacy，需要同样接入会话 `examYear`，招生计划标题改为高考年份。

## 需要调整的接口与数据点

| 类型 | 接口/数据 | 是否需要 2026 调整 | 说明 |
|---|---|---|---|
| 年份列表 | `/hl-wish/ci/memberWhitelist/noToken/commonInfo` | 是 | 必须包含 2026 |
| 选科政策 | `/hl-wish/ci/selectSubjectPolicy/noToken/subjectPolicy` | 是 | 无 year 参数，依赖高途侧切换当前年度 |
| 批次信息 | `/hl-wish/ci/h5/batchData/anno/batchListByPolicy` | 是 | 无 year 参数，需返回 2026 批次线 |
| 一分一段 | `/hl-wish/ci/scorePosition/noToken/getPosRangeByScore` | 是 | 请求带 year，必须有 2026 数据 |
| 推荐数量 | `/hl-wish/ci/ci_feign/volunteer/getRecommendProgramNum` | 是 | 无 year 参数，需高途侧保证当前年度 |
| 候选池 | `/hl-wish/ci/ci_feign/volunteer/generateAllExpertAIProgram` | 是 | 请求显式带 `examYear` |
| 静态民族/地区 | 本系统 base-data | 否 | 一般不随年度变化 |
| 专业目录/限报规则 | 本系统 base-data | 视情况 | 若 2026 专业目录或限报规则变化则需更新 |

## 实施步骤

1. 修复后端采集流程年份默认值和年份选项结构，使 `collect-flow` 对齐主站 `commonInfo.examYearList`。
2. 后端 `ChatSessionVo` 增加 `examYear`，会话详情和创建会话响应都返回该字段。
3. 前端 `sessionDetailV2` 保存会话详情返回的 `examYear`。
4. 前端 `WorkspacePanel` 使用 `examYear` 显示招生计划年份。
5. 历年分数继续按上游 `year` 字段动态展示，不做前端过滤。
6. 本地构建前端，后端跑相关单测或至少编译校验。
7. 使用 2026 样例创建会话，验证：
   - 采集流程默认年份为 2026。
   - 会话详情返回 `examYear=2026`。
   - 详情页展示 `2026招生计划`。
   - 历年录取分数线展示 2025、2024、2023 等历史年份。
   - 候选池生成请求使用 `year=2026`。
8. 再评估是否补 Legacy 页面兼容。

## 验证用例建议

### 用户采集流程

- 新用户无已有 `examYear`：默认值应为 2026。
- 年份选项应与主站 `commonInfo.examYearList` 一致，例如 2026、2027、2028、2029。
- 选项对象均应为 `code/name`。
- 旧用户已有 `examYear=2025`：应保持原值且不可编辑，不强行改为 2026。

### 普通前端创建

- 选择 2026、河北、物理、对应本科批。
- 一分一段接口请求 `year=2026`。
- 创建会话请求 `examYear=2026`。
- 候选池文件中数据非空。

### 外部初始化创建

- 请求体显式传 `examYear=2026`。
- `batch` 使用 2026 批次接口返回值。
- 初始化成功后返回会话详情页 URL。
- 打开详情页后展示 `2026招生计划`。

### 详情页展示

- 候选区专业行：招生计划标题为 `2026招生计划`。
- 方案区专业行：招生计划标题为 `2026招生计划`。
- 学校历年录取分数弹窗：年份列按上游返回的历史年份展示，例如 2025、2024、2023。
- 移动端专业卡片：历年分数年份与 PC 一致。

## 风险与回滚

- 后端新增 `examYear` 是响应字段增加，对旧前端兼容。
- 采集流程默认年份从下一年改为当前年，会影响无高考年份用户的新采集默认值，符合 2026 升级目标。
- 历年分数不做前端年度过滤，避免前端误判上游数据语义。
- 若上线后发现招生计划年份异常，可回滚 `WorkspacePanel` 招生计划标题改动；后端返回 `examYear` 可保留。

## 未决问题

1. 高途 `commonInfo` 是否已返回 2026，以及返回顺序是否稳定。
2. `subjectPolicy / batchListByPolicy / getRecommendProgramNum` 无年份参数，高途侧是否已完成 2026 当前年度切换。
3. Legacy 详情页是否仍有实际入口和用户访问量，是否纳入本次修复。
4. 导出模板表头是否需要从“去年/前年”改成实际年份，当前导出主要按历史分数数组位置映射，后续可单独评估。
