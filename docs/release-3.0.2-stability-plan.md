# Release 3.0.2 Stability Plan

本文档承接 `prod-3.0.1` 之后的新一轮稳定优化。后续新增问题默认进入 `3.0.2` 相关文档，不再继续扩大 `3.0.1` 范围。

文档定位：

- 本文负责维护 `3.0.2` 的版本目标、优先级、模块拆分和验收口径。
- 具体接口、字段、组件和测试实现，在范围确认后再补充到 `docs/release-3.0.2-implementation-design.md`。
- `3.0.1` 已经完成或正在收口的内容，不在本文重复展开；只记录后续仍需优化的部分。

## 1. 版本目标

`3.0.2` 的目标是继续提升新版工作台在真实业务中的稳定性、可解释性和操作效率，重点处理四类问题：

1. 候选筛选和工作台入口：让用户更快定位目标候选、清除筛选/排除条件，并优化登录后的默认进入路径。
2. 方案可信度和异常解释：继续收口候选为空/偏少、录取率断层、状态展示不一致等 backlog 问题。
3. Agent 质量和性能：解决长历史污染、上下文过重、对话驱动方案编辑的持续稳定性问题。
4. 方案生成和导出口径：修复专业组内专业默认顺序、专业+大学模式导出结构等线上反馈问题，保证页面、导出和用户心智一致。

本版本默认优先 PC/Web。移动端只处理明确影响新版主链路的问题；如进入移动端改动，必须补充独立验证。

## 2. 新增反馈进入 3.0.2

### 2.1 筛选面板剔除规则快速移除

问题：

- 用户在候选筛选里添加排除条件后，想快速撤销时不够直接。
- 当前如果只能回到原筛选项里反向操作，长列表下成本较高。

目标：

- 在筛选框或已选条件区域中，对排除规则提供直接 `x` 移除入口。
- 正向筛选和排除筛选视觉区分，避免用户误删。
- 移除后候选列表立即按当前条件刷新。

验收：

- 用户能在筛选面板顶部或已选条件区一键移除某个排除条件。
- 移除排除条件不会清空其他正向筛选。
- 操作在 `major` 和 `majorGroup` 两种模式下均生效。

### 2.2 筛选专业和院校支持三级专业、院校名

问题：

- 当前筛选重点在省市、专业类和部分标签，用户想按更细颗粒度筛选时效率不足。
- 真实使用中，用户常会按三级专业或具体院校名寻找候选。

目标：

- 专业筛选支持一级/二级/三级专业层级，至少能定位到三级专业名称。
- 院校筛选支持按院校名搜索或筛选。
- 筛选项来源必须来自后端候选池真实数据或领域字典，不由前端硬编码。

验收：

- 用户可搜索或展开定位三级专业。
- 用户可按学校名快速筛选候选。
- 筛选结果为空时只提示“当前筛选无结果”，不误提示系统候选不足。
- 不恢复已移除的“意向专业类/负向专业标签”等解释性标签。

### 2.3 登录后默认进入会话列表

问题：

- B 端用户登录后更需要先看到会话列表，而不是直接进入 C 端式默认会话界面。
- 当前用户进入后路径心智不稳定，可能不知道如何切换到会话管理。

目标：

- 明确登录后的默认跳转策略：B 端入口优先进入 `/assistant-pc/session` 会话列表。
- 若存在特定带参深链路，保留深链路优先级，例如直接打开某个 `sessionDetailV2`。
- 详情页仍保留明显“返回会话列表”入口。

验收：

- 正常登录后进入会话列表。
- 带会话参数的链接不被错误重定向丢失。
- 退出详情页能稳定回到会话列表。

### 2.4 前置信息采集过程增加缓存

问题：

- 用户在创建会话前需要填写成绩、选科、批次、地域、专业偏好等前置信息。
- 当前如果中途填错、刷新、返回或某一步校验失败，用户可能需要重新填写较多内容，交互成本高。

目标：

- 前置信息采集过程支持阶段性缓存，用户返回或修正某一项时，不丢失已填写内容。
- 缓存只作为创建会话前的临时草稿，不等同于正式方案或正式用户偏好。
- 用户最终确认提交后，再进入会话初始化、候选生成和方案生成流程。
- 本期以“上一步修正 + 已确认字段恢复”为主，不再单独提供“重新开始”入口；旧缓存通过提交成功、过期或非法校验自动清理，避免误带入新会话。

验收：

- 用户填错某一项后可以回到对应步骤修改，不需要整轮重填。
- 刷新页面或短时间离开后，已填写内容可以恢复。
- 提交成功后清理或标记该缓存已消费，避免下次创建会话误用。
- 缓存中不保存不必要的敏感信息；如落本地存储，需要明确过期和清理策略。

### 2.5 外部初始化会话支持学员姓名展示和稳定版本接口

问题：

- 外部系统会通过我们提供的初始化会话接口直接创建会话并生成方案。
- 外部系统希望详情页能展示当前服务学员姓名，例如在“模拟填报”之前显示“高翔”，让用户明确当前方案是为谁制定。
- 如果外部接口没有提供学员姓名，前端不应展示空占位。
- 该能力面向外部系统集成，需要形成稳定接口版本和兼容策略，避免后续字段调整影响调用方。

当前可复用能力：

- 已有外部初始化接口 `POST /gaotu-assistant-bot/chat/{tenantId}/integration/session/initialize`。
- 请求体复用 `CreateSessionReq`，其中 `createSession.userName` 已会写入 `assistant_chat_session.user_name`。
- 会话详情接口返回的 `ChatSessionVo.userName` 可作为详情页展示来源。

目标：

- 将 `createSession.userName` 在外部初始化接口语义上明确为“当前被服务学员展示姓名”。
- 详情页顶部在填报类型标签前展示该姓名，例如：`高翔` `模拟填报`。
- `userName` 缺失、空字符串或仅空白时不展示姓名标签。
- 对外提供版本化稳定入口，建议新增或文档化 `POST /gaotu-assistant-bot/chat/{tenantId}/integration/v1/session/initialize`，既有无版本路径作为兼容别名保留。
- 响应体可增加 `studentName/displayName` 这类只读展示字段；如果不新增，也必须保证 `chatSessionId -> session detail -> userName` 链路稳定。

验收：

- 外部系统传入 `createSession.userName="高翔"` 后，初始化响应和会话详情可追溯到该姓名。
- 打开 `sessionUrl` 后，详情页顶部在“模拟填报/智能填报”等标签前显示“高翔”。
- 未传姓名时，详情页保持现有展示，不出现空标签或 `undefined/null`。
- 幂等重试返回同一会话时，展示姓名与首次成功创建的会话一致。
- 新增版本化接口有文档、示例、测试；旧接口在一个版本周期内保持可用。

### 2.6 专业组方案内专业默认顺序不符合录取率正排

问题：

- 线上生产会话 `2268` 暴露：院校专业组模式下，生成后的方案中，专业组内部被选专业没有按老版本口径按专业录取率从低到高展示。
- 用户在专业组内查看专业时，默认会把录取率作为风险判断的第一参考；当前顺序不稳定会造成“系统是否乱排”的感知。
- 旧版链路基本保留 rank 返回的专业组 `majorList` 顺序；新版 PlanningState 会把推荐结果拆平、选专业、再组回 `orderedPlanState.units`，该过程中引入了不同的组内排序口径。

当前定位：

- `PlanningStateService.buildMajorGroupInnerCandidateComparator()` 的排序优先级是 `优选 -> 就业/发展分 -> 意向分 -> 录取率 -> 综合分 -> volunteerId`，录取率不是第一优先级。
- `selectMajorGroupPreferredMajors()` 会把满足 `admissionRatio >= schoolEnrollRatio` 的托底专业前置加入 `selectedMajors`，之后没有再按录取率正排。
- `buildDraftUnitsFromPlanningUnits()` 和 `buildOrderedUnitsFromOrderedItems()` 会保留 `selectedMajors / draftUnit.majorItems` 的既有顺序，因此展示和导出都会继承该顺序。

目标：

- 明确专业组内“已选专业”的默认展示和导出口径：按专业录取率正排，录取率缺失的专业排在后面。
- 托底专业能力继续保留，但托底标记不能强制改变最终展示顺序；如果需要提示托底，应通过标签/审查信息表达，而不是把低录取率专业置顶。
- 页面、工作区接口、导出 Excel 使用同一套专业组内顺序。

验收：

- 新建 `majorGroup` 会话生成方案后，每个 `orderedUnit.majorItems` 默认按 `admissionRatio` 从低到高排列。
- 包含托底专业的专业组仍能保留托底专业，但不会破坏录取率正排。
- 手动调整专业组整体顺序时，不打散组内专业；导出顺序与页面组内顺序一致。
- 补充单测覆盖：普通专业组、含托底专业组、录取率缺失、历史迁移/旧 ID 兼容。

### 2.7 专业+大学模式导出不应呈现专业组式嵌套结构

问题：

- 线上生产会话 `2268` 反馈：专业+大学模式导出的文件中，也会出现类似院校专业组模式的“学校下嵌套多个专业”的结构。
- 对专业+大学模式用户来说，每条志愿就是一个“学校 + 专业”组合；导出按学校合并会弱化志愿序号和单条志愿边界，容易误解为专业组结构。

当前定位：

- `PlanningExcelExportBuilder.buildMajorSchoolExcelRows()` 在 `volunteerModel=major` 时，会按 `schoolId / planSchoolDataId / schoolName` 聚合同校志愿，并把多个专业写入同一个 `majorList`。
- `ExcelUtil.createDataRows()` 会按 `majorList` 为同一学校生成多行，并合并学校列，因此专业模式也会呈现“学校 + 多专业明细”的嵌套效果。
- 当前单测 `PlanningExcelExportBuilderTest.shouldBuildMajorSchoolExportRowsGroupedBySchool()` 明确固定了该聚合行为；这属于当前实现语义偏移，不是生产脏数据。

目标：

- 专业+大学模式导出改为一条排序方案志愿对应 Excel 中一条主志愿行。
- 导出序号严格跟随 `orderedPlanState.items` 的当前顺序连续编号。
- 院校专业组模式继续按 `OrderedUnitDTO` 聚合导出，一个专业组对应一个导出单元，不能被本修复破坏。

验收：

- `major` 模式下，同一学校的多个不同专业在导出文件中仍是多条独立志愿，序号连续且不合并为一个学校单元。
- `majorGroup` 模式下，仍按专业组导出，组内专业明细保留。
- 页面顺序、工作区 `orderedPlanState.items` 顺序和导出顺序一致。
- 补充单测覆盖：同校多专业、不同校专业、手动移动后导出、专业组模式不回退。

## 3. 从既有 backlog 迁入的事项

### 3.1 候选为空/候选偏少可解释性

来源：

- `release-3.0.0-backlog` 的空候选初始化失败可见性。
- `release-3.0.1` 中已设计候选状态，但需要继续确认是否完整落地和验证。

目标：

- 候选池有效候选为 0 时，不继续生成“成功但空”的方案。
- 候选偏少时允许继续，但展示明确风险和原因。
- 区分系统候选不足与用户筛选导致的前端结果为空：
  - 系统候选不足：候选池本身为空或偏少，需要候选池状态提示。
  - 用户筛选为空：只提示当前筛选无结果，允许用户清除筛选。

验收：

- 专项资格、分数线边界、批次条件、上游候选异常均有可定位日志。
- 用户筛选导致空结果不会被误判为系统候选池异常。

### 3.2 录取率断层和审查状态一致性

来源：

- `probability_gap` 不是硬约束。
- `gradientOk` 与 review 结论不一致。
- `majorGroup` 断层详情展示不足。

目标：

- 明确 `probability_gap` 是软约束、审查提醒还是生成硬约束。
- 前端展示上避免出现“整体合理”但审查仍提示断层风险的矛盾感。
- 专业组模式下展示断层数量和关键位置，不只展示单个样例。

验收：

- `gradientOk / sequenceOk / gapOk / reviewStatus` 的命名和展示含义一致。
- 用户能看到“有几处相邻录取率跨度较大”以及对应位置。
- 如果候选池无法满足断层阈值，系统能说明“当前候选不足以完全修复”。

### 3.3 老版本迁移观测

来源：

- 老版本迁移观测面板 backlog。

目标：

- 继续补充 legacy 懒迁移成功、失败、跳过、source 类型统计。
- 按 `_final / _temp / original` 统计来源比例。
- 保留异常会话 ID、失败原因和是否回滚。

验收：

- 能从日志或管理查询中定位单个历史会话迁移来源。
- 能统计一段时间内迁移失败率和主要错误类型。

### 3.4 运维和发布可观测性

来源：

- 健康检查脚本纳入发布流程。
- 混合部署形态继续收口。
- 敏感配置管理。

目标：

- 每次发布记录健康检查输出摘要、镜像/JAR hash、回滚点。
- 继续明确 backend systemd、web/agent/rank Docker 的混合部署边界。
- 生产敏感配置只记录配置项和占位示例，不记录真实 key。

验收：

- 发布前后健康检查可以固定执行和归档。
- 生产异常时能按模块选择回滚动作。
- 文档和提交中不包含真实 `API_KEY / token / password`。

### 3.5 移动端体验观察项

来源：

- 3.0.0 backlog 的移动端继续验证。

目标：

- 不在 3.0.2 默认做移动端重设计。
- 如果 PC/Web 方案筛选、状态或会话入口改动影响移动端，需要列出移动端验证清单。

验收：

- 移动端不因 PC/Web 改动出现明显布局错位或入口丢失。

## 4. 分模块落地计划

### 4.1 前端 Web 工作台

优先事项：

1. 登录后默认进入会话列表。
2. 详情页返回会话列表入口继续保持明显。
3. 筛选面板已选条件区域补充快速移除入口，排除规则可一键 `x` 掉。
4. 筛选专业支持三级层级展开/搜索，院校支持名称搜索。
5. 筛选结果为空时区分“当前筛选无结果”和“系统候选为空”。
6. 前置信息采集过程增加临时缓存、恢复和上一步修改能力，提交成功后自动清空。
7. 详情页顶部展示外部初始化会话传入的学员姓名；缺失时不展示。
8. 验证专业组内专业顺序和导出文件结构修复后的页面/下载结果一致性。

测试：

- 页面路由测试：普通登录、深链路、详情页返回。
- 筛选交互测试：正向筛选、排除筛选、移除单个条件、清空筛选、空结果提示。
- 前置信息采集测试：中途返回、刷新恢复、已确认字段回填、上一步单项修改、提交后缓存清理。
- 详情页展示测试：有学员姓名、无学员姓名、从外部 `sessionUrl` 进入、从会话列表进入。
- 方案和导出人工验收：专业组内专业顺序、专业+大学导出扁平行、专业组导出聚合行。
- 双模式验证：`major` 和 `majorGroup`。

### 4.2 后端工作区和筛选接口

优先事项：

1. 检查候选筛选项生成源头，确认省市、专业层级、院校名均来自真实候选池或领域字典。
2. 补充三级专业和院校名筛选所需字段。
3. 保持后端结构化筛选状态，不把用户筛选误写成初始候选条件。
4. 继续补候选为空/偏少状态字段和原因标记。
5. 评估前置信息采集缓存是否需要服务端草稿接口；如果只做前端临时缓存，后端不感知未提交数据。
6. 外部初始化会话接口明确 `createSession.userName` 为学员展示姓名，并补充版本化 `v1` 稳定入口和响应字段策略。
7. 修复专业组内已选专业的默认排序口径，确保工作区、页面和导出都按录取率正排展示。
8. 修复专业+大学模式导出模型，避免按学校聚合成专业组式嵌套结构。

测试：

- 筛选项生成单测：专业层级、院校名、地域层级。
- 候选查询接口测试：三级专业、院校名、排除条件组合。
- 空候选和筛选空结果分别覆盖。
- 如新增服务端草稿接口，需要覆盖创建、更新、读取、清理和过期策略。
- 外部初始化接口测试：`userName` 入库、幂等命中、版本化路径、响应字段、缺失姓名兼容。
- 方案生成测试：`majorGroup` 组内专业按录取率正排，托底专业不丢失。
- 导出测试：`major` 模式一条志愿一行，`majorGroup` 模式仍一组一单元。

### 4.3 算法和审查

优先事项：

1. 梳理 `probability_gap` 当前生成和审查实现，明确软硬约束口径。
2. 修正 `gradientOk` 等 summary 字段和 review 结论的展示关系。
3. 专业组模式补充断层详情输出。

测试：

- 使用已有 `2076` 类似样本覆盖修复后仍有 unresolved gap 的情况。
- 覆盖 `major` 和 `majorGroup`。
- 覆盖候选池缺少中间梯度导致无法完全修复的解释。

### 4.4 Agent 和对话驱动

优先事项：

1. 长历史裁剪/摘要化设计，降低旧回复污染和 token 成本。
2. 对话驱动筛选能力与前端可见筛选状态对齐：用户通过对话筛选候选时，只写入可见、可撤销的筛选状态。
3. 继续收敛学校/专业简称、三级专业、院校名筛选和方案编辑的对话链路。
4. `planning_workflow_tool` 后续拆分继续排期，但不作为 3.0.2 P0。

3.0.2 P0 的长历史治理采用低风险 runtime 裁剪方案：完整 SQLite 历史继续保留用于审计和 pending 解析，但传给主 agent 的 `message_history` 和 `RequestContext.chat_history` 改为可控短上下文；pending 方案确认仍读完整历史，并且 runtime history 会保留产生有效 pending 的预览轮工具调用和回复，避免破坏 preview -> confirm -> apply 协议。详细设计见 `docs/release-3.0.2-implementation-design.md` 第 8 节。

测试：

- 干净会话和长历史会话对比 smoke。
- 使用 `zhiyuan-agent/examples/dialog_regression_302_agent_cases.json` 覆盖 3.0.2 真实 WebSocket 场景，服务可用后复跑。
- 使用 `zhiyuan-agent/examples/dialog_regression_302_explore_intent_cases.json` 先增强 Explore/Intent 前置层场景覆盖，后续根据真实跑数再串联调优。
- 对话触发筛选后，前端筛选条件可见且可撤销。
- 用户用学校名、专业三级名称、简称表达时，唯一命中才执行，歧义时要求补充。
- 模型接口异常时，plus 兼容 WebSocket 必须返回 `error + end=true`，避免前端或回归 runner 一直等待；真实效果验证需要在模型服务可用后复跑。

### 4.5 行为反馈和数据闭环

优先事项：

1. 继续确认 3.0.1 行为事件采集是否覆盖添加、删除、移动、排序、导出。
2. 行为事件改为独立新表作为主存储，`planningState.behaviorEvents` 不再作为业务读写来源。
3. `exportStatus / lastExportedAt` 已改为读取新表；新动作不再写入旧 JSON，工作台响应也不再返回事件列表。
4. 导出仍作为正反馈，但不等同于真实填报结果。

测试：

- 成功操作才记录行为事件。
- 记录失败不影响主流程。
- 事件能关联 `chatSessionId`、方案版本、动作对象、前后位置、志愿必要展示字段和时间。
- 方案层事件的详细载荷优先补齐候选池字段，覆盖单个志愿添加/删除/移动、专业组整体移动/删除、方案排序和导出；后续分析可直接读取录取率、院校排名、推荐分、学校/专业 ID 等字段。
- 候选筛选添加/排除/移除/清空本期不记录为行为反馈事件。
- 导出态切到新表后，前端工作台展示仍稳定；新表未命中时按未导出处理，不再读取旧 JSON 兜底。

### 4.6 运维和发布

优先事项：

1. 固定 3.0.2 发布前后检查清单。
2. 继续记录镜像/JAR hash 和 tag。
3. 发布包不包含本地 `.env`、真实 key 或临时样本。

测试：

- 本地开发方式验证。
- 准生产或类生产部署演练。
- 回滚命令 dry-run 或人工复核。

## 5. 优先级建议

### P0：进入 3.0.2 准入

1. 登录后默认进入会话列表。
2. 筛选排除规则可在筛选框中快速移除。
3. 筛选支持三级专业和院校名。
4. 候选为空/偏少与用户筛选空结果的状态区分。
5. 前置信息采集过程支持缓存和恢复，避免填错后整轮重来。
6. 外部初始化会话支持学员姓名展示，并形成 `v1` 稳定接口文档和兼容策略。
7. 专业组方案内专业默认按录取率正排，托底专业不再破坏展示顺序。
8. 专业+大学模式导出保持一条志愿一行，不再呈现专业组式嵌套结构。
9. 长历史污染和 token 过重的设计方案落地到文档，并至少完成验证或首轮低风险实现。

### P1：进入 3.0.2 主体优化

1. 录取率断层展示和 `gradient/review` 状态一致性。
2. 专业组断层详情展示。
3. 对话触发筛选和方案编辑的更多端到端回归。
4. 老版本迁移观测统计。

### P2：后续版本或持续建设

1. `probability_gap` 从软约束升级为硬约束的算法重构。
2. `planning_workflow_tool` 完整拆分和 action registry 全量迁移。
3. preview payload 共享存储，支持 Agent 多 worker。
4. 完整模型计费监控平台化。
5. 移动端完整重设计。

## 6. 当前不建议立即做

- 不建议在 3.0.2 直接重写整个 Agent planner。
- 不建议直接删除旧 router/workflow 兼容层。
- 不建议把用户筛选条件重新作为会话初始化默认筛选条件。
- 不建议把导出行为直接用于自动调整推荐算法。
- 不建议为了单个脏历史会话继续增加大量文本清理规则。
