# 规划对话联调清单

## 目的

这份清单用于验证当前规划工作台与对话编排的核心业务链路是否一致，重点看：

- 对话理解是否合理
- 右侧候选 / 方案 / 草稿联动是否正确
- 偏好 / 要求确认链路是否符合设计
- 院校专业组 / 专业+大学 两种模式的统计口径、展示与动作是否一致

## 联调前提

- `assistant-backend` 已启动，且使用当前规划接口版本
- `gaotu-zy-agent-v3` 已启动，WebSocket 正常
- `gaokao-volunteer-pc` 已启动，能进入会话详情页
- 准备两类样本会话
  - 样本 A：院校专业组模式
  - 样本 B：专业+大学模式

建议每个案例都记录：

- 输入话术 / 操作
- agent 返回内容
- 右侧目标视图是否切对
- 是否自动刷新
- 数量口径是否正确
- 是否出现重复弹窗、错误 fallback、需要手动刷新才看到消息

## 推荐先跑脚本化真实对话回归

在做前端手工联调前，建议先跑一轮本地真实 websocket 回归，先确认 agent / service / compat 协议链路没有明显跑偏。

脚本：

```bash
./.venv/bin/python examples/dialog_regression_runner.py
```

按指定 session + prompts 临时跑：

```bash
./.venv/bin/python examples/dialog_regression_runner.py --session 35 --prompts "方案有了么" "帮我审查一下"
```

这个脚本会直接走：

- `/gaotu-assistant-agent/plus/chat/1/bot/test/do`

并打印：

- thinking 进度
- 最终 text 回复
- follow-up `planningWorkspaceAction`

推荐用法：

1. 先挑“短历史会话”做干净验证
2. 再挑“已有方案会话”做现状 / 审查 / 重排验证
3. 最后再到前端做人工体验确认

## 推荐执行顺序

如果要用真实前端 + backend + agent 手工联调，建议按下面顺序跑，而不是随机提问：

1. 先验证初始方案是否正常生成
2. 再验证 Explore 阶段是否先分析、不乱改状态
3. 再验证偏好 / 要求确认与右侧联动
4. 再验证方案现状 / 风险 / 调整建议 / 补齐建议
5. 最后验证多轮连续对话和候选加入方案

这样更容易定位问题到底出在：

- 初始方案生成
- Explore / Intent 编排
- Plan 编排
- 前端工作台联动
- 多轮历史继承

## 真实联调话术包

下面这组话术可以直接按顺序在真实页面里跑。每轮都建议记录：

- 左侧回复是否自然
- 右侧有没有错误联动
- 是否需要手动刷新才看见消息
- 方案 / 候选 / 草稿数量是否正确

注意优先使用真实用户会说的话术，不要过度依赖“审查 / 重排 / 补偿”这类产品内部术语。像“这版有啥问题”“贵的先去掉”“现在少的这些咋补”“帮我顺一下”更接近真实对话。

### 话术包 A：现状 -> 风险 -> 调整建议

- `现在方案怎么样`
- `哪里还不合理`
- `怎么优化`

预期：

- 第一句先回答当前方案状态
- 第二句先回答风险和提醒，不直接跳执行
- 第三句给建议概览，不直接重排 / 补偿 / 替换
- 三轮都应围绕同一份当前方案，不应丢上下文

### 话术包 B：补齐建议 -> 应用前确认

- `还差的几个怎么补`
- `帮我补几个更稳的`
- `那直接应用吧`

预期：

- 第一句只返回“怎么补”的建议预览，不应直接应用
- 第二句应先提示这是高副作用动作，需要确认
- 不应在未明确确认前静默改动右侧方案

### 话术包 C：重排 -> 确认

- `帮我重排一下`
- `确认`

预期：

- 第一轮先说明这是整体改动，需要确认
- 第二轮才允许进入执行语义
- 不应第一句就直接把顺序改掉

### 话术包 D：Explore -> 偏好 -> 方案复盘

- `体制内适不适合`
- 点击“记成偏好” / 采纳
- `那现在方案哪里更贴近`

预期：

- 第一轮先做方向分析，不直接说已记录
- 采纳后不回显原始 JSON
- 第三轮回答应围绕当前方案和候选机会，不是旧 `simulate_diff`

### 话术包 E：现状讨论后再提要求

- `现在方案稳不稳`
- `不去上海`
- 点击采纳
- `看看候选`

预期：

- 第二轮仍能正确切到“要求”确认
- 采纳后右侧候选应被收紧
- 最后一轮查看候选时应承接筛后结果

### 话术包 F：专业组 / 专业+大学双模式对照

建议在两个会话上各跑一遍：

- `现在方案怎么样`
- `怎么优化`
- `帮我重排一下`

对照重点：

- 专业组模式数量口径按组
- 专业+大学模式数量口径按志愿条目
- 草稿 / 方案 / 候选展示口径一致
- 不出现专业组模式下按专业条目统计的错口径

### 话术包 G：口语化主线闭环

- `直接给我弄一版`
- `确认`
- `这版有啥问题`
- `贵的先去掉`
- `确认`
- `现在少的这些咋补`

预期：

- “这版有啥问题”应走方案审查，不要求用户使用“审查”术语
- “贵的先去掉”应承接上一轮风险，按整批高收费项给出移除预览范围
- 确认后应真实移除，并重新给出数量缺口和复审结果
- “现在少的这些咋补”应走补齐建议预览，不应退回局部查询
- 同类变体如 `这版没啥大问题吧` 也应仍按审查/风险复盘理解，不要退回泛状态播报

### 话术包 H：口语化分析 -> 直接重排

- `直接给我弄一版`
- `确认`
- `这版怎么排更合适`
- `那你直接帮我顺一下`
- `确认`

预期：

- “这版怎么排更合适”应先给分析建议，不直接改方案
- “那你直接帮我顺一下”应识别为整体重排，不应误跳到高收费处理或其他局部动作
- 第二个“确认”前必须先有重排 preview，可复用 pending payload
- 同类变体如 `那接下来该怎么弄更稳` 应先给分析建议，不应直接静默执行改动

## 场景 1：初始方案稳定性

### 案例 1A：院校专业组模式自动生成初始方案

- 前置
  - 新建会话，基础信息采集完成
  - 用户省份为院校专业组模式
- 操作
  - 进入会话详情页，不做额外手动筛选
- 预期
  - 左侧显示“方案”，右侧显示“候选”
  - 系统自动出现一版初始方案
  - 方案数量按“专业组数”统计，不按专业条目数统计
  - 冲稳保分布、总数、摘要与后端状态一致
  - 组内专业不重复
  - 不出现“只有 13 个组但某校展开 54 个专业”这类异常

### 案例 1B：专业+大学模式自动生成初始方案

- 前置
  - 新建会话，基础信息采集完成
  - 用户省份为专业+大学模式
- 操作
  - 进入会话详情页，不做额外手动筛选
- 预期
  - 系统自动出现一版初始方案
  - 方案数量按“志愿条目数”统计
  - 每个志愿展示学校 + 专业
  - 冲稳保比例没有明显断层
  - 不出现外部推荐系数异常低但被排到前列的问题

## 场景 2：兴趣阶段分析

### 案例 2A：地域兴趣分析

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`北京有哪些学校`
- 预期
  - 回复应先做兴趣阶段的信息分析 / 引导
  - 不应直接把它当成“已确认偏好”写入
  - 不应触发候选池重建
  - 如能联动右侧，应明确是查看候选，不是静默改方案

### 案例 2B：职业方向兴趣分析

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`体制内适不适合`
- 预期
  - 回复应先解释这个方向和当前方案、候选机会的关系
  - 不应直接捞一批学校当成最终答案
  - 不应直接说“已记下”
- 若给下一步动作，应是“继续看看方案是否贴近”“是否记成偏好”

### 案例 2C：地域 Explore 已有偏好时仍先分析

- 前置
  - 会话已有初始方案
  - 当前画像中已包含北京等地域偏好
- 操作
  - 用户输入：`北京的机会多一点吗`
  - 用户输入：`看看北京还有没有更合适的`
- 预期
  - 仍优先返回 `interestAnalysisPopup`
  - 不应回退到“还没准确整理出可调整的报考意向”
  - 不应仅返回“已经记下”的 `card`
  - 回答应聚焦“当前方案命中情况 + 候选里还能继续看的机会”

### 案例 2D：职业方向 Explore 稳定性回归

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`体制内这条路适合我吗`
  - 用户输入：`稳定就业方向值不值得重点看`
- 预期
  - 优先返回 `interestAnalysisPopup`
  - 不应退化成模型直接长答
  - 若 Explore tool 内部生成结构化分析失败，可接受 fallback 到模板化 `interestAnalysisPopup`
  - 不应跳过 Explore 直接进入偏好确认

## 当前遗留

- `稳定就业方向值不值得重点看` 仍存在偶发 plain text 长答，需要继续加强主 agent 对职业方向 Explore tool 的优先调用

## 场景 3：软偏好确认链路

### 案例 3A：地域偏好

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`更想去北京`
  - 在确认弹层中点击采纳
- 预期
  - 先弹确认，不直接生效
  - 采纳后，偏好生效
  - 不自动重建候选大池
  - 回复应是“当前方案命中情况 + 候选里还能继续看的机会”
  - 不应还是旧的 `simulate_diff` 口径

### 案例 3B：职业方向偏好

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`想进体制`
  - 点击采纳
- 预期
  - 先确认，再落偏好
  - 不应出现 `analyze_volunteer_intent_change received no structured intents` 式无结构化意向 fallback
  - 采纳后前端卡片状态置灰 / 置位
  - 回复不应回显原始 JSON
  - 方案分析后续能感知该方向偏好

## 场景 4：硬要求确认链路

### 案例 4A：排除地域要求

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`不去上海`
  - 点击采纳
- 预期
  - 明确走“要求”确认
  - 采纳后右侧候选立即切到带筛选的候选视图
  - 候选总量显示为“筛后数量 / 整体候选数量”
  - 不重建候选大池，只收紧当前视图

### 案例 4B：院校性质要求

- 前置
  - 会话已有初始方案
- 操作
  - 用户输入：`不要中外合作`
  - 点击采纳
- 预期
  - 确认后筛选栏出现对应条件
  - 候选区自动刷新
  - 回复能继续引导检查“当前方案里是否还有不满足要求的项”
  - 不应只更新画像不更新右侧视图

## 场景 5：方案查询与分析

### 案例 5A：查询当前方案状态

- 前置
  - 会话已有方案
- 操作
  - 用户输入：`现在方案怎么样`
- 预期
  - 回复聚焦当前方案，不是简单列学校
  - 包含总数、冲稳保、风险 / 提醒、阶段性结论
  - 院校专业组模式下数量口径按组

### 案例 5B：查询当前风险

- 前置
  - 会话已有方案，且存在 review / planAdjust 信息
- 操作
  - 用户输入：`哪里还不合理`
- 预期
  - 回答风险点、提醒点、梯度 / 保底 / 顺序等分析
  - 不应再提“专业组数量不足”这种已废弃逻辑
  - 回答内容与右侧审查数据一致

## 场景 6：方案调整建议

### 案例 6A：用户询问优化建议

- 前置
  - 会话已有方案
- 操作
  - 用户输入：`怎么优化`
- 预期
  - 返回补充 / 替换 / 顺序调整建议
  - 建议应基于当前方案真实问题
  - 不应重复提出“初始方案本该已解决的问题”

### 案例 6B：用户询问怎么补齐

- 前置
  - 会话已有方案，存在可补偿动作
- 操作
  - 用户输入：`还差的几个怎么补`
  - 用户输入：`帮我补几个更稳的`
- 预期
  - 返回可补齐动作数、主要动作、预计补入数量
  - 右侧视图切换符合设计
  - 不自动 apply，仍需用户确认

## 场景 7：候选加入方案 / 草稿

### 案例 7A：专业组模式从候选加入 2 个组

- 前置
  - 候选中存在两个北京的专业组
- 操作
  - 在候选区点击加入方案 / 草稿
- 预期
  - 草稿按专业组聚合展示
  - 方案和草稿同步更新
  - 数量口径按组，不按专业条目
  - 顶部提示不应仍说“系统初始底稿”

### 案例 7B：专业+大学模式加入若干志愿

- 前置
  - 候选区可选中多个专业+大学志愿
- 操作
  - 连续加入 2 到 3 个志愿
- 预期
  - 方案尾部自动追加
  - 草稿显示正常，不错位
  - 用户可继续手动排序完整方案

## 场景 8：调整后复盘

### 案例 8A：偏好生效后复盘

- 前置
  - 已采纳“更想去北京”
- 操作
  - 用户输入：`现在方案受了什么影响`
- 预期
  - 回答当前方案命中部分、一般部分、候选里潜在更优机会
  - 不再使用旧的 `simulate_plan_diff`
  - 不应直接给技术化字段或模板化列表

### 案例 8B：要求生效后复盘

- 前置
  - 已采纳“不去上海”
- 操作
  - 用户输入：`现在方案里还有没有不符合的`
- 预期
  - 回答当前方案是否仍有不满足要求的项
  - 必要时引导用户进一步调整方案
  - 右侧候选仍保持收紧后的视图

## 场景 9：多轮连续对话稳定性

### 案例 9A：兴趣 -> 采纳偏好 -> 查方案

- 操作
  - `体制内适不适合`
  - 点击“记成偏好”
  - 再问：`那现在方案哪里更贴近`
- 预期
  - 各步语义衔接稳定
  - 不重复弹确认
  - 不出现 fallback 误抽学校 / 专业 / 地域

### 案例 9B：方案讨论后再提要求

- 操作
  - `现在方案稳不稳`
  - `不去上海`
  - 点击采纳
  - `看看候选`
- 预期
  - 第二步仍能正确进入要求确认链路
  - 第三步后右侧候选视图被收紧
  - 不需要手动刷新对话才出现新消息

## 场景 10：双模式对照

### 案例 10A：院校专业组模式全链路

- 操作
  - 初始方案生成
  - 询问兴趣方向
  - 采纳偏好
  - 查询方案
  - 从候选加入 1 个组
- 预期
  - 全链路数量口径按组
  - 草稿、方案、候选展示都是组聚合
  - 组内专业不重复

### 案例 10B：专业+大学模式全链路

- 操作
  - 初始方案生成
  - 询问某专业兴趣
  - 采纳偏好
  - 查询方案
  - 从候选加入 1 个专业志愿
- 预期
  - 全链路数量口径按志愿条目
  - 方案与候选展示学校 + 专业
  - 不受专业组模式逻辑污染

## 当前自动化覆盖到的部分

以下部分已经有 agent 侧自动化测试覆盖，但仍需要联调确认前端呈现与真实数据效果：

- 初始方案数量口径
- 偏好 / 要求确认链路
- 兴趣阶段后续动作
- 方案查询 / 调整建议
- 候选加入方案 / 草稿后的 workspace action
- 多轮对话稳定性
- Plan 最终回复风格 guard：`execute_plan_action` 后会清理标题块、emoji、编号选项和强迫式决策文案
- Plan 状态查询主链：`query_state` 默认执行读取 planningState，不再停在 analyze/preview 空结果
