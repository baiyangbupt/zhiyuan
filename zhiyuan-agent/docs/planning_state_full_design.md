# 高考志愿规划状态与人机协同方案设计

## 1. 背景与问题定义

当前系统已经具备较强的自动推荐能力：

- `gaotu-assistant-rank` 基于专家经验为院校、专业、院校专业组进行打分
- `gaotu-assistant-backend` 基于冲稳保分层、梯度与保底规则汇总方案
- `gaotu-zy-agent-v3` 通过对话承接用户诉求
- `gaokao-assistant-pc` 提供前端采集、查看和操作入口

但现状存在三个核心问题：

1. 用户只能通过“表达意图 -> 系统固定提权/降权”的方式间接干预结果，缺少直观、确定、可回溯的控制手段。
2. 用户在前端采集流程中已经提供的画像信息，尤其是优势学科、未来发展、兴趣性格、家庭情况等，并未稳定沉淀为统一的会话初始画像，对话和后续规划无法充分继承这些信息。
3. 自动生成方案、用户手动调整、审查与补偿之间没有统一状态承载，导致系统难以理解“用户已经做了什么”“下一步应该做什么”。

因此，需要将现有系统升级为以统一 `planningState` 为中心的人机协同规划模式。

补充说明：

- 当前推荐、打分、区间分层、两种志愿模式差异以及专业组内部规则的现状梳理，见
  [planning-recommendation-current-state.md](/Users/baiyang/git/zhiyuan/gaotu-assistant-backend/docs/planning-recommendation-current-state.md)
- 跨 rank / backend / agent / frontend 的标签统一治理约定，见
  [tag-governance.md](/Users/baiyang/git/zhiyuan/gaotu-assistant-backend/docs/tag-governance.md)

## 2. 总体目标

目标不是简单让用户手工拖拽志愿，而是把系统的专家能力拆解为可感知、可干预、可验证的基础能力：

- 选取：从候选池中选出进入当前方案的志愿
- 排序：按照冲稳保、梯度、保底和用户意向整理最终顺序
- 审查：对当前方案做风险校验、数量校验和限制项提示
- 补偿：在数量不足、梯度断层、保底不足等情况下自动补齐或引导补齐

系统默认继续保留专家自动模式，但同时支持用户在界面和对话中直接干预。

## 3. 设计原则

- 专家逻辑优先：候选生成、分层、梯度、保底、安全性仍以专家经验规则为基础。
- 用户意向可显式干预：不再仅依赖固定权重调节，而是允许用户明确选、删、锁、调序、固定位置。
- 自动与手动可共存：系统既能自动生成，也要感知用户手动操作，并据此决定下一步动作。
- 状态单一来源：所有规划过程统一沉淀到 `planningState`，避免信息散落在多个响应和上下文中。
- 分阶段落地：先搭状态和最小闭环，再接审查、补偿、agent 编排和前端联动。
- 每一阶段都必须带验证：接口验证、单元测试、集成验证、关键路径回归测试同步建设。

## 3.1 三类用户诉求链路

在整体方案中，需要把用户诉求明确区分为以下三类：

### A. 临时查看

例如：

- “看看北京有哪些计算机相关志愿”
- “先筛一些稳区里的师范类”
- “有没有学费低一点的可以看看”

这类诉求的目标是查看信息，不是改变后续方案。

设计要求：

- 可由对话直接回答或总结
- 也可联动右侧候选面板临时筛选
- 不更新画像
- 不更新推荐系数
- 不影响草稿、排序、审查

### B. 方案偏好

例如：

- “更想去北京”
- “不太想去山西”
- “更看重就业”
- “可以多关注计算机周边专业”
- “想留本省”
- “想去一线城市”
- “不想只进体制内”

这类诉求的目标是影响系统后续推荐，但不是强制缩小所有可选空间。

设计要求：

- 先与用户确认是否纳入后续推荐考虑
- 写入 `planningState.profileState`
- 影响专家推荐系数、专家优选组合、默认推荐顺序
- 原则上不直接改变候选基础池成员
- 可以提示用户去右侧候选区按这个方向手动筛选查看，但不自动替用户修改当前筛选状态

### C. 方案约束

例如：

- “只报计算机相关专业”
- “不报中外合作”
- “不去北京”
- “学费必须低于某个阈值”
- “只去北上广”
- “就想学工科方向”
- “不去体制外”
- “绝对不学医”

这类诉求的目标是对方案施加强约束。

设计要求：

- 进入约束层
- 先与用户确认
- 确认后优先联动右侧候选面板筛选，让用户看到候选数量和范围如何收缩
- 同步写入长期状态，继续影响专家推荐、草稿、排序、审查
- 连带影响后续推荐、草稿、排序、审查
- 是否进一步重建候选基础池，应建立在用户已经感知筛选结果变化的基础上

## 3.2 报考状态的双层作用方式

这里需要把“用户一句话的报考状态”拆成两个作用面：

- 候选面板筛选层
- 推荐与排序承接层

### A. 候选面板筛选层

目标是让用户感知变化。

- 硬状态在确认后自动作用到这里
- 系统直接帮用户填充筛选条件
- 自动切到候选区
- 刷新对应区间或全部候选数量
- 让用户看到“筛除之后还剩什么”

### B. 推荐与排序承接层

目标是让后续专家逻辑持续生效。

- 硬状态、软状态在确认后都会写入这一层
- 影响专家推荐系数
- 影响专家优选组合
- 影响默认排序倾向
- 影响后续审查与补偿建议

### C. 正负向与硬软四象限

需要统一支持四类表达：

- 正向硬：`只去北上广`、`就想学工科方向`
- 负向硬：`不考虑留省内`、`不去南方`、`不去体制外`、`绝对不学医`
- 正向软：`想上计算机`、`想留本省`、`想去一线城市`、`想找薪资高的`
- 负向软：`不想留本省`、`不太想去南方`、`不想只进体制内`、`可以不考研`

其中：

- 硬的：确认后自动联动候选面板 + 更新后续推荐承接层
- 软的：确认后只更新后续推荐承接层，并提示用户可去候选面板手动筛选查看

## 3.3 对话主流程框架

`sessionDetailV2` 下的对话交互，不应默认把“用户提到一个方向词”直接等价成“要改方案”。

更合理的设计是把用户诉求拆成：

- 先对某个方向、词汇或对象产生兴趣
- 再查看相关信息与候选结果
- 再决定是否沉淀为软意向或硬约束
- 最后在用户明确提出“要动方案”时进入方案编排

因此整体主流程建议拆成三层：

### A. 主题层

负责识别用户当前在谈什么：

- 地域
- 院校
- 专业
- 招生类型
- 限报要求
- 目标偏好
- 方案动作

### B. 交互层

负责决定当前应该怎么回应：

- 先解释和回答
- 联动右侧候选/详情/方案面板
- 发偏好确认卡
- 发约束确认卡
- 输出方案分析、调整建议或执行结果

### C. 状态层

负责决定哪些内容写入长期状态，哪些只作为一次查看：

- 临时查询不落主状态
- 软意向确认后进入推荐承接层
- 硬约束确认后进入推荐承接层，并联动候选视图层
- 方案动作只在用户显式触发时才进入编排

## 3.4 四类对话诉求

建议把对话统一收口到以下四类：

### A. `Explore`

典型场景：

- “北京有什么学校”
- “计算机类都有哪些”
- “华南理工怎么样”
- “专项计划有哪些”

设计要求：

- 默认先做信息承接
- 优先联动右侧候选区或详情区
- 不改画像
- 不改候选基础池
- 不改方案

补充说明：

- 更泛化的“从候选里查还有什么可选”的语义，统一归到 `Explore`
- 这类查询可视为 `CandidateQuery`
- 其职责是查看候选、筛选结果和单个方向下的可选空间，而不是查看当前方案现状

补充约定：

- 当用户只是对某个方向、词汇或对象产生兴趣时，不应直接把回答收敛成“会影响系统优选”这类推荐层播报
- 更合适的做法是先输出一层“方案关联分析”，帮助用户理解这个方向与当前方案、当前候选之间的关系
- 这层分析的目标是帮助用户继续往前想，而不是立刻把该方向沉淀为正式偏好或约束

### B. `Prefer`

典型场景：

- “更想去北京”
- “优先看计算机”
- “更看重就业”
- “不太想去山西”

设计要求：

- 先识别为软意向
- 需与用户确认
- 确认后写入后续推荐承接层
- 影响推荐系数、专家优选组合和后续方案建议
- 不自动联动当前候选筛选栏
- 不自动修改方案

补充约定：

- 在用户确认前，`Prefer` 不应直接展示“新增优选 / 移出优选”这类旧口径影响文案
- 更合理的反馈应先说明：
  - 当前方案里是否已经命中这类偏好
  - 命中的分布是否集中、是否足够
  - 候选里是否存在更值得进一步看的补充机会
- 用户确认后，也不直接把结果描述成“系统优选变化”，而是描述“这条偏好与当前方案状态的关系”

### C. `Constrain`

典型场景：

- “不去北京”
- “不报中外合作”
- “只看公办”
- “学费不能太高”

设计要求：

- 先识别为硬约束
- 需与用户确认
- 确认后同步联动候选面板筛选栏
- 让用户直接看到结果范围变化
- 同时影响后续推荐、排序、审查
- 不自动修改方案

补充约定：

- 在用户确认前，`Constrain` 的预览重点不是“会移出哪些优选”，而是：
  - 当前方案里是否已有命中这条约束的项
  - 当前候选里按这条约束筛完大概还剩多少
  - 若采纳后，后续方案分析会重点检查哪些冲突点
- 用户确认后，反馈重点应放在：
  - 当前方案里已有多少项与该约束冲突
  - 当前候选视图已如何收缩
  - 是否存在可承接的替代机会
  - 下一步是否需要进一步分析或重排

### D. `Plan`

典型场景：

- “看看方案有什么问题”
- “怎么调更合理”
- “给我出一版方案”
- “按这个重排一下”

设计要求：

- 只有明确出现方案诉求时才进入
- 与 `Explore / Prefer / Constrain` 严格区分
- 进入后按细分方案动作继续编排

## 3.5 五类方案动作

进入 `Plan` 后，建议继续细分为五类能力。

### A. `PlanQuery`

职责：

- 仅查看当前方案层现状
- 不做分析
- 不改方案

包含：

- 当前草稿
- 当前排序结果
- 当前审查结果摘要
- 当前调整建议摘要

不包含：

- 更泛化的候选查询
- 某个地域、院校、专业方向下“还有哪些可选”
- 临时候选筛选结果查看

### B. `PlanAnalyze`

职责：

- 诊断当前方案是否存在问题
- 输出风险、断层、结构性问题
- 不直接给执行动作

### C. `PlanAdjust`

职责：

- 基于当前方案生成调整建议
- 可输出补充、替换、顺序调整、梯度修补建议
- 默认先给建议，不自动应用

### D. `PlanGenerate`

职责：

- 基于当前画像、约束、候选视图和推荐状态生成一版方案
- 适用于没有明确方案或希望系统重新给一版方案的场景

### E. `PlanReorder`

职责：

- 在已有草稿或已有方案的基础上重新排序
- 重点处理“怎么排”，而不是“要不要补和换”

## 3.5.2 方案关联分析

在 `Explore / Prefer / Constrain` 与正式 `PlanAnalyze / PlanAdjust` 之间，需要补一层更轻的“方案关联分析”。

这层能力的目标不是直接改方案，也不是只播报推荐覆盖层变化，而是帮助用户理解：

- 当前方案和这个方向的关系
- 当前候选里有没有更值得继续看的机会
- 下一步更适合继续确认偏好 / 约束，还是直接进入方案分析

### A. 兴趣阶段分析

适用场景：

- 用户刚对某个方向表达兴趣
- 还没有明确要求把它沉淀成偏好或约束
- 也还没有明确说要改方案

例如：

- “北京怎么样”
- “我对计算机有点兴趣”
- “中外合作值不值得看”
- “不太想去北方”

这时系统应先输出“兴趣阶段分析”，而不是直接说：

- “这会影响系统优选”
- “后续优选会增加 / 减少哪些项”

更合理的分析维度是：

- 当前方案里有没有已经命中这个方向的项
- 命中的区间分布如何
- 命中质量是偏弱、一般还是已经比较集中
- 当前候选里有没有还没纳入方案、但更值得往前看的项
- 如果用户继续推进，更适合沉淀为软意向、硬约束，还是只继续查看

### B. 确认后的状态分析

适用场景：

- 用户已经确认把某条内容纳入偏好或约束
- 系统需要告诉用户“这条要求与当前方案状态的关系”

这时也不应继续沿用“新增优选 / 移出优选”的旧口径。

更合理的输出应围绕以下四块：

- `currentPlanFit`
  - 当前方案里哪些部分已经符合这条偏好 / 约束
- `currentPlanConflict`
  - 当前方案里哪些部分与这条约束冲突，或对这条偏好覆盖不足
- `candidateOpportunity`
  - 当前候选里是否存在更适合但尚未纳入的补充 / 替换机会
- `nextActionHints`
  - 下一步建议是继续查看候选、继续分析方案，还是直接发起重排 / 调整

例如用户确认“不要北京”后，更合适的反馈是：

- 当前方案里是否还有北京院校 / 专业组
- 当前候选按这条约束筛完还剩多少
- 是否已有可替代机会
- 如果继续往前走，建议先看冲突项还是直接重排

而不是直接反馈：

- 新进入优选哪些
- 移出优选哪些

### C. 与正式方案分析的边界

这层“方案关联分析”是轻分析，不等价于正式 `PlanAnalyze / PlanAdjust`。

边界如下：

- `方案关联分析`
  - 解决“这个方向和我当前方案是什么关系”
  - 解决“当前候选里还有没有更好的机会”
  - 不直接给出完整的 add / replace / reorder 结构化建议

- `PlanAnalyze`
  - 解决“当前方案是否存在结构问题或风险”

- `PlanAdjust`
  - 解决“如果真要调，应该怎么补、怎么换、怎么挪”

换句话说：

- `方案关联分析` 是用户从兴趣 / 意向继续往前推进时的思考层
- `PlanAnalyze / PlanAdjust` 才是明确进入方案动作后的正式分析层

## 3.5.1 对话入口路由分层

`sessionDetailV2` 当前对话入口不再只依赖单层 prompt 自由判断，而是采用三层串联：

1. 强规则短路层
2. 语义预路由层
3. 主 `ChatAgent` 编排层

### A. 强规则短路层

用于承接最明确、最不应该漂移的表达：

- 明确报考意向表达
- 明确方案动作表达

例如：

- “不去北京”
- “给我出一版方案”
- “按这个重排一下”

这层以规则和显式短语优先，目标是降低高频明确请求被主 Agent 误分发的概率。

### B. 语义预路由层

用于承接规则没覆盖到、但语义上已经足够明确的高价值请求。

当前第一阶段只覆盖：

- `Prefer`
- `Constrain`
- `PlanGenerate`
- `PlanAdjust`

边界约束：

- 只做高置信度命中
- 低置信度一律回退主 `ChatAgent`
- 不承接泛信息查询
- 不替代主 Agent 的完整多轮推理

例如：

- “我更想去北京”
- “计算机优先考虑”
- “给我整一版适合我的方案”
- “这个方案还能怎么优化”

### C. 兴趣阶段编排状态机

为了避免用户刚提到一个方向时，系统立刻切成“确认卡 + 采纳”模式，`Explore / Prefer / Constrain` 之间需要补一层显式的编排状态机。

当前建议的最小状态如下：

- `interest_detected`
  - 用户刚提到一个方向、概念、词汇或偏向
  - 系统先判断这是“想了解”还是“想沉淀成要求”
- `interest_analyzed`
  - 系统已经给出一层轻分析
  - 用户此时可以继续问信息，也可以继续推进成偏好 / 要求
- `intent_confirm_pending`
  - 系统已经明确整理出可采纳的偏好 / 要求项
  - 等待用户显式采纳
- `intent_confirmed`
  - 用户已经采纳
  - 之后可以进入候选查看、方案分析、方案调整或方案生成

## 3.5.2 对话工具分层约定

为避免后续实现再次把“意向抽取、对话预览、最终回复”混写到同一个模块，当前对话侧需要统一遵守三层分工。

### A. Core 层

Core 层只负责业务事实和状态执行，不负责最终面向用户的话术组织。

当前对应：

- `app/tools/intent_state_tool.py`

核心职责：

- 意向抽取恢复与结构整理
- 当前方案 / 候选关联分析事实生成
- 缓存待确认意向
- 显式画像与 latent profile 更新
- 约束确认后的候选过滤信息计算

当前核心入口：

- `analyze_volunteer_intent_change`
- `apply_selected_intents`（仅由统一 pending confirmation 触发：卡片点击为主入口，active pending 短文本确认为兜底入口）
- `update_volunteer_intent_state`（legacy wrapper，仅用于历史兼容，不再暴露给主 Agent）

约束：

- 允许返回结构化 JSON
- 不要求在这里生成最终自然语言答复
- 不应继续承担 Explore 预览 wrapper 的职责
- 不应反向 import Explore follow-up 编排；兴趣阶段按钮或后续动作由 Service / Explore 层分流

### B. Preview 层

Preview 层是面向 Agent 的便捷入口，用于把“当前这句话”快速映射为某类可解释的分析结果，但本质上仍建立在 Core 层之上。

当前对应：

- `app/tools/intent_preview_tool.py`

核心职责：

- 承接 Explore 阶段的轻分析入口
- 承接一句明确偏好 / 要求时的确认预览入口
- 把“当前对话上下文”转换成对 Agent 更好调用的预览工具

当前入口包括：

- `analyze_current_interest`
- `analyze_current_career_direction`
- `preview_interest_analysis_from_request`
- `preview_current_intent_confirmation`
- `preview_direction_analysis_from_request`
- `preview_direction_comparison_from_request`

约束：

- 这是对话编排便捷层，不是状态单一来源
- Preview 层可以组合 Core 层能力，但不应反向写入新的业务状态语义

### B.1 Explore Follow-up 层

Explore follow-up 层承接兴趣分析后的按钮或继续动作，不属于 Core 状态执行层。

当前对应：

- `app/tools/explore_followup_tool.py`

核心职责：

- 从待确认缓存中读取刚才的兴趣 / 意向上下文
- 处理 `candidate_query`、`plan_analyze`、`prefer_confirm`、`constrain_confirm` 等兴趣阶段后续动作
- 必要时调用 Core 层的 `analyze_volunteer_intent_change` 生成确认事实
- 不直接承担画像或 latent profile 的最终写入

当前调用边界：

- WebSocket 选择类入站消息统一进入 `ChatService.handle_intent_select`
- 如果 payload 带 `actionType`，由 Service 分流到 Explore follow-up
- 如果 payload 带 `selected` / `message_id`，由 Service 分流到 Core 的选择采纳执行

### C. Response 层

Response 层负责响应模型、兼容序列化和必要的文本渲染收口。

当前对应：

- `app/tools/intent_response_tool.py`

核心职责：

- `IntentAnalysisPayload`
- `IntentStateUpdateResult`
- `ExploreFollowupResult`
- 结构化结果序列化 / 反序列化
- 兼容旧调用方的文本渲染

约束：

- Response 层不做业务判断
- 只负责把已有事实整理成兼容输出

### D. Agent / Skill 的使用约定

主 `ChatAgent` 与 skill 在当前阶段应遵循以下约定：

- Agent 先判断用户当前更像 `Explore / Intent / Plan` 哪一层
- 如果只是探索某个方向是否适合、值不值得继续看，优先调用 Preview 层工具
- 如果已经拿到了结构化偏好 / 要求，或需要更完整的确认事实，优先调用 Core 层的 `analyze_volunteer_intent_change`
- 如果用户点击了统一确认卡，或短文本确认通过 active pending 校验，Service 才调用 `apply_selected_intents` 执行写入；没有 active pending 的自然语言“确认”不触发写入
- 最终发给用户的自然中文回复，由模型结合工具结果自行组织

换句话说：

- Core 提供事实与执行
- Preview 提供对话入口
- Response 提供兼容承接
- Agent / Skill 负责真正的业务编排与最终表达

### E. 当前落地状态

截至当前版本，已经完成以下收敛：

- `intent_state_tool` 不再同时承载 Explore wrapper、最终文案拼接和核心状态执行三类职责
- `intent_state_tool` 不再反向依赖 `explore_followup_tool`
- Service 层新增 `handle_intent_select` 作为新的选择类入站入口，旧 `handle_plan_edit_select` 仅保留兼容
- Core 层新增 `apply_selected_intents` 作为“局部采纳后执行状态更新”的结构化入口，返回 `IntentStateUpdateResult` JSON；旧 `handle_plan_edit_select` 仅作为文本渲染兼容别名
- `interestAnalysisPopup` 的 `prefer_confirm / constrain_confirm` 快捷动作已经收口为二次生成 `pendingConfirmationCard`，不直接写入后续报考参考
- Service 不再通过中文回复文本判断是否刷新候选，而是读取 `IntentStateUpdateResult.intentMode` 与 `candidateFilters` 后触发候选视图动作
- Explore / Intent 的预览 wrapper 已迁移到 `intent_preview_tool`
- 职业方向识别与方向适配分析统一收敛到 `explore_direction_tool`，`intent_state_tool` 不再保留重复的方向匹配 / 方向分析实现
- `explore_direction_tool` 的方向相关性判断已集中为“方向证据”计算，当前仍是启发式事实层，不作为对话路由；后续可替换为统一标签体系评分或模型评估
- Explore follow-up 新增结构化入口 `handle_interest_analysis_action_result`，Service 主链路已直接消费 `ExploreFollowupResult`；旧 `handle_interest_analysis_action` 仅作为文本渲染兼容包装
- 响应模型与文本渲染已迁移到 `intent_response_tool`
- `impactAnalysis` 只作为结构化事实源保存当前方案命中 / 冲突、候选机会和工具侧下一步建议；用户可见层统一由紧凑 formatter 抽取最多两条具体影响事实，不再把 `summaryTitle` 和四段分组标题逐层展示。没有真实影响事实时，确认卡片或分析卡片不显示影响区。
- 地域意向按软硬语义分别处理：软偏好用 `intentMode=preference`，例如“不太想去江苏”会写入待确认的 `negative_province=江苏`，代表降低优先级或后续分析参考；硬要求用 `intentMode=constraint`，例如“不要江苏 / 必须排除江苏”才作为排他约束。当前方案或候选的局部命中查询只是证据，不能替代 Intent 预览或确认卡片；`query_volunteer_plan` 成功结果默认交回主模型综合，避免任何专业、院校、地域偏好表达被局部列表截断。
- Tool Reply Policy 不再全局信任工具返回的 `reply_strategy=direct_reply`：Policy、适配匹配、方案/候选局部查询等只读结果都必须回到主模型综合；只有确认预览、受控阻断、无变化和方案变更预览等协议级结构化结果可以直返。
- Plan apply 只认服务端 pending 确认上下文：`RequestContext.confirmed_via_pending=true` 且 pending 类型与 action family 匹配时，`execute_plan_action` 才允许高副作用动作执行；卡片点击会带 `confirmed_via_card=true`，短文本兜底会带 `confirmation_entry=short_text`。自然语言“确认 / 执行 / 好的”本身不是确认凭证，只能在 active pending 校验通过后由服务层转换为 pending 确认。
- `ChatAgent` 已按新分层挂载：
  - Core：`analyze_volunteer_intent_change`、`apply_selected_intents`（Service 内部确认后调用）
  - Preview：`analyze_current_interest`、`analyze_current_career_direction`、`preview_current_intent_confirmation`

### F. 后续继续收敛的方向

当前仍有两类内容可以继续往更清晰的结构推进：

- Response 层里仍保留部分兼容旧调用方的文本渲染逻辑，后续可进一步弱化
- Agent / Skill 虽然已经切到新分层，但真实多轮对话中的 `Explore -> Intent -> Plan` 切换仍需继续做端到端验证

1. 用户先提一个方向
2. 若更像了解或试探，进入 `interest_detected`
3. 系统返回“兴趣阶段分析”，进入 `interest_analyzed`
4. 若用户继续表达明确倾向 / 排除，或明确同意沉淀，进入 `intent_confirm_pending`
5. 用户采纳后进入 `intent_confirmed`
6. 之后再根据用户诉求进入：
   - `CandidateQuery`
   - `PlanQuery`
   - `PlanAnalyze`
   - `PlanAdjust`
   - `PlanGenerate`
   - `PlanReorder`

#### C.1 何时停在兴趣阶段

以下表达默认优先停在兴趣阶段，而不是直接发确认卡：

- “北京怎么样”
- “中外合作值不值得看”
- “体制内适合我吗”
- “信息安全和自动化哪个好”
- “我对计算机有点兴趣”
- “不太想去北方”

这些表达的共同点是：

- 用户更像在试探或了解
- 用户还没有明确要求系统把它记成长期偏好
- 用户也没有明确要求立刻改候选或改方案

此时系统应先做三件事：

- 给出结合用户自身情况的适配判断
  - 兴趣
  - 性格
  - 学科优势
  - 家庭诉求
  - 未来发展倾向
- 给出方向本身的简要信息或判断
- 给出“这个方向和当前方案 / 当前候选”的轻分析
- 告诉用户下一步可以怎么推进

不应直接做的事情：

- 默认发确认卡要求采纳
- 直接改候选筛选
- 直接改当前方案
- 直接播报“优选增加 / 减少”

#### C.2 何时升级成确认卡

以下两类场景应从兴趣阶段升级到确认卡：

- 用户明确表达想沉淀成偏好
  - “我更想去北京”
  - “后面优先看计算机”
  - “我以后更看重体制内”
- 用户明确表达排除或硬要求
  - “不去北京”
  - “不考虑中外合作”
  - “以后不想往体制内走”

这里的规则是：

- 明确“更想 / 优先 / 更看重 / 偏向”时，优先进入 `Prefer`
- 明确“不去 / 不考虑 / 不要 / 排除”时，优先进入 `Constrain`
- 如果只是模糊兴趣，不升级

确认卡的目标不是“立刻改方案”，而是：

- 把用户刚说的内容整理成可采纳项
- 告诉用户这件事和当前方案 / 候选有什么关系
- 给用户一个明确的“是否采纳”分界线

#### C.3 采纳后的动作分流

`intent_confirmed` 并不等于自动改方案，而只是进入“可以继续做动作”的状态。

采纳后应按以下方式分流：

- 若是硬要求
  - 联动候选视图筛选条件
  - 不直接改当前草稿和排序方案
  - 后续更适合进入 `CandidateQuery / PlanAnalyze / PlanReorder`
- 若是软意向
  - 不直接联动候选筛选条件
  - 更新推荐理解与后续方案分析基线
  - 后续更适合进入 `PlanQuery / PlanAnalyze / PlanAdjust / PlanGenerate`
- 若是职业导向
  - 只更新 `latentProfile.futureDevelopment`
  - 不映射成院校 / 专业 / 地域筛选项
  - 后续更适合进入 `PlanAnalyze / PlanAdjust`

#### C.4 用户视角的一问一答节奏

从用户体验上，推荐采用下面的节奏：

1. 用户提一个方向
2. 系统先回答“这个方向和你本人的适配度 + 方向本身的特点”
3. 系统再补“当前方案 / 当前候选和这个方向的关系”
4. 系统再补充几个用户能直接理解的下一步动作
4. 用户确认后，系统再告诉他：
   - 去看候选
   - 看当前方案
   - 看方案建议
   - 直接让我重排 / 出一版方案

这样做的好处是：

- 用户不会觉得系统过度主动
- 用户不会误以为自己随口一句话就把方案改了
- 对话和右侧工作台能自然衔接

这里需要进一步明确：

- `Explore` 的主目标不是优先做方案命中分析
- `Explore` 的主目标应是先做“个性化方向适配分析”
- 方案层分析只是收尾补充，用来回答：
  - 当前方案有没有承接这条方向
  - 候选里还有没有更贴近的机会

因此在实现顺序上应优先读取：

- `latentProfile`
- `score_detail`
- `init_profile`

先形成“你为什么适合 / 不太适合这条方向”的解释，
再补 `orderedPlanState / candidatePoolState` 的方案层判断。

#### C.4.3 Explore 的最小可执行分析骨架

为了避免 `Explore` 退化成“先从当前方案里捞几个学校/专业”，需要把 Explore 的最小分析骨架进一步固定下来。

对下面这类问题：

- “体制内适不适合我”
- “我适合什么方向”
- “这个专业值不值得继续看”
- “北京的机会多不多”
- “如果看重就业，哪些方向更值得了解”

系统在 Explore 阶段的优先分析顺序应是：

1. `学生本人适配度`
2. `方向/对象本身的特点`
3. `当前方案承接情况`
4. `候选机会空间`

其中第 1 层应始终优先于第 3、4 层。

推荐最小事实骨架：

- `学生本人适配度`
  - 分数与当前竞争强度是否支持继续重点了解
  - 选科是否天然限制了后续空间
  - 当前画像中已知的兴趣、排斥项、地域倾向是否一致
  - 若有明显职业导向、风险偏好、学科优势，也应优先引用
- `方向/对象本身的特点`
  - 这个方向通常看重什么
  - 它更适合哪类学生继续重点了解
  - 当前只是“值得继续看”，还是已经接近“应纳入后续偏好”
- `当前方案承接情况`
  - 当前排序/草稿里是否已经有承接项
  - 如果有，承接是强还是弱
  - 如果没有，不要直接把“没有”当成否定结论
- `候选机会空间`
  - 候选里是否还有明显可继续看的机会
  - 如果有，只举少量最能说明问题的样本
  - 如果没有，也应告诉用户这是“当前没看到密集机会”，而不是简单说“没有”

这层骨架的目标是：

- 先回答“你为什么适合/不太适合继续看这个”
- 再回答“当前方案有没有承接”
- 最后才回答“还有哪些可以看”

不应出现的退化行为：

- 一上来先列学校/专业
- 整体回答只剩“方案里有/没有”
- 用候选样本替代对学生本人的分析
- 把“当前方案未命中”直接说成“你不适合”

#### C.4.4 Explore 的四种标准出口

Explore 阶段回答完之后，不应停留在“分析结束”这一层，而应稳定收敛到以下四种用户可理解的出口之一：

1. `继续了解`
   - 用户还在理解阶段
   - 更适合继续问方向、学校、专业、比较和适配度
2. `看候选机会`
   - 当前更适合去工作台看候选里有没有相关机会
   - 适合机会面较宽、需要浏览或继续筛选的场景
3. `看当前方案关系`
   - 当前更适合先看这条方向与现有方案的关系
   - 适合用户已经有方案，且问题核心是“现在这份方案是否承接”
4. `沉淀为后续偏好/要求`
   - 用户已经从“了解”进入“以后优先/以后不要”
   - 这时才适合进入 Intent 确认链路

对于仍停留在 `继续了解` 的场景，如果用户的问题明显在追问“我这个人到底适不适合什么方向 / 什么职业路径”，
系统可以把“更专业的评估”作为 Explore 的补充出口之一，但只应作为轻提示，而不应盖过当前分析主线。

推荐口径：

- 先完成基于分数、选科、画像、方案承接的初步判断
- 再提示：如果想做更细的人格与职业兴趣匹配，可进一步做 `MBTI` 与 `霍兰德职业兴趣测评`
- 测评结果后续可继续用于解释专业选择、职业方向和方案收口

约束：

- 不应把 `MBTI / 霍兰德` 变成 Explore 的固定结尾
- 不应把测评说成志愿分析的前置条件
- 不应在尚未完成当前问题分析前，直接把用户引走

这四种出口的设计目的不是增加更多按钮，而是约束 Explore 阶段的编排结果：

- 分析完后，系统必须帮助用户前进一步
- 但这一步前进仍应保持“先分析、后决定”
- 不应在 Explore 阶段直接静默改状态或静默改方案

从实现角度，Explore 阶段的自然收尾应尽量稳定回答三件事：

- `当前判断`
- `最值得关注的一两个原因`
- `现在更适合的下一步`

其中“下一步”只需落到上述四类之一，不要求每次都给多个分叉。

#### C.4.1 兴趣阶段卡的下一步动作文案

兴趣阶段卡不建议直接给出“记成偏好 / 记成要求”这类系统化表达。

原因：

- 用户不一定理解“偏好 / 要求”的系统含义
- 用户更容易从“我接下来想做什么”来理解按钮或动作
- 同一语义可以用更自然的话术承接

推荐的用户侧动作文案如下：

- `按这个方向继续看`
  - 用于继续停留在兴趣阶段
  - 适合 Explore 场景
- `先看看候选里有没有`
  - 内部映射到 `CandidateQuery`
  - 适合用户想先浏览机会
- `看看现在这份方案合不合适`
  - 内部映射到 `PlanAnalyze`
  - 适合用户想先评估当前方案和这个方向的关系
- `以后优先按这个方向看`
  - 内部映射到 `Prefer`
  - 语义等价于“沉淀为软意向”
- `以后别再给我推荐这类`
  - 内部映射到 `Constrain`
  - 语义等价于“沉淀为硬要求”
- `按这个条件筛一下`
  - 内部映射到 `Constrain + CandidateQuery`
  - 适合地域 / 院校性质 / 招生类型等能直接作用在候选视图层的场景

不推荐的用户侧文案：

- `记成偏好`
- `记成约束`
- `沉淀为软意向`
- `设为硬约束`

这些说法可以保留在内部设计和代码语义中，但不应直接暴露给用户。

#### C.4.2 用户侧动作文案与内部语义映射

建议建立一层“用户动作文案 -> 内部动作语义”的显式映射，而不是把内部语义直接暴露给前端。

推荐映射：

- `按这个方向继续看`
  - `actionType = interest_continue`
- `先看看候选里有没有`
  - `actionType = candidate_query`
- `看看现在这份方案合不合适`
  - `actionType = plan_analyze`
- `以后优先按这个方向看`
  - `actionType = prefer_confirm`
- `以后别再给我推荐这类`
  - `actionType = constrain_confirm`
- `按这个条件筛一下`
  - `actionType = constrain_and_candidate_query`

这样做的好处：

- 前端不需要理解 `Prefer / Constrain`
- 用户看到的是自然语言动作
- agent / backend 仍然可以稳定落到统一语义

当前已落地的第一版实现：

- `interestAnalysisPopup` 已补充用户侧动作按钮
- 首批动作文案采用：
  - `先看看候选里有没有`
  - `看看现在这份方案合不合适`
  - `以后优先按这个方向看`
- 为了不额外扩 websocket 入站协议，前端当前复用已有 `intentSelect` 入站类型，并在 payload 中显式透传 `actionType`
- 当前已落地的 `actionType` 包括：
  - `candidate_query`
  - `plan_analyze`
  - `prefer_confirm`
  - `constrain_confirm`
- `candidate_query` 当前只返回候选数量与筛选事实给对话回复使用，不自动触发右侧候选视图刷新；只有用户明确采纳“要求”后，才由 `planningWorkspaceAction.candidateFilters` 联动候选筛选栏
- `prefer_confirm / constrain_confirm` 当前先生成统一 `pendingConfirmationCard`；用户点击卡片采纳前不会写入后续报考参考，也不会刷新候选或方案
- 这样按钮点击不再依赖一条模糊自然语言去猜路由，同时也没有引入新的 websocket 协议分支
- 后续更换文案时，不会影响动作编排逻辑

#### C.5 实现顺序建议

这部分后续实现建议按下面顺序推进：

1. 先把 `interest_detected -> interest_analyzed -> intent_confirm_pending` 的边界收清楚
2. 再补“兴趣阶段回答”与“确认卡”两种返回协议的显式区分
3. 再把采纳后的动作分流接到 `CandidateQuery / PlanAnalyze / PlanAdjust`
4. 最后再做 richer 的多轮托管式方案生成

### C. 主 `ChatAgent` 编排层

其余请求仍进入主 Agent：

- `Explore`
- 普通知识问答
- 多轮澄清
- 复杂组合诉求
- 低置信度模糊表达

这样做的目标不是把入口路由做成一个大而全的分类器，而是：

- 先收口最容易漂移、又最值得稳定化的动作
- 再把复杂场景保留给主 Agent
- 避免入口层过早吞掉大量本应由多轮对话处理的请求

## 3.6 方案动作编排链

每个 `Plan` 动作建议遵循统一编排骨架：

1. 读取当前上下文
2. 判断前置状态是否齐全
3. 缺什么就补什么
4. 执行当前动作本身
5. 决定是只返回结果，还是继续引导下一步

补充约束：

- 用户一句“把这个删了”“把北京的往前放”“加一个北京工业大学”这类直接动作，不应默认机械执行
- 除非是低风险、强指向、可快速回滚的小动作，否则都应先走“分析当前影响 -> 审查风险 -> 给建议/预览 -> 用户确认 -> 执行 -> 执行后复盘”
- `固定 / 解锁` 这类系统内部动作不建议直接暴露给用户，不纳入用户侧主动作体系

## 3.7 五类直接改方案动作

围绕“当前方案”的用户直接改动诉求，建议收敛为以下五类用户可理解动作：

- 调位置
- 增加志愿
- 去掉志愿
- 替换志愿
- 局部重做

这些动作都属于 `Plan` 范畴，但不应与 `PlanAnalyze / PlanReview / PlanAdjustPreview` 混为一谈。更合理的关系是：

- `PlanAnalyze`
  - 负责回答“现在这版方案怎么样”“哪里不合理”“如果这么改会怎样”
- `PlanAction`
  - 负责执行或预执行“调位置 / 增加 / 去掉 / 替换 / 局部重做”
- `PlanReview`
  - 负责在执行前后复查梯度、安全垫、风险与提醒

### 3.7.1 调位置

典型表达：

- “把这个往前放”
- “这个放后面一点”
- “北京的放前面”
- “这两个换一下”

编排要求：

1. 先识别用户要动的是：
   - 单个志愿
   - 一组志愿
   - 一类志愿
2. 读取当前方案上下文：
   - 目标项本身
   - 相邻志愿
   - 当前冲稳保分布
3. 分析直接调位会不会造成：
   - 顺序倒挂
   - 梯度断层
   - 局部风险升高
4. 输出建议：
   - 直接这么调是否可行
   - 是否有更合理的位置
5. 用户确认后执行
6. 执行后复盘：
   - 哪些位置发生变化
   - 当前顺序是否更合理

执行分层：

- 小动作
  - 单个志愿上移 / 下移
  - 可以快速分析后确认执行
- 大动作
  - 一组前移 / 一类志愿整体前移
  - 应先给风险提示和替代建议

### 3.7.2 增加志愿

典型表达：

- “加一个北京工业大学”
- “把这个专业放进方案”
- “再补几个北京的”

编排要求：

1. 先识别增加目标是：
   - 明确志愿
   - 学校 / 专业方向
   - 一类候选
2. 查询候选里是否真实存在对应项
3. 分析增加后：
   - 是适合追加到草稿末尾
   - 还是更适合替换现有志愿
   - 是否会破坏梯度或保底结构
4. 输出建议：
   - 直接加入
   - 先放草稿再看
   - 用它替换谁更合理
5. 用户确认后执行
6. 执行后复盘：
   - 新增了什么
   - 对当前方案结构的影响是什么

补充约束：

- “增加”不等于永远只是 append
- 对关键位置的新增，更常见的合理动作其实是“替换 + 微调顺序”

### 3.7.3 去掉志愿

典型表达：

- “这个不要了”
- “把这个学校删掉”
- “这个专业组去掉”

编排要求：

1. 识别删除对象：
   - 单个志愿
   - 整个专业组
   - 某一类志愿
2. 分析删除对象是否属于：
   - 关键保底
   - 梯度承接点
   - 唯一满足某个要求 / 偏好的项
3. 如果直接删除会留出缺口，应先提示风险
4. 输出建议：
   - 可以直接删
   - 删了后建议补什么
   - 更适合替换而不是直接删除
5. 用户确认后执行
6. 执行后复盘：
   - 删除了什么
   - 当前方案是否需要补位

补充约束：

- 对明显非关键的单项删除，可走轻量确认
- 对整组删除、关键保底删除、批量删除，必须先做影响分析

### 3.7.4 替换志愿

典型表达：

- “把这个换成那个”
- “这个学校不如换成北京的”
- “用这个替掉现在这个”

编排要求：

1. 同时识别：
   - 换出项
   - 换入项
2. 对比两者在以下维度的差异：
   - 录取率
   - 冲稳保层级
   - 偏好 / 要求命中
   - 风险水平
3. 输出建议：
   - 值不值得换
   - 换完哪个维度更好
   - 哪个维度会变差
   - 是否需要顺便调整相邻顺序
4. 用户确认后执行
5. 执行后复盘：
   - 替换结果
   - 方案结构是否仍合理

补充约束：

- “替换”是比“增加”与“删除”更高阶的组合动作
- 系统应优先把它视为“先分析差异，再执行”，而不是两个独立动作直接串起来

### 3.7.5 局部重做

典型表达：

- “保底这部分重弄一下”
- “北京相关的这一块重新安排”
- “这几个学校帮我重新配”

编排要求：

1. 先识别局部重做范围：
   - 某一层级
   - 某个方向
   - 某几个目标志愿
2. 分析当前主要问题属于：
   - 数量不合理
   - 顺序不合理
   - 方向不匹配
   - 风险集中
3. 输出局部预览方案，而不是直接整版推翻
4. 用户确认后执行局部替换 / 局部重排
5. 执行后复盘：
   - 这一段怎么变化
   - 整体是否仍满足审查要求

补充约束：

- `局部重做` 不等于 `ordered_regenerate`
- 优先应局部修补，只有用户明确要求“整版重排”时才走整体重排

## 3.8 五类动作的统一编排骨架

建议把上述五类动作统一建模为：

1. `ActionTargetResolve`
   - 识别用户想动什么
   - 定位到当前方案项 / 草稿项 / 候选项
2. `ImpactAnalyze`
   - 分析这项改动对当前方案的影响
3. `RiskReview`
   - 判断是否触发新的梯度 / 安全垫 / 风险问题
4. `SuggestionOrPreview`
   - 给用户一个更合理的动作建议或预览
5. `ConfirmIfNeeded`
   - 根据动作风险级别决定是否需要确认
6. `Execute`
   - 执行 move / add / remove / replace / local_rebuild
7. `PostReview`
   - 执行后复盘并说明当前状态

其中：

- `ActionTargetResolve / ImpactAnalyze / SuggestionOrPreview`
  - 属于模型主导的编排层
- `RiskReview`
  - 优先调用 planning review / adjustment 事实能力
- `Execute`
  - 由工具层负责，不负责用户话术组织
- `PostReview`
  - 返回自然语言结果，必要时再引导下一步

## 3.9 与当前 agent 架构的对齐方式

在 `model + skill + tool` 架构下，建议职责边界如下：

### A. `plan_chat` skill

负责：

- 判断用户是不是在“动当前方案”
- 决定属于五类动作中的哪一类
- 决定先分析、先审查，还是可以进入确认
- 组织最终自然语言回复

### B. `plan_execute` skill

负责：

- 承接已经明确对象和确认条件的执行类动作
- 统一编排 `move / add / remove / replace / local_rebuild`
- 执行后触发必要的复盘与收尾

### C. tool 层

只提供两类能力：

- 事实类
  - 查当前方案
  - 查候选
  - 查风险
  - 查调整建议
- 执行类
  - 调位
  - 增加
  - 删除
  - 替换
  - 局部重做

补充要求：

- tool 不负责面向用户的话术组织
- tool 返回结构化事实或执行结果
- 最终回答统一由模型生成

## 3.10 五类动作与当前已有 tool 的映射

结合当前 `gaotu-zy-agent-v3` 的实现，五类动作与已有 tool 的关系如下。

### A. 调位置

当前已有：

- `query_planning_ordered_plan`
  - 用于读取当前排序方案
- `query_planning_state`
  - 用于读取当前阶段、风险、待处理项
- `run_planning_review`
  - 用于执行最新审查
- `analyze_planning_plan_adjustment`
  - 用于给出当前方案的可调整建议
- `move_planning_ordered_item`
  - 用于执行单条排序移动

当前缺口：

- 缺少“先分析后建议目标位置”的专门动作封装
- 对“把北京的放前面”“这两个换一下”这类多目标调位，还没有高层组合执行器

结论：

- 单条调位已经具备最小执行能力
- 批量调位 / 换位仍应由 skill 层编排，后续可补 `swap_ordered_items` 或 `move_ordered_items_batch`

### Plan Adjustment 接口语义

当前统一约定：

- `GET /session/plan-adjustment`
  - 只读取当前已经持久化的 `PlanAdjustmentStateDTO`
  - 不触发重新分析
- `POST /session/plan-adjustment/analyze`
  - 触发重新分析并持久化
  - 直接返回完整的 `PlanAdjustmentStateDTO`

这样调用方不需要再执行“先 `POST analyze`，再 `GET plan-adjustment`”的二跳读取。

调用建议：

- 只想看已有结果：直接 `GET`
- 想重新计算并立刻消费结果：直接 `POST analyze`

兼容要求：

- agent / tool 层不应再假设 `POST analyze` 返回的是完整 `PlanningStateDTO`
- 如需校验 stale flag 或 phase，可单独读取 `planningState`；如只消费方案调整建议本身，应直接使用 `PlanAdjustmentStateDTO`

### B. 增加志愿

当前已有：

- `query_planning_candidate_pool`
  - 用于查候选和筛选目标志愿
- `select_planning_draft_items`
  - 用于把明确 `volunteerId` 加入草稿
- `select_candidates_to_draft`
  - 用于按简单条件从候选中选入草稿
- `query_planning_draft`
  - 用于回看当前草稿
- `generate_planning_ordered_plan`
  - 用于在确认后把草稿重新整理成排序方案

当前缺口：

- 没有单独的“增加后是否应替换现有项”的原子判断能力
- 没有“增加一个明确学校 / 专业后，推荐替代谁”的 tool 级接口

结论：

- “加入草稿”已经可做
- “增补并给替代建议”仍主要依赖模型结合 `candidate_query + plan_analyze`

### C. 去掉志愿

当前已有：

- `query_planning_draft`
- `query_planning_ordered_plan`
- `query_planning_state`
- `run_planning_review`
- `remove_planning_draft_items`
- `ban_planning_draft_items`
- `ordered_remove`（agent router alias，当前实现为 remove draft item，从而同步影响 ordered）

当前缺口：

- 缺少“从 ordered 直接删掉并自动补位”的显式动作
- 缺少“删除前自动判断它是否是关键保底 / 承接点”的专用检查接口

结论：

- 目前更适合把“删除”理解成：
  - 先从草稿移除
  - 再按需重排 / 补偿 / 复审
- 当前 `ordered_remove` 的最小实现已经补齐：
  - 语义：删除当前方案中的指定志愿
  - 实现：复用 `remove_planning_draft_items`
  - 边界：不自动补位、不自动重排
- 对“删掉后是否要补位”仍由 skill 层决定编排

### D. 替换志愿

当前已有：

- `query_planning_candidate_pool`
- `query_planning_draft`
- `query_planning_ordered_plan`
- `analyze_planning_plan_adjustment`
- `remove_planning_draft_items`
- `select_planning_draft_items`

当前缺口：

- 缺少真正的原子 `replace_planning_item`
- 缺少“换出项 / 换入项对比分析”的专用 tool

结论：

- 当前只能通过“remove + select + regenerate/review”组合近似替代
- 这是后续最值得补的高价值执行原子之一

建议新增：

- `compare_planning_replace_candidates`
- `replace_planning_draft_items`

### E. 局部重做

当前已有：

- `query_planning_state`
- `query_planning_candidate_pool`
- `query_planning_draft`
- `query_planning_ordered_plan`
- `analyze_planning_plan_adjustment`
- `preview_planning_compensation`
- `apply_planning_compensation`
- `generate_planning_ordered_plan`

当前缺口：

- 缺少“只针对某一段 / 某一类 / 某几个志愿做局部重排或局部重建”的执行原子
- 当前只有：
  - 整体重排
  - 自动补偿
  - 单点移动

结论：

- “局部重做”目前只能由模型先分析，再落成若干个小动作组合
- 还不适合完全自动托管执行

建议新增：

- `preview_local_plan_rebuild`
- `apply_local_plan_rebuild`

## 3.11 当前建议的实现优先级

如果后续继续做代码落地，建议优先顺序如下：

1. `替换志愿`
   - 用户表达最自然
   - 当前缺少真正原子能力
   - 也是“增加 / 删除”最常见的组合收口
2. `局部重做`
   - 能承接“这段不满意，帮我重新配”这类高价值诉求
   - 比直接整体重排更符合用户真实使用习惯
3. `批量调位置`
   - 用于承接“北京的放前面”“把这两个换一下”
4. `删除后补位`
   - 用于把“去掉某项”补成完整闭环

换句话说：

- 当前系统已经具备：
  - `查`
  - `审`
  - `预览`
  - `单点调位`
  - `加入草稿`
  - `移出草稿`
  - `整体重排`
- 当前最缺的是：
  - `替换`
  - `局部重做`

具体建议如下。

### A. `PlanQuery`

执行顺序：

1. 读取 `orderedPlanState`
2. 若为空，再看 `draftPlanState`
3. 若仍为空，再判断是否存在可展示的初始方案
4. 返回当前方案概览
5. 联动右侧方案区

### B. `PlanAnalyze`

执行顺序：

1. 读取当前方案
2. 没有方案则终止，并提示先生成方案或查看候选
3. 判断当前分析结果是否可复用
4. 不可复用时补跑分析
5. 输出问题诊断
6. 引导用户如需可继续看“怎么调”

### C. `PlanAdjust`

执行顺序：

1. 读取当前方案
2. 没有方案则转为 `PlanGenerate`
3. 判断当前分析基础是否齐全
4. 不齐则先补跑 `PlanAnalyze`
5. 生成调整建议
6. 返回建议预览
7. 等用户明确说“按这个改”再进入应用动作

### D. `PlanGenerate`

执行顺序：

1. 读取当前画像、约束、候选视图、候选池、推荐覆盖层
2. 判断推荐覆盖层是否可用
3. 不可用时先刷新推荐相关状态
4. 判断当前是否已有方案
5. 区分“新出一版”还是“覆盖当前方案”
6. 生成方案
7. 返回并刷新方案区

### E. `PlanReorder`

执行顺序：

1. 读取当前草稿或当前方案
2. 若没有可重排对象，则转为 `PlanGenerate`
3. 判断排序前提是否满足
4. 基于已有内容重排
5. 返回并刷新方案区

## 3.7 状态分层与失效语义

建议把规划相关状态按四层理解：

- 画像层
- 视图层
- 推荐层
- 方案层

### A. 画像层

包含：

- 软意向
- 硬约束
- 身体限制
- 潜在偏好

规则：

- 软意向变化，影响推荐理解和后续方案理解，但不自动修改候选基础池
- 硬约束变化，影响推荐理解和后续方案理解，并联动候选视图层，但不自动修改候选基础池

### B. 视图层

包含：

- 候选筛选条件
- 候选排序方式
- 仅看专家优选等当前查看态

规则：

- 视图变化不应回写画像
- 视图变化影响基于当前视图的默认推荐和方案分析
- 单纯视图变化不应自动推翻已有正式方案

### C. 推荐层

包含：

- 推荐覆盖层
- 初始推荐结果

规则：

- 任何依赖推荐分和专家优选结果的方案动作，在执行前都要先校验这层是否可复用

### D. 方案层

包含：

- 草稿
- 排序结果
- 调整建议
- 审查结果

规则：

- 草稿变化 -> 排序、调整建议、审查失效
- 排序变化 -> 调整建议、审查失效
- 调整建议被应用后 -> 原有建议结果失效
- 审查结果只依赖当前方案，方案一变即失效

## 3.8 当前阶段的产品策略

当前阶段建议优先做“辅助式编排”，而不是“一步托管式编排”。

含义：

- 系统先给信息、建议、预览
- 用户明确确认后再执行真正的状态变更或方案应用

这要求系统严格遵守以下边界：

- 未出现明确方案诉求时，不进入方案编排
- 未确认前，不把偏好和约束写成真实状态
- 未获得执行授权时，不自动修改正式方案
- 查询优先由右侧面板承接
- 建议优先由对话承接

## 3.9 后续扩展方向

在当前辅助式编排稳定后，后续可继续扩展：

- 托管式方案编排
  - 用户明确授权后，系统串行完成查询、筛选、补齐、重排、审查
- 算子化方案引擎
  - 将分析、补充、替换、重排、审查等能力拆成可编排算子
- 多轮收敛式方案生成
  - 允许系统和用户围绕同一版方案多轮来回收敛，而不是一次性出最终答案

## 3.10 实现落地清单

为避免后续实现继续在“老画像入口、planningState 原生入口、planning router 动作入口”之间混用，建议按以下顺序落地。

### A. 第一步：统一入口分层

先将所有用户请求统一收口到以下四类：

- `Explore`
- `Prefer`
- `Constrain`
- `Plan`

落地要求：

- `Explore`
  - 只走查询与右侧查看联动
  - 不写长期画像
  - 不直接进入方案动作
  - 候选查询统一包含在这里，可单独标记为 `CandidateQuery`
- `Prefer`
  - 统一走软意向确认入口
- `Constrain`
  - 统一走硬约束确认入口
- `Plan`
  - 统一走 planning router

目标：

- 避免“只是想了解一下某个方向”被误写为长期画像
- 避免“想按当前方案继续调”被误走画像链路

### B. 第二步：统一 `Plan` 子动作路由

在 `Plan` 内继续细分并显式收口到：

- `PlanQuery`
- `PlanAnalyze`
- `PlanAdjust`
- `PlanGenerate`
- `PlanReorder`

落地要求：

- `PlanQuery`
  - 统一承接“看当前方案 / 看草稿 / 看排序现状”
- `PlanAnalyze`
  - 统一承接“当前方案有没有问题 / 有没有风险”
- `PlanAdjust`
  - 统一承接“怎么调更合理 / 有什么建议 / 优化一下”
- `PlanGenerate`
  - 统一承接“给我出一版 / 按当前条件生成一套”
- `PlanReorder`
  - 统一承接“重排 / 重新排序 / 调整顺序”

目标：

- 不再继续用少数几个粗粒度动作承接所有方案诉求
- 保证“分析”“建议”“生成”“重排”的边界稳定

### C. 第三步：收口状态写入入口

在入口语义稳定后，再统一 backend 写状态的主入口。

建议：

- 老 `userprofile` 兼容链路暂时保留，但只作为兼容层
- 新规划逻辑优先收口到 `planningState` 语义入口
- 软意向与硬约束的确认动作，必须能表达不同的后续影响范围

目标：

- 避免所有状态写入最终都退化成同一条“老画像同步 -> 统一打脏”链路

### D. 第四步：修正 stale 机制

在入口与动作边界明确后，再统一修正 stale 逻辑。

重点：

- 软意向变化的失效范围
- 硬约束变化的失效范围
- `candidateViewState` 变化是否立即打脏
- 草稿、排序、审查之间的失效链

目标：

- 让 stale 机制服务于“当前动作语义”，而不是继续被历史入口反向驱动

### E. 第五步：前后端联调与回归

在语义和 stale 收平后，再做统一联调。

建议优先验证：

- `Explore -> Prefer`
- `Explore -> Constrain`
- `Prefer -> PlanGenerate / PlanAdjust`
- `Constrain -> PlanReorder / PlanAnalyze`
- `PlanQuery / PlanAnalyze / PlanAdjust / PlanGenerate / PlanReorder` 各自动作边界

目标：

- 确保对话、工作台、backend 状态与排序/审查结果在同一套语义下工作

### 4.3 `gaotu-assistant-rank`

## 5. 统一状态模型

统一规划状态以 `planningState` 为中心，建议长期包含以下部分：

- `sessionId`
- `version`
- `phase`
- `staleFlags`
- `profileState`
- `constraintState`
- `candidatePoolState`
- `draftPlanState`
- `orderedPlanState`
- `reviewState`
- `pendingActions`
- `operationLog`

### 5.1 `profileState`

#### 显式画像 `explicitProfile`

用户直接表达或前端显式采集的信息：

- 意向专业、排斥专业
- 意向院校、排斥院校
- 意向地域、排斥地域
- 优势学科

其中优势学科必须在两类入口下都进入会话初始画像：

- 纯文本入口：由对话采集或历史画像补足
- 前端采集入口：由 flow config / 初始化逻辑写入会话画像

#### 潜在画像 `latentProfile`

由 `intake_chat` 引导采集，对志愿偏好产生间接影响：

- `futureDevelopment`
  - 就业倾向
  - 职业类型
  - 行业偏好
  - 稳定性 / 收入 / 深造偏好
- `interestPersonality`
  - 兴趣学科
  - 个性特征
  - 学习方式与校园偏好
- `familyContext`
  - 家庭地域诉求
  - 学费承受度
  - 就近需求
  - 是否支持长期异地发展

这部分不建议继续塞入原有 `UserProfileData`，而应统一持久化到 `planningState.profileState.latentProfile`。

#### 身体条件 `physicalConstraints`

用于限报和审查：

- 视力
- 色觉
- 身高
- 特殊限制

### 5.2 `constraintState`

用于承接从画像推导出的约束与偏好：

- `hardConstraints`
  - 身体条件不可报
  - 标签型限制报考
- `softPreferences`
  - 地域倾向
  - 院校层次倾向
  - 就业导向倾向
- `derivedPreferences`
  - 专业簇推导
  - 就业方向推导
  - 风险偏好推导
  - 学费弹性推导

### 5.3 `candidatePoolState`

候选池是“可选但未入方案”的中间层，必须可查询、可筛选、可解释。

需要明确区分：

- 候选基础池：受硬约束影响
- 候选基础池：由分数、省份、批次等基础供给决定，V2 阶段默认不因硬约束确认而自动重建
- 专家推荐覆盖层：受软意向影响
- 候选面板筛选 / 候选视图状态：承接硬约束确认后的显式筛选条件，只影响当前查看结果

前端展示时也要同步区分这三类语义：

- 普通类标签：临时查看
- 偏好类标签：推荐覆盖层输入
- 要求类标签：候选视图筛选输入，并继续影响后续推荐与方案建议

建议前台通过颜色、底色和文案前缀明确区分，避免用户误把一次查看操作当成长期方案变更。

进一步约定：

- 普通类标签不等于运行时接口字段里的通用 `tags`
- 候选筛选请求只允许使用标准化字段
  - `schoolTags / negativeSchoolTags`
  - `majorTags / negativeMajorTags`
- agent 在意图识别后若要联动工作台，也必须下发同样的标准字段

建议候选项长期至少包含：

- 志愿唯一标识
- 冲稳保区间
- 院校、专业、院校专业组信息
- 专家推荐分 / 录取概率 / 解释标签
- 风险标签
- 与用户意向相关的命中原因

### 5.4 `draftPlanState`

草稿态表示“已选中但未最终定序”的集合，支持：

- 手动加入
- 删除
- 锁定
- 禁用不再推荐
- 记录来源
  - system
  - user_manual
  - agent_auto
  - compensation

### 5.5 `orderedPlanState`

排序态表示“当前拟提交顺序”，支持：

- 从草稿生成初始顺序
- 用户上下调序
- 固定位置
- 记录排序原因
  - 草稿顺序
  - 按冲稳保重组
  - 用户手动调整
  - 系统补偿调整

### 5.6 `reviewState`

审查态用于承接所有校验结果、告警、建议动作和补偿结果。

建议结构长期包含：

- `checks`
  - 校验项编码
  - 校验级别
  - 是否通过
  - 文案
  - 命中对象
- `suggestions`
  - 建议补充什么
  - 建议删除什么
  - 建议调整哪个区间比例
- `autoFixes`
  - 系统已自动补偿的动作
- `needUserConfirm`
  - 需要用户确认的变更

## 6. 规划流程重构

统一流程重构为以下闭环：

1. 初始化画像
2. 推导约束与偏好
3. 生成候选池
4. 选取草稿
5. 生成排序
6. 审查当前方案
7. 自动补偿或引导补偿
8. 用户最终确认

### 6.1 初始化画像

入口分为两类：

- 纯文本入口
- 前端采集入口

统一要求：

- 会话创建时即加载已有显式画像
- 如果是前端采集入口，必须把优势学科和初始采集结果一起带入
- `intake_chat` 新采集到的未来发展、兴趣性格、家庭情况也要持续写入 `planningState`

### 6.2 候选池生成

候选池生成继续复用现有 backend 与 rank 的专家逻辑：

- 先由专家规则形成候选集合
- 再叠加用户画像、约束和派生偏好
- 输出冲稳保区间、推荐原因、风险标签、录取概率等结构化结果

### 6.3 草稿选取

草稿不是最终结果，而是“用户可见的待编排集合”。

选取来源包括：

- 系统自动选入
- 用户在选取视图手动加入
- agent 根据用户指令加入
- 系统补偿加入

### 6.4 排序

排序必须同时兼顾：

- 冲稳保区间分布
- 区间内部梯度
- 分数利用最大化
- 保底安全性
- 用户优先意向
- 用户手动锁定与固定位置

系统自动排序后，用户可以在排序视图中继续拖拽和删除。

### 6.5 审查

审查尽量系统自动进行，类似代码助手在你完成一轮编辑后自动检查风险。

审查输出不只是“有问题”，还要明确：

- 为什么有问题
- 问题影响什么
- 建议怎么改
- 是否可以由系统自动代为补偿

### 6.6 补偿

补偿用于解决：

- 数量不足
- 保底不足
- 梯度断层
- 区间失衡
- 由于用户删除或限制条件导致方案缺口

补偿优先级：

1. 优先保留用户手动确认和锁定结果
2. 优先在用户偏好范围内补齐
3. 无法满足时再进行弱偏好扩展，并请求用户确认

## 7. 风险管理与审查规则整理

以下规则来自当前 `risk_management` 与数量校验材料，应逐步配置化并纳入 `reviewState`。

### 7.1 区间配比合理性

当前核心规则：

- 冲 > 40% 视为风险
- 冲 < 20% 视为风险
- 保 < 20% 视为风险
- 冲 > 40% 且 保 < 20% 视为高风险
- 冲 < 20% 且 保 < 20% 视为风险

当前经验配比建议：

- 冲稳保约 `3:3:4`

设计落地要求：

- review 输出风险级别、命中原因、建议配比
- compensation 能根据区间不足自动推荐补充候选

### 7.2 兜底安全性

当前经验规则：

- 若用户分数 `>= 580`，默认兜底相对安全
- 若用户分数 `< 580`，则需要关注保区间中的本省院校数量
- 若本省保底院校少于经验阈值，则提示保底风险

设计落地要求：

- 审查时结合分数、省份、保区间本省院校数
- 自动补偿优先建议补充本省保底志愿

### 7.3 倒挂现象

核心含义：

- 从上到下的录取概率不应逆序恶化
- 若上一个志愿的录取概率高于下一个志愿，则存在倒挂风险

设计落地要求：

- ordered plan 审查时按当前顺序检查
- 输出命中位置和调整建议
- 若是用户手动排序导致，允许用户保留，但需要明确提示

### 7.4 梯度合理性

核心含义：

- 录取概率梯度不应存在较大断层
- 当前经验阈值是相邻录取概率差值 `> 8%`

设计落地要求：

- 对排序方案按录取概率检查梯度
- 标记缺失区间
- 补偿时优先从缺失概率带补齐候选

### 7.5 中外合作办学提示

若志愿中存在中外合作办学标签，需要显式提示用户确认是否接受。

### 7.6 高收费专业提示

若志愿中存在学费高于经验阈值的专业，需要结合家庭经济情况提示风险。

### 7.7 限报要求提示

若志愿命中色盲色弱、单科成绩、性别、语种等限制标签，需要结合用户画像审查。

### 7.8 特殊类型招生提示

不同省份的特殊类型招生规则不同，需要按省份配置标签并提示用户核对。

### 7.9 边缘分数提示

若用户分数处于当前批次线以上一定分数范围内，需要提示滑档风险并建议增加稳保和省内院校。

### 7.10 固定提示项

包括：

- 招生计划代码更新提醒
- 调剂风险提醒

## 8. 数量校验规则整理

数量校验材料体现的是“不同填报模式下，用户填报数量是否满足官方要求”的补充审查能力。

### 8.1 按专业组填报

需要同时检查两层：

- 用户填报的专业组数量，相对当前省份要求的数量是少于、等于还是大于
- 在每个专业组内，用户选择的专业数量是否满足该省份对该专业组的要求

对应动作：

- 数量不足：提示增加专业组或补齐组内专业数量
- 数量刚好：提示满足官方要求
- 数量过多：提示精简，避免临时报考时慌乱

### 8.2 按专业填报

检查用户填报的专业总数量，相对当前省份要求是少于、等于还是大于。

对应动作：

- 少于要求：提示补足
- 等于要求：提示安全
- 多于要求：提示可适当精简

### 8.3 按院校填报

与按专业组填报类似，需要同时检查：

- 用户填报的院校数量是否满足省份要求
- 每个院校下选择的专业数量是否满足该省份要求

对应动作：

- 数量不足：提示补足院校或院校内专业
- 数量刚好：提示满足要求
- 数量过多：提示精简

### 8.4 设计落地要求

- 数量校验应成为 `reviewState` 的一类标准化检查项
- 检查结果必须绑定当前填报模式
- 若系统知道用户所在省份和批次，应直接使用省份配置规则
- 若缺少配置或模式不明确，应降级为提示，不做强校验

## 9. 对话与前端协同设计

### 9.1 前端能力

前端至少提供两类核心视图：

- 选取视图
  - 查看候选池
  - 手动加入草稿
  - 局部筛选与批量操作
- 排序视图
  - 查看已选草稿或排序方案
  - 上下拖拽
  - 删除
  - 固定位置

后续可增加：

- 审查视图
- 补偿建议视图

### 9.2 Agent 编排

agent 不再直接“黑盒生成最终方案”，而是要把用户诉求拆解到基础动作上。

例如：

- “我想多看看北京的计算机，但一定要稳一点”
  - 更新地域和专业偏好
  - 生成候选池
  - 推荐用户在候选池中优先查看北京计算机相关候选
  - 若需要可自动选入部分稳妥项

- “把这个学校提前一点”
  - 调整 `orderedPlanState`
  - 重新触发局部审查

- “我不接受中外合作”
  - 新增硬约束
  - 刷新候选池、草稿、排序和审查

### 9.3 技能表达

在对话 skill 中，需要明确向用户解释系统的决策依据，包括：

- 为什么推荐这些候选
- 为什么这样分冲稳保
- 为什么当前排序更合理
- 为什么提示某个风险
- 如果自动补偿，会补什么、为什么补

5. 审查是否准确识别区间比例、保底、倒挂、梯度、数量问题
