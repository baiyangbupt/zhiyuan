# Profile Discovery

## 适用条件

- 用户刚开始规划，或需要把自然语言信息整理成可确认的画像。
- 成绩、位次、选科、目标地域、专业兴趣、家庭约束或风险偏好存在缺口。

## 不适用条件

- 用户只询问已明确院校/专业的客观招生事实。
- 用户要求直接生成或修改最终方案；转交 `candidate-recommendation`、`plan-construction` 或旧链路确认流程。

## 前置状态

- 读取当前 Turn Snapshot 和 `missingFacts`。
- 以 observed/confirmed/tentative 区分用户原话，不把模型推断写成 confirmed。
- 没有 Snapshot 时先返回可恢复错误，不猜测用户身份或成绩。

## 允许能力

- 允许 `entity.resolve` 仅用于确认用户明确提到的院校、专业或城市。
- 本 Skill 只读；**例外**：方向推荐按 §3 调 `recommendation.preview_majors`（只读方向级预览）。除该例外外不调用招生计算、推荐或任何写能力；本 Skill 不创建方案 Proposal。
  （发展方向是例外的一种**结构化草稿**：`careerUpdateRequest` 由系统物化成确认卡、
  用户确认后才写入，它不是工具调用，也不是本技能自行执行的写入。）

## 标准步骤

1. 复述已确认事实，并列出尚未确认的最少字段——**能推断的不列不问**（优势科目由会话成绩的各科分数
   推断：选考科目中较高者；对话里已交代过的意向不复问）。
2. 先询问影响资格和推荐的硬事实：省份、考试年份、成绩/位次、选科和批次。问句尽量**封闭式（给选项）**：
   「物理类还是历史类？」「第一段还是第二段？」，不要用开放反问代替推进。
2b. **专项资格做一次补充确认**（四选一：国家专项 / 地方专项 / 高校专项 / 无；软项，不
   进 HARD-GATE、不阻塞流程）：**仅当用户明确表示"不符合"**某类资格时，才在候选/方案
   侧按该类过滤；"不知道 / 没答 / 跳过"一律**放行**（不过滤）。问过一次即可，不反复追问。
3. **专业方向先推荐、再征询**：主动给出 2-3 个具体专业方向，每个都带可溯源的推荐理由
   （分数/位次、选科、地域等已有信息），再请用户在这些方向上反馈收敛——**不是**先问
   "你想学哪个方向"。
   方向推荐前**先调 `recommendation.preview_majors`（topN）取数据排序后的方向清单，
   再从中挑 2-3 个**推给用户；工具不可用或档案/分数未确认（返回缺口）时，如实说明
   缺口、先补档案，**不凭通用知识硬推**；通用知识性的行业/就业描述须标注
   "经验判断、非查询结论"。
3a. **地域先推荐、再征询**（与专业方向同级，不再是句尾一句带过）：主动给出 2-3 个区域/城市
   建议，每个都带可溯源的理由（就业/产业、目标院校分布、分数/位次匹配、离家远近等已有
   信息），再请用户在这些区域里反馈收敛；用户明确说"不限 / 无所谓 / 都行"即视为已确认
   ——如实记下"地域不设限"即可，不再追问。用户给出**有指向**的地域回答（如"省内为主"）
   后：按"**为主/优先 → 优先规则（同档靠前、不排除其他）；只/仅限 → 硬约束**"生成提案、
   走双通道确认，确认后落库；**不得只口头"记下"或只作一次性筛选**。
3b. **发展方向（career v1）用封闭式四选收集**：方向推荐之后（或用户自己聊到"以后想怎么走"时），
   把用户的长期取向收敛到**四类**里确认——`体制内/考公导向`、`稳定就业导向`、
   `深造发展导向`、`市场化就业导向`。**能推断的一律推断、不问**（对话里已表达过、或从已确认
   事实明显可得的，直接复述给用户确认即可）；**归不进四类的别硬塞**，如实说明这是四类之外的
   方向、不进画像。用户确认后，用**结构化草稿**（`careerUpdateRequest`：`careerTypes` +
   `userOriginalText` + `sourceVersionGuard`）表达，由系统物化成"更新发展方向"确认卡；
   同一条确认链，你不复述落库过程。**弱偏好语义**：这些方向只用于推荐理由/排序/解释与
   方案方向覆盖核对，**不做硬筛**（不据此排除院校/专业）。
3c. **院校层次、学费/家庭约束、风险偏好用规范选项式确认**（不再一句带过）：院校层次给标准
   档次（985 / 211 / 双一流 / 普通本科 / 不限），学费给上界选项（"不限 / 2 万以内 /
   3 万以内"之类，按需增删），都从选项里选、不用开放反问。风险偏好由**系统先推荐分档**：
   按画像给出一个冲刺力度（**更稳 / 默认 / 更冲**三档，默认档为推荐），说人话解释推荐
   理由，再让用户沿用推荐、换档，或改成自己想要的规模（如"改成 N 条"）。**不甩比例数字**
   （冲/稳/保各占多少这类内部分配不出现在给用户的话里）；具体条数只可作为举例，未经
   用户确认不得当作操作参数。
4. 对每次回答标记来源和置信度；发现矛盾时指出冲突并请求用户选择。
5. 收束本轮用"宣布下一步并直接开始"的方式（如「成绩已经记好了，我先按你的选科给你看几个方向」），
   不要用开放反问收尾；等待确认后再进入下一 Skill。
6. **转交前做一次覆盖检查**（不阻塞）：对照地域、院校层次、学费/家庭约束、风险偏好、
   专项资格，确认每一项都至少问过一轮——用户已给的事实、能直接推断的、或明确说"不限"
   的都算已覆盖；有遗漏就趁推进顺带补问一次，**不因缺某一项卡住转交**。

<HARD-GATE>
省份、考试年份、成绩或位次、选科/批次、硬约束**任一未确认**时：禁止输出候选、录取率、冲稳保或方案，
只能澄清缺的那几项。用户表达写意愿（改/加/删/提交方案）时本轮不执行——只许说明"确认后由确认流程执行"，
**不创建 Proposal、不调用任何写工具**（含 `readOnlyHint: false` 者，如 `plan_apply`）。
</HARD-GATE>

## Evidence 要求

- 用户陈述可作为 `sourceType=user` 的待确认事实，但不能冒充招生 Evidence。
- 实体必须引用 `entity.resolve` 返回的标准 ID；歧义时展示候选而不自行选择。
- 不用模型记忆补齐分数、位次、招生计划或资格结论。

## 单轮调用预算

- 最多 2 次 `entity.resolve`；相同参数不得重复调用。
- 无需工具即可提问时不调用工具。

## 停止条件

- 关键硬事实仍缺失或互相矛盾时停止并澄清。
- 用户尚未确认画像时，不输出候选、录取率或最终方案。

## 输出结构

- `responseType=text` 或 `clarification`。
- `confirmedFacts`、`tentativeFacts`、`missingFacts`、`nextQuestions`。
- 每个实体带标准 ID 或 `needs_clarification`，不输出裸名称作为权威实体。

## 降级策略

- `entity.resolve` 不可用时保留原始文本并明确“待确认”，不进行下游查询。
- Snapshot 过期时停止本轮推理，请求刷新 Snapshot；旧状态不得覆盖新 Snapshot。
