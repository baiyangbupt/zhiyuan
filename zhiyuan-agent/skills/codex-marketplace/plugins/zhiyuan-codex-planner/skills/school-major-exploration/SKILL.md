# School and Major Exploration

这是一条**分阶段的对话流程**，不是一个动作清单。每一阶段末尾说清"下一步要什么"，
用户随时可以打断并改方向——改方向不是失败，是本来的用法。

## 适用条件

- 用户希望了解院校、专业、培养方向、城市或就业取舍。
- 用户已有明确或可解析的院校/专业名称，但还没有要求基于成绩生成候选。
- **也包括看起来很简单的一句话**："计算机和物理哪个好""学医累不累"——
  这类没有唯一实体、也没给参数的问题，正是本技能的主场。
- **职业路径问题**（"我适合什么方向""体制内适不适合我""稳定就业值不值得优先考虑"
  "这个分数还要不要优先考虑读研"）——见下面「职业路径主题」一节
  （方向问题在本技能分析，不转给学校/专业意向抽取）。

## 不适用条件

- 需要历年录取事实、招生计划或选科资格判断时，转交 `admission-fact-analysis`。
- 用户要求按个人分数排序候选或构建志愿表时，转交后续 Skill。

## 前置状态

- Snapshot 中存在当前用户会话和 planning stage。
- 目标实体先通过 `entity.resolve` 唯一解析；不接受模型自行拼接 entity ID。
- 已知偏好只作为探索维度，不自动升级为硬约束。
- **画像不全不是前置条件**：门禁事实缺失时本技能照常进入，见阶段 1。

## 允许能力

- `entity.resolve`
- `catalog.search_schools`、`catalog.get_school`
- `catalog.search_majors`、`catalog.get_major`
- `recommendation.preview_majors`（只读：方向级聚合预览，按画像取 topN）
- 仅只读；禁止 profile、plan、recommendation 写操作。

## 标准步骤

### 阶段 0 · 分类，并把分类说出来

先判断这一轮属于哪一类，**在回复第一句说出来**（用户能纠正你，这比猜对了更有用）：

| 分类 | 特征 | 走向 |
|---|---|---|
| 信息不全 | 自身情况还没交代 | 阶段 1 → 3：**先给方向性内容**，门禁事实放在最后问 |
| 方向对比 | "A 和 B 哪个好""值不值" | 阶段 1 → 2 → 3 → 4 全走 |
| 具体查询 | 点名了院校/专业，要资料 | 阶段 1 → 2 → 3，收敛可以省 |

**没有"必须先填表"这一类**：三类都要先给出用户能听懂的内容。

### 阶段 1 · 建立基线

- 复述已知（来自 Snapshot 与对话），列出**还没确认的最少字段**——**能推断的不列不问**：
  优势科目由会话各科分数推断（选考科目中较高者）、对话里已交代过的意向不复问。
- 门禁事实（省份 / 考试年份 / 成绩或位次 / 选科 / 批次）缺失时，它挡住的是
  **录取结论**（分数、概率、冲稳保、能不能报），**不挡方向性解释与维度对比**。
  两者分开说：能说的先说完，再把缺的列出来。
- 推进靠主持：每步**先宣布下一步做什么、然后直接开始**（如「我先按你的选科给你看几个方向」），
  不用开放反问当推进手段；需要用户定的用封闭式选项。
- 提问顺序、冲突处理（两个值冲突时引用两者、问哪个为准，不许取平均）、单轮问题数
  按 `planner-questioning-guide.md` 执行。

### 阶段 2 · 取权威数据（这一步不许用记忆代替）

按对象取最小必要的数据，**每条事实都要能说出它来自哪个工具**：

| 要什么 | 用哪个工具 |
|---|---|
| 实体唯一化（学校 / 专业 / 专业类） | `entity.resolve` |
| 院校、专业目录信息 | `catalog.search_schools` / `catalog.get_school` / `catalog.search_majors` / `catalog.get_major` |
| **批次码**（`batch` 的合法取值） | `catalog.list_batches`（按省份不同：浙江第一段=`17`、上海本科批=`01`）。**不要把"本科批"这种名字当 batch 传**——上游不报错，只返回空 |
| **这所学校在我省按什么招生**（招生单元 + 招生专业/计划数/选考要求） | `catalog.list_admission_units(schoolId, areaId)` → `admission.get_enrollment_plan(schoolUnitId)`，**免分数** |
| **两个以上对象的同口径并列** | `admission.compare`（2–5 个实体 + 口径四项：省份/批次/年份/科类） |
| 录取分、位次、招生计划、选科资格 | **不在本技能**：转 `admission-fact-analysis`（注意：**学校级可查、专业级还没接**，别让用户先挑专业） |
| **招生章程原文**（这所学校怎么录、有什么硬要求） | `admission.get_charter(schoolId, year?)`——**免分数**，正文是学校发布的招生简章全文，标题自带年份。**不要**拿 `getSchoolRule`（录取规则摘要）当原文：那条在该校没规则时回占位文案"正在更新中"，且响应没有标志位区分 |

`admission.compare` 的口径四项**必须给全**：它拒绝用"最近一年/默认省份"凑数，
也不把跨年、跨批次的数字并排——那种表看起来能用，实际是在拿两个口径的数字比大小。
它只填分数线口径能支持的维度；录取率、学费等维度会如实列进 `unavailableDimensions`。

取不到时：**明说取不到**，并说清"缺的是哪个数据、补上它需要什么条件"。
不得用模型记忆补，也不得把"没查到"写成"没有"——这两件事对用户的含义完全相反。

### 阶段 3 · 给维度对比

- **两个以上对象、且口径齐全时，用 `admission.compare` 取数**，不要自己调 N 次
  `admission.get_history` 再拼表：口径一致性只有那个工具会强制，而且单轮调用预算
  撑不住 N 次查询。
- **事实与解释分开标注**：来自工具的写清来源；模型自己的解释标 `planner_experience`，
  并说明它不构成录取结论。
- 对比维度：学科门类与培养方式 / 选科门槛 / 升学路径 / 典型去向 / 城市与费用 /
  转换成本 / 各自适合什么样的人 / **发展方向（体制内/考公、稳定就业、深造、市场化就业）**。
- **每条维度注明"要把它落实成结论，还缺什么数据"**——这句话是把探索接到后续技能上的钩子，
  比"我需要更多信息"具体得多。
- 实体还不唯一时：先给**不绑定具体实体**的通用对比，再澄清"比哪两个"。

### 阶段 3b · 职业路径主题

用户在问职业路径、长期发展路线、就业取向，或"适不适合我""值不值得重点看""先优先哪条路"
（还处在了解和判断阶段）时，按下面组织：

- **先看学生本人，再看方案**：① 先给"以你目前情况更适合重点了解什么路径"的判断；
  ② 再看当前方案在没在这个方向上；③ 最后才看候选里有没有值得补看的机会。
- **中低分段优先就业**：处于中低分段时，不把深造/读研当优先建议，先保就业确定性
  （就业承接、岗位需求、路径清晰度）；用户主动问深造时，把它说明为后续增益而非当前主目标。
- **弱偏好，不硬筛**：画像里已确认的发展方向（快照 `preferences.careerTypes`，四类中文标签）
  只用于解释、排序与建议侧重，**不据此排除任何院校/专业**。
- **不和意向混用**：用户只是问/讨论时，只做分析——不进偏好确认、不说"我帮你记下来了"。
  只有当用户明确表达"以后优先按这个来""把这个作为后续偏好""我就按这个方向走"时，
  才用结构化草稿（`careerUpdateRequest`，写实例）出"更新发展方向"确认卡；
  只读实例按"需要用户确认后由确认流程执行"表述。学校和专业只是这条分析里的证据，
  不是主体——"有哪些学校适合考公"仍是学校主题，方向只是分析视角。
- **落案前不承诺**：出了"更新发展方向"卡（含"更新成绩"等同族确认卡）之后、用户确认之前
  （点卡片确认或回复确认），绝不说"已记下/已更新/帮你记上了"，只说"已经拟好一张待确认卡，
  点卡片上的确认或直接回复确认即可生效"——确认落地由确认流程完成，不替它提前宣布。
- **输出**：先给判断、再给依据；不列学校名单；信息不足时明说这是初步判断。

### 阶段 4 · 收敛成可判定的取舍

- 把开放问题收敛成 **2–3 个可判定的选项**（例："更看重本科毕业就能就业" / "愿意走长学制做研究" /
  "还没想好，先看看专业都学什么"），请用户选，而不是继续罗列信息。
- 用户选定后写成"已确认偏好"，但**不替用户下价值判断**。

<HARD-GATE>
用户没有确认取舍之前，不进候选推荐（`candidate-recommendation`）或方案构建（`plan-construction`）。
探索阶段**永远只读**：不写 profile、不生成 pending、不改方案、不输出冲稳保或志愿顺序。
</HARD-GATE>

### 交接

本轮结束必须点名下一轮走哪个技能、需要用户给什么：

- 转向"我能不能上 / 怎么填" → `admission-fact-analysis` 或 `candidate-recommendation`
- 方向已明确且信息齐全 → `candidate-recommendation`
- 情况本身还没交代清 → 先回 `profile-discovery`

## Evidence 要求

- 学校和专业名称、层次、培养信息必须来自目录工具的标准实体和 Evidence。
- 搜索无结果返回 `not_found`，歧义返回 `needs_clarification`；不以相似名称替代。
- 任何时效性招生数字必须改用 `admission-fact-analysis` 查询。
- `planner_experience` 只能出现在解释与提问引导里，不能顶替事实。

## 单轮调用预算

- 最多 4 次读取调用，其中实体解析最多 2 次；同参数只调用一次。
- 优先批量搜索和单次详情查询，避免 N+1。

## 停止条件

- 实体仍有多个候选、用户偏好无法区分，或资料覆盖不足时：
  **先给不绑定具体实体的通用维度对比**（学科门类与培养方向、典型选科要求、升学与就业路径、常见取舍），
  **再**澄清具体对象。不允许只回一句"哪个好没有统一答案"就收尾——用户问的是比较，
  比较本身有可说的内容，缺的只是"比哪两个"这个限定。
- 通用对比不得写成结论：不能说"A 比 B 好"，只能说明两个方向**各自适合什么样的人**。
- 硬门（阶段 4）未过时不进下一阶段。
- 不输出录取率、冲稳保标签或最终志愿顺序。

## 输出结构

- **首句是分类与路由**（"这轮先按方向对比走"）。
- `responseType=fact` 时逐条绑定 `evidenceRefs`。
- 结构化比较使用 `artifactRefs`，包含实体 ID、比较维度和 limitations。
- 实体尚未唯一时用 `responseType=clarification`，但 `message` **必须包含通用维度对比**，
  澄清只放在 `clarification` 字段与末尾问题里——把"我要问的"和"我已经能说的"分开，
  用户才不会觉得被一句反问挡回来。
- 末尾**宣布明确的下一步**：能直接开始的直接开始（先给内容），需要用户定的用 2-3 个可判定选项
  请其选择；不以开放反问收尾，也不代替用户做未经确认的价值判断。
- 解释面向用户只用可溯源事实与业务语言：不直出系数、权重、打分、匹配度/热度指数等内部数值。

## 降级策略

- 目录服务暂时不可用时返回 `recoverable.error`，保留已确认实体，不使用模型记忆补齐。
- 取不到某类数据（如章程原文）时，**把它作为一条明确的缺口说出来**，
  不要让回答看起来像已经覆盖过；也不要因为缺口存在就整体拒答。
- 版本过期时刷新 Snapshot 后重查；禁止使用旧结果覆盖新状态。
