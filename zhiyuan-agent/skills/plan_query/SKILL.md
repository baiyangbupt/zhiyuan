# 方案局部查询技能

## 目标

本技能只处理“局部存在性 / 示例 / 机会补充”查询，例如：

- “当前方案里有没有上海的网络与新媒体”
- “候选里还有没有北京的计算机类”
- “方案里有没有广西师范大学的工业设计”
- “候选里还有没有民办财经类院校”

它不处理：

- 整体方案状态
- 整体数量是否达标
- 整体风险审查
- 生成、补齐、替换、重排、审查这类方案动作

这些问题应走方案主链路，而不是局部查询。

## 可用工具

### `query_plan`

用途：

- 查询当前方案里是否命中某组局部条件
- 查询候选池里是否还有符合条件的机会
- `scope=plan` 查询当前方案，`scope=candidates` 查询候选池

### 推荐参数形态

调用 `query_plan(scope, filters)`，优先传结构化 filters：

- `scope`
  - `plan`
  - `candidates`
- `school`
- `major`
- `province`
- `city`
- `school_tag`
- `major_tag`
- `tiers`
- `limit`

如果是意向确认类工具，不要发明额外 key；专业意向只使用：

- `level1`
- `level2`
- `level3`
- `negative_level1`
- `negative_level2`
- `negative_level3`

## 调用原则

### 1. 优先结构化，不要整句直塞

如果用户已经明确说出了条件，就直接传结构化参数。

例如：

- “当前方案里有没有上海的网络与新媒体”
  - `scope="plan"`
  - `filters={"province":["上海"], "major":["网络与新媒体"]}`

- “候选里还有没有北京农学院的生物工程”
  - `scope="candidates"`
  - `filters={"school":["北京农学院"], "major":["生物工程"]}`

### 2. 注意“学校 + 专业”和“院校专业组”不是一回事

当用户说的是：

- “广西师范大学工业设计”
- “上海建桥学院网络与新媒体”

优先拆成：

- `school`
- `major`

不要把整串只当成一个学校名，也不要把“第01组 / 006专业组”当成用户必须显式说出的部分。

### 3. 地域条件单独进地域字段

像下面这些：

- “上海的网络与新媒体”
- “北京院校”
- “浙江机会”

优先拆到：

- `province`
- `city`

不要把地域词和学校/专业词混成一个 `query` 字符串。

### 4. 标签条件单独进标签字段

像下面这些：

- “民办”
- “财经类院校”
- “公办”
- “双一流”

优先拆到：

- `school_tag`
- `major_tag`

### 5. 这些问题不要走本技能

以下诉求不是局部命中查询：

- “方案有了么”
- “现在方案怎么样”
- “还差几个怎么补”
- “帮我补几个更稳的”
- “帮我替换掉”
- “帮我重排一下”
- “帮我审查一下”

它们应转回 `plan-chat` 主链路。
