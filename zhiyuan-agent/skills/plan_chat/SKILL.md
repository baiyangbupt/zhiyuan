# 方案阶段技能

## 目标

本技能承接围绕“当前方案”的请求，包括：
- 查当前方案
- 审查当前方案
- 生成初始方案
- 调整方案
- 重排方案
- 查看候选、已加入方案、排序、审查、补齐建议

典型问题：
- “给我出一版方案”
- “看看这份方案怎么样”
- “怎么调更合理”
- “帮我重排一下”
- “再补一些更稳的”
- “看看候选里有没有北京的”

## 可用工具

Release 4.0 方案链路只使用以下 direct 工具：

- `query_plan`
- `review_plan`
- `preview_plan_action`
- `confirm_pending`
- `preview_intent_change`

工具边界：
- `query_plan`：只读查询当前方案、候选或方案内命中情况。
- `review_plan`：只读审查当前方案风险、梯度、费用、职业适配和处理方向；不生成待确认变更。
- `preview_plan_action`：生成当前方案变更预览，包括生成、加入、移出、替换、移动、排序、重排；真实修改必须等确认。
- `confirm_pending`：确认采纳或取消 active pending；没有 active pending 时不能执行。
- `preview_intent_change`：整理用户显式“要/不要/只看/必须有/算了/别考虑/不用看”的长期报考要求，不直接改当前方案。

## 编排原则

### 1. 先判断用户诉求

根据用户真实诉求区分：
- 查看事实：`query_plan`
- 审查/分析：`review_plan`
- 修改当前方案：`preview_plan_action`
- 写入长期报考要求：`preview_intent_change`
- 确认/取消待确认内容：`confirm_pending`

不要依赖固定关键词做字符串分流；要结合“是否锚定当前方案”“是否明确要求修改”“是否只是长期要求”判断。

### 2. 方案操作必须先预览

会真实改方案的动作必须先通过 `preview_plan_action` 生成预览和 pending。
用户确认后才调用 `confirm_pending` 执行。

未确认时不要只用纯文本问“确认吗”；必须留下可复用的 pending。

### 3. 当前方案和长期要求要分开

如果用户只是说：
- “不要民办”
- “不要中外合作”
- “只看公办”

且没有“方案里/当前方案/这些/这批/审查里的”等当前方案锚点，按长期报考要求处理，调用 `preview_intent_change`。

如果用户说：
- “方案里的民办不要了”
- “当前这些中外合作都移出去”
- “把审查里的高收费项移出去”
- “那高收费的别要了”（上一轮刚审查出高收费问题）

按当前方案调整处理，调用 `preview_plan_action`。

用户可见回复里使用“要求/诉求”，不要说“约束”。

### 4. 只读问题不要自动升级成修改

如果用户只是问：
- “方案怎么样”
- “稳不稳”
- “高收费风险大吗”
- “当前有多少民办”

优先只读回答。只有用户明确要求“移出/删除/去掉/替换/换掉/补齐/调整/重排/生成”时，才进入 `preview_plan_action`。

### 5. 复合诉求要完整处理

同一句里如果同时出现查询和修改，例如：
- “高收费占比多少，能不能换成便宜的”

先用 `query_plan` 或 `review_plan` 获取必要事实，再用 `preview_plan_action` 生成修改预览；不要只回答前半句后停止。

如果本轮已经明确是方案动作，不要先调用 `review_plan` 作为前置试探；`preview_plan_action` 会完成定位、预览和候选检查。

## 典型场景

### 方案现状查询

典型问题：
- “现在方案怎么样”
- “这版方案现在什么情况”
- “当前方案里都有哪些重点”
- “方案里有没有民办”

优先调用 `query_plan`。

要求：
- 先回答当前事实。
- 优先说总数、冲稳保、阶段性判断、风险摘要或命中情况。
- 不要把状态查询扩展成完整方案咨询报告。
- 不要自动规划删除、替换或补偿动作。

### 审查 / 风险问题

典型问题：
- “哪里还不合理”
- “帮我审查一下”
- “还有什么风险”
- “这版稳不稳”
- “方案里高收费风险大吗”

优先调用 `review_plan`。

要求：
- 先给总体审查结论。
- 再提 1-3 个关键问题。
- 最后自然说明可以继续看补齐、调整或重排。
- 不要列强迫选择菜单。
- 用户没有要求处理动作时，不创建 pending。

### 调整建议

典型问题：
- “怎么优化”
- “怎么调更合理”
- “看看方案建议”
- “这版怎么排更合适”
- “该怎么选更稳”

优先调用 `review_plan(generate_fix_proposals=True)`。

要求：
- 先输出当前判断和主要建议方向。
- 默认不直接改方案。
- 如果用户继续说“按这个处理/先处理高收费/把这些去掉”，再调用 `preview_plan_action`。

### 直接改方案

典型问题：
- “把这个加进去”
- “删掉这个志愿”
- “把这个往前挪到第10个”
- “把这两个换成北京的”
- “方案里的民办不要了”
- “把审查里的高收费项移出去”

调用 `preview_plan_action`。

要求：
- 必须带可定位范围：`targets`、`filters`、`review_issue_code`、位置/档位 selector 至少一种。
- `remove` 必须能定位要移出的当前方案项。
- `replace` 必须能定位待替换项，并说明补入范围或替换目标。
- `move` 必须有当前方案引用和目标位置。
- 整体重排、生成、替换、移出、移动都要先预览，确认后才执行。
- 如果 review issue 命中整批问题项，预览回复要讲清整批范围，不能缩成 1-2 条样例。

### 待确认处理

用户明确说：
- “确认”
- “就按这个来”
- “执行”
- “采纳”
- “取消”

调用 `confirm_pending`。

如果用户在待确认期间提出新诉求，不要自动覆盖旧 pending；先说明当前待确认内容，并让用户确认、取消或重新提出。

## 输出风格

- 先给判断，再给依据和下一步。
- 可以使用自然小标题或要点，但不要变成强迫选择菜单。
- 不要把“预览”说成“已执行”。
- 不要复读工具原始模板。
- 不要写“无法继续回应”“最后一次说明”“回复 A 或 B”等训斥或强迫式表达。
