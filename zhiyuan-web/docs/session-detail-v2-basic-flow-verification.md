# Session Detail V2 Basic Flow Verification

## 1. 目标

本文件用于验证 `sessionDetailV2` 当前最基础的显式工作流是否已经串通:

1. 系统给出默认候选结果
2. 用户在候选区筛选和查看志愿
3. 用户将志愿加入方案
4. 用户在草稿中查看、删除、锁定
5. 用户进入排序区，基于系统初始底稿手动调整顺序

本阶段暂不验证:

- 对话驱动自动编排
- 系统自动审查 / 自动补偿
- 批量操作
- 草稿区复杂批量编辑
- 排序区拖拽式重排

## 2. 启动前置

需要本地至少保证以下服务可用:

- `gaokao-volunteer-pc`
- `gaotu-assistant-backend`
- `gaotu-assistant-rank`
- `gaotu-zy-agent-v3`

前端建议通过 `sessionDetailV2` 页面验证，确保 URL 带有:

- `chatSessionId`
- `tenantId`
- `botId`
- `userId`

切页前置约定:

- frontend、backend、agent 的候选筛选字段必须统一为
  - `provinceNames / negativeProvinceNames`
  - `schoolKeywords / negativeSchoolKeywords`
  - `majorKeywords / negativeMajorKeywords`
  - `schoolTags / negativeSchoolTags`
  - `majorTags / negativeMajorTags`
- 不再接受旧 `tags / negativeTags` 口径
- 统一标签治理说明见
  - [tag-governance.md](/Users/baiyang/git/zhiyuan/gaotu-assistant-backend/docs/tag-governance.md)

当前候选语义补充:

- `candidatePoolState` 表示由用户分数、省份、批次等基础信息决定的大候选池
- 页面上看到的候选结果 = `candidatePoolState` + `planningState.candidateViewState`
- 用户在筛选栏的选择会持久化到 `candidateViewState`
- 对话确认后的硬约束当前也只会落到筛选栏和 `candidateViewState`，不会自动重建大候选池

## 3. 当前工作台预期

### 3.1 页面结构

桌面端当前应看到:

- 左侧对话区
- 右侧工作台
- 工作台顶部状态卡
- 主视图 tab:
  - `候选志愿`
  - `排序方案`
- 右下角浮动 `草稿` 入口

### 3.2 当前交互原则

- 候选筛选是显式可见的
- 加入方案不会自动切走当前候选焦点
- 草稿默认由用户手动展开 / 收起
- 排序区默认是系统给出的初始底稿
- 用户手动上移、下移、固定之后，排序结果继续由用户控制
- 不自动触发审查

## 4. 验证步骤

### 步骤 1: 首次进入页面

操作:

- 打开 `sessionDetailV2`
- 保持默认落在 `候选志愿`

预期:

- 右侧顶部能看到候选 / 草稿 / 排序 / 审查四张摘要卡
- 候选区能正常展示院校组卡片
- 每个院校下能展开专业表格
- 右下角能看到浮动 `草稿` 按钮
- 此时草稿默认不自动展开

排查点:

- 候选为空时，检查 `candidate-pool/generate` 和 `candidate-pool/query`
- 若页面只有上半屏，检查样式容器高度是否生效

### 步骤 2: 候选筛选

操作:

- 点击 `冲 / 稳 / 保`
- 在标签输入框中输入如 `公办`、`北京`、`法学`
- 切换排序字段和升降序

预期:

- 候选列表会自动刷新
- 刷新页面后，当前筛选条件和排序方式应保持
- 院校组顺序与当前排序字段一致
- 院校 / 专业组卡片默认折叠
- 候选区顶部能看到总数和当前已加载数量
- 候选较多时下滑会继续自动加载，而不是只停留在第一页
- 专业列表内容与老版本字段颗粒度基本对齐

重点核对字段:

- 学校名
- 地域 / 批次 / 性质 / 类别 / 层级
- 历年录取分数线入口
- 专业名
- 招生计划
- 学制
- 学费
- 选科要求
- 近年录取人数 / 最低分 / 最低位次
- 录取率
- 冲稳保标签

### 步骤 3: 加入方案

操作:

- 在候选区对一个或多个专业点击 `加入方案`

预期:

- 按钮变为 `已加入方案`
- 顶部草稿数量增加
- 当前候选视图不自动切走
- 当前页面不会自动展开草稿

补充预期:

- 新加入项仍会作为当前关注项保留高亮上下文
- 再次点击同一项不会重复加入

### 步骤 4: 展开草稿

操作:

- 点击右下角 `草稿`

预期:

- 草稿面板展开
- 顶部看到:
  - `已选草稿`
  - `去排序`
  - `收起`
- 列表中能看到已加入的草稿项

每个草稿项应支持:

- 查看 tier
- 查看院校 / 专业
- 锁定 / 解锁
- 删除

### 步骤 5: 草稿操作

操作:

- 删除一个草稿项
- 锁定一个草稿项
- 再解锁
- 点击 `收起`

预期:

- 删除后草稿数量减少
- 删除项在候选区可重新加入
- 锁定 / 解锁状态即时更新
- 收起只关闭草稿面板，不改变候选或排序主视图

实现备注:

- 前端删除草稿后会重新查询候选池，因此候选卡片上的 `已加入方案` 状态应恢复
- 当前“删除草稿”不等同于“禁用候选”，不会阻止再次加入

### 步骤 6: 进入排序

操作:

- 再次展开草稿
- 点击 `去排序`

预期:

- 主视图切到 `排序方案`
- 刷新页面后仍保持在上次停留的主视图，不会默认跳回候选
- 如果当前尚无排序结果，系统只生成一次初始底稿
- 排序区顶部看到说明条:
  - 未手动调整前显示“系统初始底稿”语义
  - 如已手动调整，说明条切换为“已包含你的手动调整”语义
- 每个排序项显示状态标签:
  - `系统初排`
  - `手动调整`
  - `已固定`
  - review 区只保留需要关注的简短风险标签，详细信息通过 hover 查看
  - 排序顶部的提醒和建议合并在同一行信息带里展示

### 步骤 7: 手动调整排序

操作:

- 对某个排序项点击 `上移`
- 对某个排序项点击 `下移`
- 对某个排序项点击 `固定位置`
- 对某个排序项点击 `删除`

预期:

- 顺序立即变化
- 手动调整过的项显示 `手动调整`
- 固定后的项显示 `已固定`
- 若对应草稿已锁定，则排序项显示 `已锁定`，且上移 / 下移 / 固定按钮不可操作
- 删除排序项后会同步从草稿移除
- 后续再切回候选或草稿再回来，顺序保持不变

### 步骤 8: 草稿变化后的排序保序

操作:

- 在已有排序结果后，再回到候选新增一个草稿项
- 或从草稿中删除一个已在排序中的项

预期:

- 已有排序不会整体重算
- 新增草稿项会追加到排序末尾
- 被删除草稿项会从排序中同步移除
- 其余排序项相对顺序保持不变

这一步是当前“用户可控性”的关键验证项。

实现备注:

- backend 当前通过 `syncOrderedPlanWithDraft()` 同步已有排序和草稿
- 同步策略是:
  - 保留仍存在于草稿中的既有排序项
  - 删除已从草稿移除的排序项
  - 将新增草稿项追加到末尾
- 不会因为草稿有增删而整体重新 regroup

## 5. 当前已知限制

- 排序区当前是按钮式上移 / 下移 / 固定，不是拖拽
- 审查标签展示依赖 review 数据，但本阶段不自动触发审查
- 草稿仍是轻量浮层，不是完整主视图
- 对话意图到 planning 动作链还未作为主流程串联

## 7. 下一步补缺方向

1. 审查的显式触发与结果回看
